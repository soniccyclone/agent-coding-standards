# A specification's state is a useful fiction nobody has to be able to compute, and every bit of nondeterminism you leave in it is room for an implementation you haven't thought of yet

**Lesson:** The commonest error in writing a specification is letting the implementation leak into it — choosing variables that mirror the data structures you expect to build, so the spec ends up describing a design rather than an obligation. The correction is to pick the state space purely for how clearly it lets you state what must be true, with no obligation that any participant can ever evaluate it. This is not a technicality. In a system built out of separate machines, the interesting abstract event can occur at a moment when no participant knows it occurred: enough parties have independently accepted the same thing that the decision is now fixed, but nobody has yet learned this and possibly nobody ever will. The abstract state changed anyway. Accepting that the specification's state is a global fiction, computed by an observer nobody has to implement, is what lets you specify such systems at all — insisting the spec talk only about facts somebody holds locally forces you to smuggle the algorithm into the requirement.

The second discipline is to write the weakest thing you can live with. Fewer actions is better, and more nondeterminism is better, because each place the spec declines to commit is a place an implementation is allowed to differ. This pays twice. Immediately, it makes the spec shorter and easier to check against. Later, it makes the spec survive: a permitted behavior you never intended is far less damaging than a forbidden behavior your best available implementation exhibits. That second failure is where impossibility results bite. If it is known that no asynchronous implementation can guarantee termination, then any specification demanding termination has already ruled out every implementation you can actually build, and the defect is in the specification, not the algorithm. So the right response to an impossibility theorem is to go back and weaken the promise until the achievable implementations satisfy it honestly — which usually means specifying only what must never go wrong, and saying nothing binding about what will eventually go right. A spec that permits a useless implementation which never answers is uncomfortable, and it is still the correct spec, because the discomfort is a property of the world.

There is a real cost to be paid somewhere, and the skill is choosing where. A spec that names an explicit set of candidate values and then picks one later is longer and has more moving parts than one that decides the instant a candidate arrives, and yet it can be the better artifact — both because more people can read it, and because it absorbs the awkward part of the reasoning (the fact that a real implementation commits much later than the abstract decision) into a small proof between two specifications, leaving the hard proof about the actual algorithm simpler. Deliberately introducing an intermediate specification to localize the ugliness of a proof is a legitimate move, and cheaper than fighting the ugliness inside the proof that matters.

A programmer who works this way writes the specification before the implementation, resists the urge to make it look like the code, and treats every "the spec should also require..." impulse as a claim needing justification rather than an obvious improvement. They also get correctness working before efficiency, knowing that each efficiency gain buys itself with a more complicated invariant — and occasionally that the honest price of an efficient implementation is a changed specification.
