# Act only on facts that can never become false again, and keep strengthening the invariant until it is something each participant can maintain alone — the algorithm is what is left over

**Lesson:** In a system with concurrency and failures, an observation is nearly worthless unless it is permanent. Anything that can revert — a count, a current leader, a liveness check, a lock you believe is held — was true when you sampled it and may be false by the time you act on the sample, and no amount of care at the call site fixes that. The design response is to identify which predicates over the system state, once true, stay true forever, and build every decision out of those only. That drives a specific structural choice: make each recorded fact write-once, so a slot that has taken a value can never take a different one, and a slot that has been ruled out can never be un-ruled-out. Monotonic facts compose into monotonic facts, and you can then define derived properties over them — this group has permanently ruled itself out, this group has permanently committed — that are equally safe to act on, even across the crash of the party that recorded them.

The second half is a proof technique that doubles as a design method. Start from the property you actually need, which is typically global and involves several parties at once, and then repeatedly strengthen it into a form that is easier to maintain rather than weaker. Strengthening sounds like the wrong direction — you are promising more — but a stronger statement is often the one that is locally maintainable, because it removes the case analysis that required knowing about other parties. Keep pushing until each conjunct is something a single participant can preserve using only what it can see in front of it. At that point the algorithm is not designed so much as read off: every action any party is allowed to take is an action that preserves the invariant, and the steps a party must take before it is entitled to act (interrogating others, forcing their undecided slots into permanent refusals) are exactly the steps that give it enough monotonic facts to establish the invariant locally.

This is why proofs about such systems can be structured to check each action independently, with the invariants as the only coupling between them. The consequence for engineering is direct and underappreciated: when you later change or add an action, you re-verify that action against the invariants and nothing else. The invariant is the interface between the parts of the correctness argument, exactly as a type signature is the interface between parts of the code, and a system whose invariants are written down is one you can keep modifying without redoing the reasoning from scratch. A system whose correctness lives only in the head of whoever wrote it has to be re-argued in full every time, which in practice means never.

A programmer who takes this on stops writing code that checks a condition and then acts on it as if the check were still valid, and starts asking of every condition: can this become false? If it can, they either make the recorded fact irreversible or they arrange for the action to be safe under retraction. They also write the invariant down next to the state it constrains, and treat "which invariant does this new code path preserve" as the first question about any change, not an afterthought.
