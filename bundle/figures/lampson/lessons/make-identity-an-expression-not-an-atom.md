# Treat the source of a request as a composed expression rather than an atomic name, and give the composition operators algebraic laws so authority can be computed instead of guessed

**Lesson:** Systems habitually record the origin of an action as a single flat token — a user id, an account, a certificate subject. In anything larger than one machine that token is a lie of compression. What actually produced a request is a user, who logged into a particular machine, running a particular operating system, executing a particular program, temporarily acting under a self-imposed restriction. The engineering instinct is to squash all of that down to the user, or to invent a separate ad-hoc field for each contributing layer. Both fail: the first destroys the information that a reviewer needs, and the second makes every new kind of contributor a new special case in every decision point.

The alternative is to admit that origin is *structured*, and to make the structure a value in a tiny language: a handful of ways to combine sources (both of these together, this one quoting that one, this one restricted to a role, this one acting on another's behalf), closed under themselves so that a composition of composites is still a legal source. What turns this from notation into leverage is insisting that each combinator obey algebraic laws with respect to a single ordering relation on sources — one source may stand in for another. If every combinator is monotone in that ordering, then a fact proved about a component still holds after the component is embedded in a larger composition, and the authority of an arbitrarily nested source can be derived mechanically from facts about its parts. Without monotonicity, every new nesting is a fresh proof obligation and the design collapses under its own generality.

The practical payoff is that the whole apparatus of the domain becomes one relation plus indirection. Membership in a group, a key standing for a person, a short name standing for a long one, a program image standing for the program's specification, a session standing for a login: these stop being five subsystems and become five instances of the same statement. What a builder does differently is resist the urge to add a mechanism per case. When a new kind of participant appears — a hardware root, a boot image, a batch agent — the question is not "what new field do I add" but "what does this stand in for, and which existing combinator expresses how it was formed." The cost of the abstraction is that the checking algorithm must be restricted to a decidable, fast fragment of the language; the fully general form is easy to write down and expensive to decide, so the deployed grammar is deliberately narrower than the theory. That trade — expressive model, restricted checkable subset — is the honest shape of the design, not a defect in it.

**Source:** [Authentication in Distributed Systems: Theory and Practice](../works/authentication-in-distributed-systems-theory-and-practice.md) — the theory section that introduces conjunction, quoting, roles and delegation as operators over a single "stands in for" ordering, together with the later section that deliberately restricts the grammar of composite sources so the access decision stays both complete and fast.
