# A rule about how costs must be attributed is an architectural constraint in disguise: decide what it forbids before you adopt it, and make sure every exhaustible resource is inside the model rather than beside it

**Lesson:** Requirements about measurement look innocent next to requirements about function. "Every unit of resource consumption must be attributable to a requester" and "the same work must cost the same regardless of what else is happening" read like accounting policy, the sort of thing that gets satisfied by instrumentation after the fact. They are nothing of the kind. Attributability demands that system activity be traceable to an individual request, which rules out any machinery that acts on its own initiative — background reclamation, speculative retention, deferred cleanup, automatic placement decisions. Predictability rules out the rest: if a request's cost must not depend on the surrounding load, then benefiting from work someone else already did is forbidden, which is a prohibition on sharing. Between them, the two constraints eliminate the entire class of implementations in which a system manages a scarce fast resource on everyone's behalf, and they do it without ever appearing in a discussion about resource management.

The consequence in the field is not subtle inefficiency but gross waste, and it arrives disguised as fairness. If nothing may be retained unless someone explicitly asked and can be billed for it, then the most heavily shared items — the directories, the tables, the common subsystems that everybody touches — are the ones that get fetched and discarded most often, because no single requester owns them. The design is behaving exactly as specified while doing enormous redundant work, and the specification's authors, having reasoned about the requirement's fairness rather than about its implications, were surprised by the magnitude.

The mirror-image failure is worth holding in the same thought, because it shows that the lesson is not simply "account for less." An explicit allocation abstraction typically covers the one or two resources everybody agrees are scarce, and every other finite quantity — table slots, identifier ranges, queue depths, indices whose width was fixed by a representation choice — sits outside it. Each of those is a wall the system can hit while the accounted resources are still plentiful, and each needs its own bespoke handling, which is to say each becomes a source of small design problems and obscure bugs. So the discipline has two halves that must be applied together: enumerate every exhaustible quantity and pull it inside a single accounting model rather than letting it become a special case, and then interrogate the strictness of that model to see which implementation strategies it is silently outlawing. A constraint you cannot name the cost of is a constraint you have not yet evaluated.
