# A system's design has to budget for its own revision: expect the first build to be discarded, keep the unchangeable surfaces few, and always retain somewhere to stand while you change them

**Lesson:** System design differs from algorithm design in a way that reorganizes the whole activity: the requirement is vague, it is complex, and it will change. That means there is no best design to find, and searching for one is wasted effort. The realistic goals are to avoid a genuinely bad structure and to divide responsibility cleanly among the parts — modest aims, but the only honest ones when the target keeps moving. The corollary most designers resist is that if any part of what the system does is actually novel, the first implementation will have to be thrown out and rebuilt to get something acceptably small, fast, and maintainable. Not patched: rebuilt. Knowing this in advance is much cheaper than discovering it, because planning for a prototype changes what you are willing to invest in the first version and stops you defending it out of sunk cost. Where a predecessor can be copied from, copy — even from a system whose ambitions were wrong, since the parts that failed for being over-general are separable from the parts that worked.

What makes revision affordable or unaffordable is the count and stability of the surfaces that parts of the system depend on each other through. An interface is exactly the set of assumptions each side must make about the other, so changing one means finding and correcting every assumption it supported, and that cost grows superlinearly with system size until it becomes intolerable regardless of how obvious the required change is. Strong static checking helps by locating the broken assumptions, but locating them is the easy half; a person still has to fix each one. Past a certain scale there is no option but to carve the system into pieces joined only by boundaries you intend to leave alone for years. This is why the temporal argument and the minimality argument are the same argument arriving from different directions: every capability you publish becomes an assumption you cannot retract, so a small interface is not merely easier to implement, it is the only kind you can afford to have been wrong about.

When a boundary must move anyway, the technique is to keep a foothold rather than to attempt a synchronized flag day. Implement the retired interface as a client of the new one, so existing dependents keep working while the underlying structure changes beneath them; the simulation usually costs a small fraction of rewriting the dependents and rarely needs to be fast. The same shape appears at very different scales, from emulating an obsolete instruction set to running whole virtual copies of a machine on itself. The general principle is to arrange for a vantage point that does not rely on the correctness of the thing you are working on. A debugger that displaces the target system entirely and inspects it as inert data can operate on layers too low to debug from within, and needs only one trivially simple mechanism to be working. Any tool that depends on the health of what it examines is useless exactly when you need it.

There is real tension here with a competing instinct. Concealing implementation choices is what preserves your freedom to revise them, but each concealed choice may also be hiding capability the clients wanted, and each additional assumption clients are permitted to make can buy substantial performance. No rule resolves it. What a designer can do is know which of the two they are trading away in each case, and notice that the balance shifts with scale: in a small module, letting parts assume more about each other is how you make it fast; in a large system, the ability to change each part independently outweighs almost everything else.
