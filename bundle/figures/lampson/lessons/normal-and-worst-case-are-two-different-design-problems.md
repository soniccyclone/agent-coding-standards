# The normal case and the worst case are two different design problems with two different success criteria, and one mechanism serving both will serve neither

**Lesson:** A designer who asks "what should this do?" as a single question is asking two questions at once and will get a mediocre answer to both. The common path is judged on speed. The pathological path is judged on a far weaker standard: that it eventually gets somewhere, that it makes progress at all. Those criteria are so different that trying to satisfy them with one mechanism forces a compromise where neither is met — the fast path carries the machinery the disaster path needs, and the disaster path inherits assumptions the fast path made about there being slack available. Separate them and each can be built honestly: a representation optimized for cheap incremental edits, plus an occasional wholesale reorganization when the incremental structure degrades; a fast allocator that assumes a cushion, plus a rationing regime that activates when the cushion is gone and deliberately serves one request at a time so the last reserve is enough to complete something. The reserve has to be sized by bounding the resources needed to release a single item, and that bound is then a permanent, acknowledged tax on the act of multiplexing the resource.

The corresponding heresy is that a system may be allowed to fail outright in the worst case, provided the failure is detected mechanically and is rare. Deadlocking, starving a client, or restarting from scratch are all acceptable outcomes if the alternative is carrying prevention machinery through every ordinary operation. This trade only looks reckless if you believe the failure is otherwise avoidable. It isn't: hardware faults and bugs already guarantee that recovery must exist, so the recovery path is a sunk cost, and once it exists, permitting a few more entries into it buys real speed for free. Refusing to admit failure into the design is what produces systems that are simultaneously slow and fragile — the guarantee costs everyone constantly and still cannot be honored when the network partitions.

The same reasoning inverts the usual goal of resource allocation. Nobody has ever succeeded at optimizing the use of a shared resource in a general-purpose system: decades of attempts to predict reference patterns, cluster related code, or tune scheduling on rich state all produced nothing that beat crude demand-driven schemes with adequate slack. Only the very coarsest distinctions produce intelligible effects. What actually matters is staying away from the cliff, because degradation past saturation is catastrophic rather than gradual. So the objective is not to maximize utilization but to avoid ruin, which means overprovisioning the resource that is cheap and refusing work when demand exceeds what can be served. Shedding load is the constructive form of this: turn users away, discard packets, restart. Cleverness only pays where the load is known precisely enough to characterize, and a general-purpose system is by definition not that.

A programmer who takes this seriously stops writing one code path that tries to be robust and quick at the same time. They ask what the fast case actually is, build for it without defensive weight, then ask separately what happens when the assumption underneath it fails, and answer that with a slow mechanism whose only obligation is to move forward. They also stop treating high utilization as evidence of a well-tuned system and start treating it as proximity to a cliff.
