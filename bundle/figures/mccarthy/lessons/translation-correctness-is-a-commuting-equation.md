# State the criterion before the method, and a translator's correctness becomes an equation between two routes rather than a matter of testing

**Lesson:** The distinction the paper insists on before anything else is between a problem and a procedure, and it is routinely collapsed in practice. A problem is nothing but the criterion that decides whether a candidate answer is acceptable; you can understand one perfectly while possessing no method whatever for solving it. A procedure is a way of producing candidates. Once the two are kept apart, "is this code correct?" stops being a vague question, because correctness is a relation between an artifact and a criterion that was stated independently of it — and code with no independently stated criterion is not incorrect, it is simply not the kind of thing about which correctness can be claimed.

Apply that discipline to a compiler and you get something sharp. Give the source language a meaning: a function from a program and an initial assignment of values to variables to the final assignment. Give the target machine a meaning of the same shape, over its own notion of state. Give a representation mapping that says how a source-level state is laid out as a machine state. The translator is then correct exactly when two routes agree: run the source program abstractly and then represent the result, versus represent the input and then run the translated program. One equation, and it says everything — no test suite, no appeal to typical cases. Note also what falls out of the framing: the translation function is a mathematical object distinct from any program that computes it, so a compiler is a further, separate thing — a machine program which, applied to a represented source program, produces what the translation function specifies. Keeping those two apart is what lets you talk about a compiler being a correct implementation of a correct translation.

The reason this framing is worth the trouble is that it is the only known way to get out from under debugging. Testing a program on inputs one hopes are representative until the failures stop is a procedure whose hope is frequently unfounded, and no amount of it establishes the equation above. Proving the equation does. The same shape generalizes far past compilers: any time you have two implementations of the same abstraction at different levels — an in-memory model and its serialized form, an interpreter and an optimizing pipeline, a data structure and its persisted layout — the meaningful correctness statement is that translating and then operating agrees with operating and then translating, and that statement is checkable in a way that spot-checks are not.

A programmer who has internalized this writes the acceptance criterion first, as a thing that exists apart from the implementation, and treats every layer boundary as a place where a commuting condition ought to be stated even when it will not be formally proved. Even unproven, the condition is worth writing, because it names precisely what the layer promises and turns "the translation looks right" into a claim with a truth value.

**Source:** [Towards a Mathematical Science of Computation](../works/towards-a-mathematical-science-of-computation.md) — the early section distinguishing problems from procedures and the enumeration of the kinds of facts one wants to prove about programs; then the closing part of the semantics section, which defines the meaning of a program as its effect on the variable assignment, defines a machine the same way, and states correctness of translation as the agreement of the two routes through the representation mapping, separating the translation function from the compiler that realizes it. The argument against debugging appears in the section on practical applications.
