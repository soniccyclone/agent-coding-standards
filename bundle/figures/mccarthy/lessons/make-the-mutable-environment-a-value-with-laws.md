# Turn the mutable environment into a single value with stated laws, and imperative code becomes reasonable by the same means as functional code

**Lesson:** Assignment and jumping look like a different universe from equations between functions, and the usual response is to build a separate reasoning apparatus for each. There is a cheaper unification. Collect every variable a program mutates into one composite value — for machine code, the contents of every register the program disturbs — and a block with one entrance and one exit stops being a sequence of effects and becomes a function from that value to a new one. Branch targets get their own such functions, and a control-flow graph transcribes directly into a set of mutually recursive equations that carry exactly the information the graph did, no more and no less. There is nothing left to reason about that is peculiar to imperative form.

For this to be usable, the composite value needs an interface with laws rather than an intuition. Two operations suffice: read the value currently bound to a name, and produce the environment that results from rebinding one name while leaving the rest alone. Three equations then say everything about how mutation behaves — reading after a write returns the written value if the names match and otherwise sees through to the prior environment; rebinding a name to what it already holds changes nothing; and two writes to distinct names commute, while two writes to the same name collapse to the later one. Those laws are the entire semantic content of mutable variables, and once they are written down, equational proof over imperative programs proceeds exactly as it does over recursive definitions: it is only that the formulas get longer. The paper goes further and shows the reasoning can be carried out on the imperative text directly, by peeling one iteration off a loop, introducing a branch whose two arms do the same thing, simplifying each arm under the condition that reached it, and continuing until two visibly different programs are seen to satisfy the same equation.

The correspondence is not symmetric, and the asymmetry is the practical payload. Every control-flow graph becomes a recursion, but only recursions of a restricted shape come back the other way: the self-reference must sit in tail position, never nested inside the argument of something else. Definitions of that shape are loops. Definitions that are not of that shape need an explicit stack to become loops, and the paper's observation is that arithmetic computations can usually be massaged into the restricted shape while computations over symbolic structure usually cannot. That tells you something real about cost — the presence or absence of a stack is not an implementation accident, it is a structural property of the recursion visible in the definition before you compile anything.

A programmer who thinks this way represents state explicitly at the boundaries of anything they intend to reason about, so a stateful component can be discussed as a function of an environment rather than as an accumulation of history. They state the access and update laws of any environment-like abstraction they build — a context object, a store, a register file — because those laws are what makes reasoning possible and their absence is what makes stateful code opaque. And they read tail position as a load-bearing property rather than a stylistic one.
