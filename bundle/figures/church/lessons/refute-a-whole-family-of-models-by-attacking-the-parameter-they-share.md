# Refute a whole family of approximations at once by attacking the parameter they share, not the design of any one of them

The question is whether the intuitionistic propositional calculus can be captured by a table of truth-values the way the classical one is captured by two — some finite set of values, some designated subset, some tables for the connectives, such that the tautologies are exactly the theorems. Church presents Gödel's answer, and the answer does not examine any candidate table. It builds one family of formulas: for each number of variables, the disjunction of all the pairwise equivalences among them. Two facts are established about it. It is not a theorem of the calculus, for any number of variables. And it becomes a theorem the moment any two of its variables are made the same. Put those together with a proposed table having some fixed number of values, take more variables than the table has values, and the pigeonhole does the rest: some two variables must receive the same value, the formula therefore evaluates as it does under identification, and it comes out designated. So it is a tautology under that table and not a theorem, and the table fails. Every finite table fails, by the same paragraph, without any of them being inspected.

The technique is worth separating from the result. Refuting an approximation one design at a time is unbounded work and the designs keep coming. Refuting the parameter is bounded work and it closes the question. The move requires finding the property that every member of the family must have merely by virtue of the parameter — here, that finitely many values must collide once you supply enough distinct things — and then constructing a witness that turns collision into the wrong answer. Church notes in the same place that a system of truth-values that *is* characteristic exists once infinitely many values are allowed, which is what makes the argument informative rather than merely negative: it identifies finiteness, and nothing else, as the obstruction.

Engineers face the same question constantly and usually answer it empirically, which does not terminate. Can a fixed-size summary distinguish these states? Can a finite abstract domain analyze this program precisely? Can a fixed-length fingerprint identify these documents? Can a model with a bounded queue capture this protocol? Can a schema with an enum of statuses represent this workflow? The empirical answer — try one, find a counterexample, try a bigger one — never ends, because each failure looks like a sizing problem and invites a larger size. The structural answer ends it: if the thing being modeled makes more distinctions than the model has states, some pair is conflated, and if you can exhibit a property that becomes true under conflation and is false in general, no size works. The conclusion is not "use a bigger table"; it is "this family cannot do the job, so change the family."

Two further habits come with it. First, when you do prove a family inadequate, say what parameter was doing the work, because that tells you what to relax — unbounded values, unbounded memory, a different kind of abstraction entirely. A refutation that identifies the obstruction is a design constraint; one that just says "it doesn't work" is a dead end. Second, notice the shape of the witness. It was not an adversarial edge case; it was an ordinary family of inputs, scaled past the model's capacity, together with an observation about what happens when the model is forced to conflate. That construction is usually available and is usually cheaper than the search it replaces.
