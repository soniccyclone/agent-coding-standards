# Any notation you can actually write in names only countably much, so the expressive ceiling is arithmetic, not a failure of cleverness

Church pauses, in the middle of setting up how expressions with free variables determine functions, to record a limit that no amount of design effort can move. The expressions available in any particular language can be listed one after another; the functions from real numbers to real numbers cannot. So there is no language, and no system of notation whatever, in which every such function is picked out by some expression. The same counting argument denies you proper names for all the real numbers themselves. He is careful about why this is not evaded by the obvious trick: an unending decimal expansion is not a name, because a name has to be something that can actually be written down and used as a constituent of a written sentence, and an infinite expansion never can be. Finiteness of the naming expression is a requirement of the notion of a name, not an incidental limitation of paper.

What makes this worth keeping is that the ceiling has nothing to do with the quality of the notation. It is not that the language is impoverished, or that a better primitive basis would reach further, or that the next generation of designers will do better. Any notation a person can write in has countably many expressions, and that alone settles which fraction of the space of possible behaviors is reachable. Enriching the vocabulary, adding primitives, allowing abbreviation — all of these change which countable slice you get, never the cardinality of the slice. Church's own practice reflects this: he treats the interesting question not as whether a language can say everything, but as which analysis of the subject matter its finite apparatus makes it easy to say.

There is a second, sharper edge on the finiteness requirement. Church distinguishes the function itself from any expression determining it, and notes that a function need not be the associated function of any form at all. So an object can exist perfectly well and still have no finite designation in the language you are working in. Reasoning about it then has to proceed through whatever finite descriptions do exist — properties, constraints, generating rules — never through the object itself. The finite rule that produces the infinite thing is the only handle there is.

For a programmer the arithmetic bites immediately. The programs expressible in any language form a countable set; the functions from inputs to outputs do not, so almost every possible behavior has no program, in every language, forever. That reframes several familiar frustrations as the same fact. A configuration format that requires one entry per case cannot cover a space that grows without bound, and no amount of format design fixes it — only a rule that generates the entries. A test suite that enumerates examples is a finite object approximating an uncountable one, so the interesting question is never coverage but which finite description of correctness you can write. A lookup table, a hand-maintained mapping, an exhaustive switch: each is a bet that the space is small, and each fails the same way when it is not. And when a requirement cannot be stated finitely, the honest response is that it has not been specified yet — you have gestured at a set, not defined one.

**Source:** [Introduction to Mathematical Logic](../works/introduction-to-mathematical-logic.md) — the section on functions, and its accompanying remarks on why the enumerability of the forms of a language, set against the non-enumerability of the functions on the reals, rules out any notation in which every function is the associated function of some form, together with the argument that an infinite expansion cannot serve as a name.
