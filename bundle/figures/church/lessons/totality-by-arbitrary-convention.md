# You can buy unconditional downstream laws by totalizing a partial operation with one arbitrary fixed choice, and the bill comes due wherever the filler value is read as an answer

Church introduces an operator that forms a name for the unique thing satisfying a given condition. The construction is only meaningful when exactly one thing satisfies it, and he faces the degenerate cases directly: nothing satisfies the condition, or several things do. He lists the options. Natural language, he observes, would hand back an expression that carries a meaning but designates nothing. He declines that route and instead picks some particular value, arbitrarily, and declares it to be what the name designates in every degenerate case — with the stipulation that the pick is made once and for all for each collection of values, not case by case. Nothing about the chosen value recommends it; the point is only that a choice exists and is fixed.

The purchase this makes is visible a few sections earlier, where he states that his formalized languages will be built so that every name, sentences included, designates something. That is not a metaphysical preference, it is an economy. If designation can fail, then every rule, every derivation step, and every stated law has to carry a side condition about definedness, and every proof has to discharge it. Making the operation total by fiat removes the side conditions from the entire body of downstream reasoning at the cost of one deliberately meaningless stipulation at the boundary. He can afford it because no result he cares about ever appeals to the value chosen — the filler exists so the machinery has something to grip, and is never read as an answer to anything.

That last condition is exactly the one engineering violates, and it is what separates the technique from the disaster. Totalizing is right when the win is unconditional laws and nothing downstream consumes the filler as information. It is wrong the moment the filler can reach a decision or a display, because then a question with no answer has been silently replaced by an answer, and the failure that would have surfaced at the boundary instead travels as ordinary-looking data until it emerges somewhere with no trace of where it came from. Note also the discipline in the stipulation being fixed once and for all: a filler that varies by call site or by run is worse than either alternative, since the unconditional law you bought no longer holds and the errors are now nondeterministic too.

So there are three honest treatments of a partial operation and the choice among them is a design decision, not a matter of taste. Forbid the bad input at construction time, so the case cannot arise. Let the operation designate nothing and pay the side condition in every downstream rule, which is the right price when the caller must be forced to handle absence. Or totalize by arbitrary convention and get side-condition-free laws, valid only if the convention's value is never mistaken for a result. Every familiar mechanism a programmer already knows sits in one of these slots — a default returned for a missing key, a saturating or wrapping arithmetic, a not-a-number that propagates, an absence-typed return, a constructor that refuses to build the illegal case — and the mechanism is usually chosen by habit rather than by asking which of the three properties the surrounding code actually needs. The question to ask is simple: is anything going to read this value and believe it?
