# Declaring an equality is cheap; the obligation that every operation respects it is paid separately for each operation and each argument position

Church extends the predicate calculus with equality, and the way he has to do it is instructive. Naming the relation and stating that everything equals itself takes one line. Getting the property everyone actually wants from equality — that equals may be swapped for equals — takes an axiom schema with infinitely many instances, one for each context in which the substitution might occur. When he restricts to a system with only finitely many operations, he can replace the schema by a finite list, and the shape of that list is the point: reflexivity, symmetry and transitivity, and then, for *each* operation, one axiom per argument position saying that replacing an equal in that slot preserves the result. A unary operation costs one; a binary operation costs two; a ternary, three. Add another operation to the language and you owe another handful of axioms, and nothing about the original equality axioms supplies them.

The structural claim is that equality decomposes into two things that get conflated. One is the relation itself — an equivalence, self-standing, easy, and by itself almost useless. The other is a claim about the rest of the system: that every construct in the language is blind to the difference between related elements. The second is not a property of the relation at all. It is a property of each operation, discharged operation by operation, and there is no general argument that covers a construct you have not examined. The infinite schema is exactly the admission that with unboundedly many contexts you have unboundedly many obligations; the finite list is what you get when the surface is finite, and it scales with the surface.

Programmers meet the identical structure and usually only pay for the first half. Defining an equality method on a type is a small local edit. The thing that makes it trustworthy is that every operation touching that type produces indistinguishable results on equal inputs — hashing, ordering, serialization, cache lookup, set membership, database round-trip, logging, diffing, the comparison a test uses. Each of these is a separate obligation, and each one is a place where the equality silently fails to be a congruence. The classic symptoms are all congruence failures: two objects that compare equal but hash differently and so appear twice in a set; a value that equals another before serialization and not after; a comparator inconsistent with equals so a sorted container loses elements. Nobody wrote a bug; somebody defined a relation and did not check that a particular operation respects it.

Two working consequences follow. First, the cost of introducing a notion of sameness is proportional to the size of the surface it must hold across, not to the difficulty of writing the predicate — which is why a project-wide "canonical form" or "semantic equality" is a far larger commitment than it looks, and why domain-specific equalities scoped to a few operations are often the cheaper correct answer. Second, adding a new operation to a type with a custom equality is not a neutral addition. It is a new proof obligation, and it should be treated the way Church treats it: as a line item that must be written down and checked, not as something inherited from the equality that already exists.

**Source:** [Introduction to Mathematical Logic](../works/introduction-to-mathematical-logic.md) — the section on the functional calculus of first order with equality, where the substitutivity property is given as an axiom schema over all contexts and is then shown, for a calculus with finitely many functional constants, to be replaceable by a finite set: the reflexive, commutative and transitive laws together with one substitutivity axiom for each argument position of each functional constant.
