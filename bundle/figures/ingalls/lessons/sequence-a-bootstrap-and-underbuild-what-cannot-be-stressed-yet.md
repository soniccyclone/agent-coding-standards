# Treat the order of a bootstrap as a design artifact: make every stage observable, and deliberately under-build whatever that stage cannot stress

**Lesson:** Bringing up a system that will eventually host itself is a sequencing problem, and the sequence deserves as much design attention as the architecture does. The property to sequence for is that every stage produces something you can watch: a few instructions interpreted, then an expression evaluated and printed, then a window drawn, then the whole interface moving slowly. This is usually defended as morale, and morale is real, but it is the same property as testability — a stage with no observable output also has nothing you can check, so its defects wait and arrive later mixed with everyone else's. Ordering by observability therefore buys two things at once, and it is worth reordering work that has no other reason to be reordered in order to get it.

The rule that makes such a sequence cheap is to ask of each component not how to build it well but what the weakest version is that the current stage cannot break. A partial system is feeble, and its feebleness bounds the demands it can place on its own scaffolding: storage management can be a bare allocator that never reclaims anything while the system only executes a handful of instructions, because it will never run long enough to exhaust memory. Answering that question requires knowing what the stage can actually reach, which is a concrete analysis rather than optimism, and it is what distinguishes deliberate under-building from carelessness. Consciously choosing the inadequate version dominates the instinct to finish each component before moving on, because the finished version would have been designed against guesses about a system that does not exist yet.

Three further habits belong to the same discipline. Borrow a working instance of the thing you are building as your host, keep the old one authoritative, and make the moment of independence an explicit milestone rather than a gradual drift — until you cross it you carry work forward from the old system, and after it you never look back. Build components in parallel where the dependency graph permits, since two immature components exercise each other: while the translator was being written, running the untranslated system found and fixed most of its bugs. And instrument the bootstrap far past what production would tolerate, with checks on every low-level access, while recording that the instrumentation is scheduled for removal. Its removal is a legitimate later performance improvement, which means early performance numbers are measurements of the scaffolding rather than of the artifact, and should not be argued about as if they were the real thing.

**Source:** [Back to the Future: The Story of Squeak](../works/back-to-the-future-the-story-of-squeak.md) — the project-plan section, with its ordered stages from new image format through typing in the published interpreter description to designing the translator, its claim that facilities became available just as they were needed, its example of debugging the interpreter and object memory using a temporary allocator with no way to reclaim garbage because the system executed too few instructions to run out, its note that most interpreter and object-memory bugs were found by running under an existing Smalltalk while the translator was being prepared, its week-by-week record of visible milestones from simulated instructions through an evaluated expression and a displayed window to the point of crossing over into self-evolution and full self-support, and its explicit attention to remaining motivated; plus the optimization section's attribution of the earliest performance leaps partly to the removal of scaffolding such as assertion checks and range checks on memory references.
