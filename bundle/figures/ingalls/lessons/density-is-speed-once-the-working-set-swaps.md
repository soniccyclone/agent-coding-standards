# Once the working set has to be swapped, density is speed — so encode by census and frequency, and keep the encoding invertible

**Lesson:** The habitual trade of size against speed holds only while everything in use fits in the fast store. Past that point the trade inverts, because the dominant cost is no longer instructions executed but material moved through the memory hierarchy, and a representation a quarter the size of the obvious one produces a working set that stops being evicted. This reverses the instinctive moves: widening, unrolling, and duplicating to save work each buy local speed at the price of the thing that actually determines throughput. So the size of your representation is a performance parameter, and it should be chosen with reference to the capacity of the level of storage the program has to live in, not from an abstract preference for fast decoding. The practical consequence is that being willing to give up some raw execution speed for compactness can leave you faster overall, which is the sort of claim that sounds like a rationalization until you notice it was made by measuring rather than by intuition.

The method for getting density is worth separating from the goal. Do not invent an instruction set; take a census of the categories your language actually has, and give one short code to each frequent member of each category. The categories fall out of the semantics: the distinct places a value can come from, the distinct ways control can move, the handful of constants that appear constantly. That census-driven encoding is dense precisely where programs are repetitive, and it stays honest about the tail by providing extension codes — an escape followed by a wider field — so the unusual case is merely longer rather than unrepresentable. This is a much better discipline than choosing a uniform width, because a uniform width is set by the worst case and therefore pays for the rare case on every occurrence of the common one. It also produces an encoding whose units correspond to things a reader of the language already knows, which is what makes the encoded form comprehensible at all. Related and often skipped: anything derivable at translation time should be computed then and carried at the head of each unit, so beginning an execution is initialization from stored constants rather than analysis.

There is one obligation that comes with compressing a program's representation, and forgetting it cancels the benefit. If the compact form cannot be turned back into the readable form, you must keep both, and keeping both means the saving was never real. So an encoding intended to buy space should be designed to be reconstructible into something a person can read, and whether you actually need to exercise that reconstruction is a separate matter that depends on whether you have somewhere cheap to keep the readable copy. Stating it as a design property rather than a happy accident is what keeps the option open — the general form being that a lossy compression of an artifact people must still be able to read is a decision to store two artifacts, and should be recognized as such before it is made.
