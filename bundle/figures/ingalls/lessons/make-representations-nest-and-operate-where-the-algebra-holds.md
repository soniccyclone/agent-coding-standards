# Design representations so the cheap conversion is the correct one, quantize the parameter you cannot afford exactly, and perform each operation in the space where its algebra actually holds

**Lesson:** A mechanism that has to move data between representations of different widths and kinds needs a default conversion, and the interesting question is not how to implement one but how to make the obvious implementation correct. It can be arranged: if each smaller value set is chosen as a subset of the next larger one, then padding with zeros on the way up and truncating on the way down are not approximations, they are the right answer, and no table is required for the whole family of conversions. That correctness is bought before any conversion code exists, by a decision about the value sets themselves. So when two representations of the same thing must interconvert, spend the design effort on making them nest rather than on making the conversion smart — and reserve the explicit override for the pairs that genuinely do not nest, which will be few.

For those, the override is typically a table indexed by the source value, and exactness stops being affordable as the source widens: one entry per possible value is unremarkable for a byte and absurd for a full word. The instinct at that point is either to refuse the wide case or to write a separate procedure for it, and both are worse than the third option — accept a coarser table and reduce the input's precision to match before indexing it. One mechanism then spans every width, with table size exposed as an accuracy knob the caller sets. This is the general escape whenever a general mechanism appears not to scale into some regime: look for a lossy projection of the input onto the domain the mechanism already handles, and make the loss a parameter rather than a limitation. Keeping a single code path is worth more than the last bits of fidelity, because a special case for the large inputs is a second implementation of the same operation, and second implementations are where behavior diverges.

The third rule concerns operations rather than conversions. Some operations are simply not defined in the representation you were handed: averaging indices into a palette is meaningless, since neighbouring indices need not name neighbouring values. The temptation is to define some plausible approximation in that space anyway. The better move is to transport into a space where the operation genuinely means what you intend, perform it there, and map the result back through the conversion you already have. You pay two conversions per operation and you get a result that is correct by definition instead of correct by argument. Stated generally: before implementing an operation over a representation, check that the representation supports the operation's algebra at all. If it does not, the implementation belongs in the space that does, and the representation's only job is to get in and out of that space.
