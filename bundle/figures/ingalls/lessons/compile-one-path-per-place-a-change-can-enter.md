# Compile a propagation structure by enumerating the places a change can enter and emitting one straight-line path for each

**Lesson:** A structure whose meaning is "disturb this value and these consequences follow" looks like it must be interpreted: keep the dependency graph at run time, and after every change search it for what to update next. That reading is a failure of imagination. If the dependencies are acyclic, the set of points where a disturbance can originate is finite and can be listed, and for each one the consequences form a fixed order that a topological sort computes once, ahead of time. So you do not compile the structure. You compile one specialized routine per origin of change, each a straight sequence of steps with no search in it, and the graph itself stops existing at run time. The residue each routine works on is small: a cell for every sub-part and a cell for the value currently resting on every dependency edge, with the routine doing nothing but reading and writing those cells in a predetermined order. Generalize the move: whenever a declarative model's semantics are stated as a perturbation and its consequences, specializing on the perturbation site is the compilation strategy, and its cost is proportional to the number of sites rather than to the model's cleverness.

Two things must be got right for the strategy to be complete rather than merely plausible. First, disturbances do not only arrive at the outer boundary. Parts in the interior generate them spontaneously — anything wired to a person, a clock, an instrument — so consequences have to be able to travel outward from an interior point into the enclosing structure, not just inward from its edge. Enumerating entry points is therefore a question about the whole nesting, and a scheme that only handles inbound disturbance silently breaks the moment a construction is used as a part inside another one. Second, the specialized routines overlap heavily, because two nearby entry points share a long tail of consequence. Those tails show up as repeated subsequences in the emitted code and can be factored back into shared routines afterward. That is the right order of operations: specialize first, then re-share what the emitted code shows to be duplicated. Refusing to specialize in order to avoid duplication gives up the whole benefit to forestall a problem that is easier to fix once you can see it.

What this buys is the reconciliation of two things usually traded against each other: a medium can be alive under the author's hand and also compact and fast when shipped, because the fast form is derived from the live one rather than written beside it. That derivation is what makes the author's experience during construction evidence about the delivered artifact — a claim you forfeit the moment the two representations are maintained independently. It is worth insisting, too, that the compiler's output be an ordinary definition in the host system, whose instances hold the sub-parts and resting values as ordinary storage, rather than a private encoding only the compiler understands. An output made of the same material as everything else stays open to the tools that already exist, so compiling something does not cost you the ability to look inside it.

**Source:** [Fabrik: A Visual Programming Environment](../works/fabrik-a-visual-programming-environment.md) — the compilation section, which maps a diagram's interpretive behaviour into a class definition holding one storage cell per sub-component and per wire-borne datum, derives a linear traversal per data perturbation by topological sort, distinguishes traversal routines for disturbances arriving at the boundary from radiation routines for disturbances originating in nested sub-parts, and notes the common instruction subsequences between two such routines as an opportunity to compress the generated code afterward.
