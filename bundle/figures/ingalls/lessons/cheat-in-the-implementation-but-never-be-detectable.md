# Cheat in the implementation but stay undetectable: guard the frequent case and fall through to the general one

**Lesson:** Take a uniform model as far down as it will go — down into integer addition, down into whatever the machine would rather do natively — and the honest consequence is that it will be slow on any machine not built for it. The wrong responses are both common: abandon uniformity at the bottom and admit a class of things the model does not describe, or defend it and ship something too slow to use. The right response separates two claims that get conflated. Uniformity is a property of what a program can observe, not a property of the code that runs it. So the implementation may special-case anything it likes, provided nothing above can tell the difference. The condition is not decorative; it is what makes the concession safe, because a difference that programs can detect eventually becomes a difference they depend on, and then the model has quietly acquired an exception nobody wrote down.

The structural discipline that keeps the concession undetectable is to make the fast path a guarded prefix of the general one rather than a parallel implementation of it. Check cheaply for the frequent shape; if it holds, do the work inline and continue; if the check fails, drop into the general mechanism which was never modified. Two implementations of the same operation drift apart and produce exactly the observable divergence you promised would not exist, while a prefix plus a fall-through cannot: there is still only one definition of the general case, and the fast path can only ever skip work, never redefine it. The same shape recurs above the interpreter as well. When an automatic bookkeeping mechanism costs more than the values it protects are worth, exempt the dominant class of values by making their representation self-evident from the reference itself, so that the bookkeeping is not skipped conditionally but is inapplicable by construction.

Which cases deserve this treatment is a measurement question, and the measurement is about the traffic rather than the vocabulary. The operations worth an inline path are the few that dominate the flow of data in practice — small-integer arithmetic, indexing, character handling, advancing a stream — not the ones that look most important in the manual. This inverts the usual instinct to optimize the impressive parts. It also gives a clean criterion for a self-describing system's own inner machinery: the fastest layer is allowed to stop obeying the metaphor internally, so long as it performs the identical steps and leaves the objects it manipulates fully ordinary to everyone else. That combination is what lets a system be uniform in its semantics and pragmatic in its execution without the two facts fighting.

**Source:** [The Smalltalk-76 Programming System: Design and Implementation](../works/the-smalltalk-76-programming-system-design-and-implementation.md) — the efficient-message-handling section, whose stated rule is that the implementor must cheat without being caught and that no non-uniformity may be perceptible to the user, realized by assigning special code syllables to the most frequent operations, checking inline whether both operands are integers and proceeding without symbol lookup or environment creation, and passing control to the ordinary sending code whenever the check fails; the note that the microcode interpreter performs the same steps as sending messages to activation records without actually sending them; and the storage-management section's exemption of small integers from reference counting via distinguished references, justified by their dominance of the data flow.
