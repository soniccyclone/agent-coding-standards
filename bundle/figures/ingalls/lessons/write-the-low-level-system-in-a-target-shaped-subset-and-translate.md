# Never write the low-level system in the low-level language: write it in a subset of your good language shaped like the target, and translate

**Lesson:** The usual reasoning is that portability and speed require the low-level language, therefore the system must be written in it, therefore you inherit its tooling and its debugging experience for the life of the project. The middle step is where the error is. What portability and speed require is that low-level code be *produced*, not that it be *authored*. So author in the language with the good tools, restricted to a subset that maps one-for-one onto the target's constructs, and generate the rest. The restriction is the whole trick and it must be severe: no closures beyond a few control forms, no dynamic dispatch, no objects at all, arithmetic and array access only in the shapes the machine already has. What is left barely resembles the language it is a subset of, and that is the point — a subset that mirrors the target needs no runtime support underneath it, so the generated code runs at the speed of code written in the target directly, and the generator itself is a table of a few dozen rewrite rules over parse trees rather than a compiler project.

Two consequences of choosing severity are worth naming because they invert common expectations. First, scope the generator to exactly one client — your own system — and refuse the general problem of translating the full language. Generality here would demand emulating the source language's semantics in the target's runtime, which costs both the performance and the simplicity you were buying. A tool built for one caller can be finished in the time a general one takes to specify. Second, the need for type annotations is a function of the distance between source and target rather than a property of the source language. When the subset's operations already correspond to the machine's own data types, a translator has nothing left to infer and annotations would tell it nothing it does not know. Requests for a declaration syntax are therefore evidence that the subset is still too expressive, and the cheaper fix is to narrow the subset rather than to enrich the input.

The deeper payoff is that one text serves as both the debuggable artifact and the delivered one. Run it interpreted inside the live environment and it is hundreds of times too slow for production but fully open: any step can be halted, inspected, counted, and profiled with the ordinary tools, including the innermost loops that would otherwise be the least approachable code in the system. Translate the same text and you have the shipping engine. Because the transport between the two regimes is mechanical, correctness established in the slow regime carries over without re-establishment — code exercised for weeks interpreted has been observed to work on its first translated run. That is the practical case against maintaining an explanatory model beside a real implementation: two texts diverge and the readable one slowly becomes a lie, while one text with two execution regimes cannot. Establish correctness where observation is cheap, obtain speed by a transformation that cannot change meaning, and never debug the fast version at all.

**Source:** [Back to the Future: The Story of Squeak](../works/back-to-the-future-the-story-of-squeak.md) — the translation section, which states the authors' unwillingness to write in C, the decision to write and debug the virtual machine in Smalltalk while building a Smalltalk-to-C translator in parallel, the restriction of the virtual machine to a subset excluding blocks, message sending and objects so it maps directly onto C constructs with methods becoming functions and instance variables becoming globals, the table of roughly forty-two rewrite rules over parse trees, the contrast drawn with translators supporting full semantics that must depend on the source language's runtime, the argument that the subset maps so closely onto hardware data types that type declarations would not help, and the note that the Blue Book's Smalltalk description of a virtual machine was intended only as an explanatory model rather than working source; together with the interpreter section's simulator subclass running the identical code inside Smalltalk for stopping, inspecting and instrumenting, the measured factor of roughly 450 between the two regimes, and the sound-synthesis account of methods runnable either interpreted or translated without changing a line, which worked correctly on their first translated execution after weeks of interpreted use.
