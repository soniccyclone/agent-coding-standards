# A self-describing system needs a floor: make it a couple of operations, name where the discipline stops, and keep a readable model beside the fast one

**Lesson:** A system described in its own terms cannot be described all the way down. Somewhere the rule it enforces on everyone else has to be broken, because the mechanism that implements the rule needs access of a kind the rule forbids — reaching a component of a thing by position rather than by asking it. This is not a flaw to be argued away; it is the floor, and the only real design questions about it are how many operations it consists of and how many places in the system use them. Two operations, used in exactly one place, is a floor you can describe in a sentence and audit by inspection. The same operations available everywhere as a convenience is no longer a floor but a bypass, and a bypass makes every claim about the discipline above it unfalsifiable. So state where the buck stops, keep it to a countable set, and treat the number of call sites as a property worth defending rather than an accident of convenience.

The second half of describing a system in itself is to accept that the description and the fast implementation are different artifacts with different jobs. A model of the machine written in the language the machine runs is what makes the machine comprehensible, analyzable, and simulable step by step. It is not what you execute; that will be something closer to the hardware, obeying the same steps by faster means. Holding both is not duplication to be eliminated, because they answer different questions: the model is the authority on what the machine means, the implementation is the authority on how long it takes. What does need care is preventing the model from being mistaken for a verified specification. If it is simplified relative to the real thing, or has not been checked in detail, that has to be said plainly next to it, because a readable model presented as authoritative is worse than none — everyone will reason from it, and the places it was smoothed over are exactly the places that will surprise them.

The general shape here applies well beyond language implementation. Any system that claims to be built out of its own materials should be able to answer three questions crisply: which primitive capabilities are outside the discipline, where exactly they are used, and which artifact is the readable statement of what the system means as opposed to the one tuned for execution. Systems that cannot answer these usually turn out to have a diffuse floor — privileged access scattered wherever it was once expedient — and a diffuse floor is the thing that quietly makes a self-describing system undescribable.
