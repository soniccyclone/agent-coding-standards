# Reason about a component against an environment allowed to do anything except touch what the component owns

**Lesson:** To reason about one process without dragging in the rest of the system, Manna and Pnueli replace everything outside the process with a single nondeterministic step that may scramble any state at all, subject to one restriction: it cannot modify state the process owns, where ownership means exactly one component ever writes it. Under that model the component admits strictly more behaviors than it does in any real system, so anything you prove about it holds in every context you might drop it into, including the actual one. The direction of the guarantee is stated plainly and the converse is shown to fail: a property that holds when the component sits in its real neighborhood may be unprovable in the arbitrary-context model, because that model lets the environment do things no real neighbor would. This is over-approximation as an engineering choice — accept some unprovable-but-true claims in exchange for conclusions that survive any composition.

The ownership discipline is what makes the whole thing work, and it is a constraint on program structure rather than on the proof. If two components can both write a variable, there is no way to describe either one's environment as something that leaves the component's own state alone, and the decomposition collapses. So a reasoning technique reaches back and dictates an architectural rule: single writer per piece of mutable state. That is worth noticing on its own. The verification method did not adapt itself to arbitrary code; it named the code shape under which local reasoning is possible at all.

The consequences show up in the shape of what you can prove locally, and this is the part that transfers. A component in isolation can rarely promise the thing you actually want, because the environment is free to undo the premise the promise rested on. What comes out of a local argument is a weaker disjunction: eventually the good thing happens, or the environment reneged on the condition I was relying on. Their small handshake example produces exactly that shape at each step. The stronger claim is recovered by pairing the local result with a separately-established global fact that rules out the reneging — a monotonicity invariant showing that once a signal is raised it is never lowered. Local reasoning and global reasoning alternate, each making the next step of the other cheaper, and neither is asked to do the whole job.

A programmer who works this way specifies each component against a hostile-but-bounded environment rather than against the neighbors it currently happens to have, and states the bound as an ownership fact: this is mine to write, everything else may change under me at any moment. They expect component-level guarantees to come out conditional, and they treat the conditions as first-class deliverables — a small set of global invariants that the composition must establish, which is precisely the interface between the pieces. The alternative, proving things about a component in the context of its current siblings, produces claims that quietly break the next time the component is reused, and gives no artifact naming what it needed from its neighbors.

**Source:** [Temporal Verification of Reactive Systems: Progress](../works/temporal-verification-of-reactive-systems-progress.md) — the compositional-verification sections of the Response chapter, which define modular computations via variable ownership and an arbitrary environment step, state the one-way relationship between whole-program and modular computations, give the compositional rules for safety and response, and work the handshake example where each modular response claim carries an escape disjunct discharged by a global monotonicity invariant.
