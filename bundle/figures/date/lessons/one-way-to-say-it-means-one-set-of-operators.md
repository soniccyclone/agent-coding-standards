# One way to say it means one set of operators

**Lesson:** Date supplies an accounting argument for representational uniformity that is sharper than any appeal to elegance. If a formalism admits two distinct ways of expressing the same information, then it needs two sets of operators over that information, and the count scales: several representations demand several operator families, each of which must be specified, implemented, documented, taught, remembered, and correctly composed with the others. The crucial observation is that this multiplication buys nothing. There is no question answerable under many representations that is unanswerable under one. Extra representations add surface, not reach, and surface is exactly what costs.

He runs the argument on ordering. Suppose positions were meaningful, so that a collection had a first and a next. Immediately a family of positional operators becomes necessary: read the nth item, insert here, move this from here to there. All of it is machinery whose only purpose is to service a property that carries no information about the world being modeled, and all of it creates new ways to be wrong, including the classic hazard of code that walks off the end of one field into the adjacent one. Positional access also fails his interpretability test, since the sentence a row asserts does not have a slot for where the row sits. Where ordering genuinely is needed, at a display boundary or in a host language that only knows about arrays, he pushes the conversion out to that boundary and keeps it out of the model, so the cost is paid once at the edge rather than by everything inside.

The rule generalizes into a checklist that Date applies to whole categories of proposed features: anything that is a second way to express what the existing constructs already express should be rejected, not because it is inelegant but because it doubles an operator surface for no gain. Composite or compound fields are turned down on exactly this basis, since the existing type facility already supplies whatever grouping is wanted. Facilities that let a program bypass type checking to compare things whose types differ are turned down because they rest on the confusion between a type and its representation and would need their own semantics to explain. He is equally strict at the other end of the range, insisting that if a formalism admits collections it must admit empty ones, and that degenerate cases such as a relation with no attributes or a key with no components are meaningful and useful; special-casing them away is another kind of non-uniformity, and one that silently corrupts the algebra's identities.

A programmer working this way audits an API by counting the distinct ways it lets a caller say the same thing, and treats each redundancy as a future maintenance tax with a known interest rate. Faced with a request for a new construct, the first question is whether it is shorthand expressible in what already exists, in which case it can be added freely as sugar, or a genuinely new way of representing information, in which case the full operator-set cost must be paid and justified.

**Source:** [An Introduction to Database Systems](../works/an-introduction-to-database-systems.md) — the properties-of-relations discussion in the relations chapter, where the absence of left-to-right and top-to-bottom ordering is defended by the argument that additional representations require additional operator sets and add complexity without power. Also [Databases, Types, and the Relational Model: The Third Manifesto](../works/databases-types-and-the-relational-model-the-third-manifesto.md), whose proscriptions chapter refuses positional attributes, positional rows, composite attributes, and type-check overrides on these grounds, and insists that empty sets and degenerate keys be respected rather than excluded.
