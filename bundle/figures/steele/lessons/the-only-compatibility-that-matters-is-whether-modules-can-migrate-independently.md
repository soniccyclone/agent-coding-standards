# The only compatibility worth designing for is whether independently owned modules can adopt a feature one at a time

**Lesson:** This specification pauses in the middle of its type-system chapter to distinguish three notions of backward compatibility, and the sequence is the whole argument. The weakest notion asks only whether every old program still means what it used to; the specification dismisses it as an academic property, because no real program consists solely of code its author controls — even the smallest one leans on collection and utility types shipped by the platform. The middle notion asks whether old programs keep working against the new platform, which is achievable by never touching what already exists and only adding beside it. That, too, gets rejected, and the reason is organizational rather than technical: a library vendor who adopts the new facility forces every consumer to adopt it in the same release, a consumer cannot adopt it until every supplier has, and two mutually dependent modules must move together or not at all. The strongest notion, the one the design actually targets, is that a module can be converted to use the new facility without forcing any module on either side of it to change at the same time.

Once that is the goal, the consequences follow with unpleasant inevitability, and the specification states them rather than hiding them. The new type information cannot be fully present at run time, because code compiled before the feature existed has to keep interoperating with code compiled after it; so the type discipline is enforced where both sides can be checked and erased where they cannot, a category of types is defined precisely by whether it survives to run time, and a deliberately unsound legacy form is admitted as a bridge. The document says outright that the new form's rules are unsound on purpose, scopes exactly which member accesses through the bridge produce warnings and which do not, and separates the two directions of the problem — old code calling new libraries, and new code calling old libraries — as distinct warning categories with distinct justifications. The residual risk is even given a name so that the specification can point at it consistently wherever it resurfaces.

Why this holds is a fact about ownership, not about types. A dependency graph spanning multiple organizations has no synchronized release; every edge in it is a place where two parties upgrade on different calendars. A soundness guarantee that requires simultaneous recompilation of the whole graph is not a guarantee anybody can cash, so trading part of it for the ability to convert one node at a time is not a failure of nerve but a correct reading of where the real constraint lives. What makes the trade honest is that it is bounded and visible: the unsound region is named, the checks that survive are stated, and the warnings tell a programmer precisely which of their assumptions the compiler could not verify.

A programmer who has internalized this evaluates every schema change, wire-format revision, API version, and language feature by asking who has to deploy simultaneously. If the answer is "everyone," the design is not finished no matter how clean it is, and the fix is usually to accept a marked, temporary hole in the guarantee at the seam between old and new — with the hole documented, diagnosable, and confined — rather than to demand a flag day. The corollary is just as important: a compromise taken for migration must be recognizable as one, so that it can be argued about, warned about, and eventually withdrawn, instead of quietly hardening into the permanent semantics of the language.

**Source:** [The Java Language Specification](../works/the-java-language-specification.md) — the discussion in the types chapter surrounding reifiable types and the legacy unparameterized form, where the three grades of compatibility are laid out and the resulting limits on run-time type information, the intentionally unsound bridge type, and the two directions of unchecked warning are each derived from the migration requirement.
