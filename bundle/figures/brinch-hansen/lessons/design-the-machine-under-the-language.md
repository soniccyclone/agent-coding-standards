# Design the machine you wish you had been given, then hold the layer above it to explaining itself without ever mentioning it

**Lesson:** Real hardware is never the machine your abstractions want. It interrupts, it protects storage in an inconvenient granularity, it has a particular number of processors, and it makes you care about registers and addresses. There are two ways to respond. The common one is to let those facts appear in the language and in the programs, which is why systems code has historically been written with an escape hatch to the metal. The better one is to spend deliberate effort building the smallest possible layer whose job is to *be* the machine you wanted, understood as something the hardware now includes rather than as one more program that runs on it, and then to define your language against that machine and never against the real one. This is not the same as a library of conveniences. The layer is chosen so that the concepts above it are complete: not merely that interrupts are handled somewhere, but that the word "interrupt" has no referent in the language at all.

The criterion for whether the layer succeeded is worth stating precisely, because it is easy to get almost right and almost right is worthless. A program's behavior must be explainable entirely in terms of the concepts of the language it is written in, with no appeal to how the translator works or what the underlying machine does. Any construct that can force a programmer to reason below that line has broken the whole arrangement, since the reduction in complexity that the abstraction was purchased for evaporates the moment anyone has to look through it. A language that permits arbitrary address manipulation cannot meet this test even if most programs never abuse it, because the reasoning required to debug the exceptional program is reasoning about the machine.

The engineering payoff is concrete and runs opposite to the usual expectation that abstraction costs performance. Targeting a machine designed for your language makes code generation simple; simple code generation and static resource knowledge make the resulting programs fast; and the same design gets portability nearly for free, since moving the system means reimplementing a small interpreter rather than a compiler. A programmer who thinks this way treats the boundary between language and machine as something to design rather than accept, and treats every remaining leak across it as a bug in the layer rather than a fact about computers.
