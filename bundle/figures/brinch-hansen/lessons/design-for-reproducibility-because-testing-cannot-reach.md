# Design concurrent code for reproducible behavior, because the errors that matter are the ones testing can never reach

**Lesson:** Sequential programming lets you get away with an empirical attitude: run it, look at the output, fix what's wrong. Concurrency destroys the ground that attitude stands on, and the arithmetic of why is brutally simple. A single unsynchronized access can resolve several ways; a loop over ten thousand records multiplies those ways into a count with ten thousand digits; and which one you observe depends on unrelated load and on scheduling decisions you do not control. You will essentially never see the same behavior twice, which means no amount of running the program tells you anything about the runs you did not perform. The only place the defect can be found is in the text, and if the text is thousands of lines with no structural clue about where to look, it may as well not be findable at all.

That argument reorders the whole design of a concurrent system around a single objective: make the observable behavior reproducible in spite of programmer error. Reproducibility here is not determinism of scheduling, which nobody can promise, but the guarantee that timing cannot change the result — that whatever the interleaving, the answer is the same one. Achieving it means arranging the program so that the dangerous cases are excluded structurally rather than avoided by care. Parts that share nothing writable are provably independent and can be checked as such. Parts that must share are forced through operations that cannot overlap. What remains is a small, explicit set of places where timing matters at all, and that set is small enough to reason about.

The corollary is a preference about *when* errors get caught that goes beyond convenience. A check performed before the system runs and a check performed while it runs are not two grades of the same good: the first keeps the failure from happening, the second only tells you afterward what the failure was. Brinch Hansen made the distinction with an aviation comparison, and for any system whose failure has consequences outside itself it is decisive, justifying real sacrifices in language power to move as much checking as possible to the earlier moment. A programmer who has internalized this treats "we'll find it in testing" as an admission that a class of defect has been left in the design, and treats a concurrency bug that reproduces reliably as a lucky accident rather than the normal case.
