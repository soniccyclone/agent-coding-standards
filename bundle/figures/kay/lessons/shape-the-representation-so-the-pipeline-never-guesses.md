# Treat a processing chain as concurrent stages joined by queues, then reshape the data so decision points do not stall it

**Lesson:** A path from source text to visible result is usually described as a sequence of phases, each finishing before the next begins, and that description is a habit rather than a requirement. If each phase is instead a stage that consumes from one buffer and produces into another, they can all run at once, throttled only by how far ahead each is allowed to get. Two things become visible once the chain is drawn this way. The buffer depths are a tuning knob, keeping any stage from racing so far ahead that its work is wasted. And each buffer is a legitimate place to stop and keep what is in it — the same chain yields stored source, stored intermediate structure, and stored output form depending only on where you tap it. Which of those you persist is then a design decision made on the merits, such as keeping the parsed structure and discarding the text because the text can be regenerated, rather than a consequence of which phase happened to have a file format.

The interesting failure of such a chain is not throughput but decision points. When the flow reaches a branch whose outcome only the last stage can determine, every earlier stage has nothing to do and the pipeline collapses to the speed of a single sequential machine — and since branches are frequent, this is not a corner case. There are two ways out and they are not equally good. The costly way is to guess and build machinery to undo the consequences when the guess was wrong, which is a large amount of logic that exists solely to repair itself. The cheaper way is to change the shape of the representation so that no guess is needed: if the two continuations are laid out so that both are reachable from the branch, the early stages can prepare a little of each, and the resolution costs only a switch of pointer. The buffered work in the abandoned direction is wasted, but a small fixed amount of waste with no recovery machinery beats an unbounded amount with it.

The generalizable move is to stop treating the layout of the intermediate form as an implementation detail downstream of the design, and start treating it as the variable you tune to keep the stages busy. Where a linear representation forces a stall, a representation that mirrors the structure of the control flow removes it. That is the same reasoning that makes the ordinary case of a call easier than a branch — a call is a transfer whose destination is already known, so preparation can begin immediately — and it points at a general test: at each point where a stage must wait, ask whether the thing it is waiting for could have been made knowable earlier by arranging the data differently.

**Source:** [The Reactive Engine](../works/the-reactive-engine.md) — the section on deferment, which redraws the path from keyboard to display as stages communicating through queues that may all run concurrently with buffer depths as a tuning parameter, notes that any of those queues may be diverted into storage and gives the case of a system that discards its source text because it can be recovered from the retained structure, then identifies branching as the condition under which the whole arrangement degrades to sequential speed and proposes structuring the program text to mirror its control flow so both continuations can be prepared and the transfer costs only a pointer switch, contrasting this with an earlier machine that also worked down both paths but required extensive logic to undo the wrong one.
