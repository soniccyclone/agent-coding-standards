# Replace changing a component's state with asking it to achieve something, and measure a construct by the intent it carries

**Lesson:** Hiding a component's fields behind procedures is widely taken to be the point of encapsulation, and it is nearly the whole of what most systems built in that style actually do. It accomplishes very little. If the operations available on a component are still fetch-this-field and store-into-that-field, then the caller is still reasoning about the component's internal state, still sequencing its own changes to that state, and still responsible for maintaining whatever invariants relate the fields — the only thing that changed is that each of those steps now costs a procedure call. The stronger discipline is to eliminate state-shaped operations from the vocabulary entirely, so that what a caller can express is an outcome it wants and the component decides what has to change. Where the interface offers only outcomes, the caller cannot be wrong about the internals, because it was never told about them.

The reason to prefer this is measurable in the length of programs, and the mechanism is worth stating plainly. A storage operation carries almost no intent: it says what one location should now contain, and nothing about why, so achieving anything interesting requires many of them in a particular order that only the author understands. A request for an outcome carries the intent, and carries with it whatever accumulated behavior the receiving component has, including everything it inherits. So the amount of purpose expressed per line differs by a large factor, and the difference compounds because sequences of low-intent operations are what force callers to know ordering constraints, which is what makes them fragile when the component changes. Judge a construct by how much of what you meant it conveys, not by how directly it maps onto machine action.

There is a corresponding rule about when a request may be interpreted. If storing into something is treated as an operator applied to an already-resolved location, then the component never sees the whole request and cannot act on the combination — the classic case being a structure with a default value, where resolving the destination before the value is known forces a change that the component would not have made had it seen both together. Deliver the entire request, destination and value and operation, to the component and let it decide, rather than committing to any part before it has looked. The general principle is that no part of a request should be evaluated to a commitment before the party responsible for satisfying it has had a chance to see all of it. The people this ultimately serves are not machines: programmers do not think by enumerating state transitions, and the less a system obliges them to, the better they will do.
