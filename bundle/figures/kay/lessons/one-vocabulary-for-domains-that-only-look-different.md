# Look for the shared process beneath surface-different domains, then split the score from the performer

**Lesson:** Domains that present through different senses look like different problems and get built as separate subsystems with unrelated vocabularies. Often they are the same problem wearing different clothes: coordinated control of change over time, with parallel strands that must stay synchronized, plus a choice of qualitative "voice" applied to each strand. Recognizing that identity is a design act with two large payoffs. The system shrinks, because one set of concepts serves several apparently unrelated areas instead of one set per area. More importantly, a person who learns the vocabulary in one domain arrives in the next already fluent, and can carry a technique across a boundary that would otherwise have been opaque — and the analogies between the domains stop being poetic and become operational, since the same expression really does drive both.

Finding that common structure requires resisting the pull of surface features, which are what practitioners of each domain naturally describe to you. The productive question is not what these activities look like but what they *do*: which quantities change, on what schedule, under whose control, and what has to be kept in step with what. Where the answers coincide, one vocabulary is warranted; where they genuinely diverge, forcing unity is worse than leaving them apart. The test is whether a nontrivial idea expressed in one domain remains meaningful when read in the other.

The factoring that makes such a unification pay is separating the description of a process from whatever realizes it. A specification of what happens over time should be an independent object that can drive any number of different performers, and a performer should be able to accept any number of different specifications. Fuse them and every combination becomes a separate artifact you must build and maintain; keep them apart and the combinations come free, along with the ability to capture a performance as a description, edit that description, and replay it through something else entirely. This is the same distinction as data versus the code that consumes it, and it is worth making explicitly at every place where a system encodes a procedure.

**Source:** [Personal Dynamic Media](../works/personal-dynamic-media.md) — the treatment of animation, music and programming as different sensory views of dynamic processes sharing one framework, the argued analogy between visual and musical images including timbre as the "font" of musical expression, and the explicit separation of control from player in the animation and music systems where one sequence drives many drawings and one score directs many instrumentalists.
