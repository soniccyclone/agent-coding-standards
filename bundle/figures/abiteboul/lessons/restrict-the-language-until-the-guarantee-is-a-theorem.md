# Restrict the language until the guarantee you need is a theorem about the language

**Lesson:** There are two places to obtain a property like termination, or safe parallel execution, or the ability to optimize automatically. You can prove it about each program you write, over and over, or you can arrange the language so that every program written in it has the property and no proof per program is required. This work is a sustained demonstration of the second route, with the price tag attached each time. Forbid retraction, so that a computation may only add facts and never remove them, and termination in time polynomial in the data follows from nothing more than counting how many facts could possibly exist. Allow retraction and that argument collapses; the computation may run forever, and all you keep is a space bound. The bound was never a property of any particular program. It was a property of the shape of the state transition.

The same trade runs through static analysis, and it decides what tooling can ever exist. For the smallest interesting query class, asking whether one program's output is always contained in another's is decidable, and each program has a unique smallest equivalent form, so genuine optimality is a well-posed goal. Allow negation and that question becomes undecidable, which means no complete optimizer for the larger language can exist, no matter how clever its author. The ceiling on your compiler was fixed the moment the language admitted the construct. The distributed material makes the same point at the level of system design. A model built on functions with no side effects, applied to immutable records that carry no references to each other, gets partitioning, retry after failure, and parallel speedup as consequences of its shape rather than as features to be engineered. What it gives up is stated plainly: computations that need to correlate records held on different machines, and workloads made of many small coordinated state changes, are off-model and stay off-model.

The discipline this suggests is to name the guarantee you actually need before choosing constructs, then remove whatever makes that guarantee unprovable in general. Grow-only structures instead of mutable ones when you need a termination or convergence argument. A restricted query or rule form when you need automatic rewriting. Pure functions over independent records when you need horizontal scale. Each restriction should be recorded together with what it forecloses, because the honest version of this move includes the list of things you have made impossible, and a model whose exclusions are undocumented will be quietly worked around by the first engineer who hits one.

**Source:** [Foundations of Databases](../works/foundations-of-databases.md) — the framing example that opens the chapter on recursion with negation, which contrasts grow-only iteration with iteration that can delete and derives the polynomial time and space bounds from the shape of each; and the chapter on static analysis and optimization, whose survey of what is decidable for conjunctive queries and undecidable once difference is admitted is drawn on for the tooling-ceiling argument. The distributed side comes from the opening of the chapter on large-scale distributed computing in [Web Data Management](../works/web-data-management.md), which lists the properties that make its programming model parallelizable and states which classes of work it deliberately does not serve.
