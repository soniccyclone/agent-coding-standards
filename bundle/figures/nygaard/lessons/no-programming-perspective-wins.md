# Treat Programming Styles As Lenses To Switch Between, Not Camps To Join

**Lesson:** Nygaard sorts programming into three ways of construing what a computation *is*: a system of components moving through states, a chain of value-producing applications, or a state space progressively narrowed by stated restrictions with the answers deduced rather than sequenced. He then declines to rank them. Each construal makes a different class of problem obvious and a different class awkward, so none of them can absorb the others, and he explicitly rejects borrowing Kuhn's vocabulary of paradigms — that word implies mutual exclusion and a winner, which is exactly the wrong prediction about these three.

The argument is about human cognition more than about semantics. A construal is valuable precisely because it fixes what you attend to first; that same fixation is what makes it a bad fit elsewhere. The remedy is not to find the universal construal but to become fluent enough in several that you can re-view the same problem through each and notice which one collapses the difficulty. Nygaard treats that capacity for deliberate re-viewing as basic professional equipment rather than as an advanced skill, and he extends the demand to the notations themselves: a language or description formalism intended for serious use should carry more than one of these modes, because the teams using it will need to describe both the world and the deduction.

The practical difference shows up in how disputes get resolved. Someone who believes this does not ask which style is superior; they ask which style makes this particular problem's essential structure cheap to state, then check the answer against a second style before committing. They are suspicious of a codebase written entirely in one register, since that usually means the register was inherited rather than selected. And they will accept a larger set of constructs in a language when those constructs buy genuinely different modes of description, while still refusing constructs that are only variations within a mode already covered.

**Source:** [Program Development as a Social Activity](../works/program-development-as-a-social-activity.md) — the section enumerating the major perspectives on programming and the following argument that a future description-and-programming language must support all of them, together with the earlier definition of multiperspective reflection as an aspect of the science.
