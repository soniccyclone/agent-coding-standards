# Ask what an apparently non-denotable construct stands for; the answer is the surrounding situation it silently refers to

**Lesson:** Some constructs look constitutionally unable to be values. A destination in a program is one of them: it is not a number or a function, it is a place, and places seem to belong to the text rather than to the world the text talks about. Landin treats the apparent impossibility as a question worth answering rather than a fact to accept, and the answer follows a pattern that recurs everywhere. A destination is not meaningless — it is meaningful relative to something the notation never mentions, namely the whole pending situation that the machine would otherwise have returned to. Pair a piece of code with a snapshot of that pending situation and you have an object. It can be named, handed to a function, returned from one, stored, passed through several layers of code that have no idea what it is, and finally invoked, at which point the pending situation it carries replaces the one currently in force.

The shape of the move is worth extracting from its subject. Whenever a construct resists being turned into a value, look for the ambient thing it depends on, because that dependence is what is blocking it. Make the dependence into a component of the object and the resistance disappears. What you get back is not merely a tidier account but a genuine increase in what can be expressed, because everything the language already knew how to do with values now applies to a thing that previously only had a fixed syntactic position. Landin makes the point about the vehicle rather than the notation: he offers a way of writing his operator, then says plainly that a reader could accept the concept and reject his spelling of it, and that this separability is the merit of designing at the level of structure rather than surface.

He is equally careful about the limits, and the care is part of the lesson. Giving a destination a denotation works only in a qualified sense — the object is defined by reference to the machine's suspended state, so talk about "the value of a label" is licensed only so far and no further, and he says so explicitly rather than overselling. There is a matching admission on the implementation side. Once such an object can outlive the region it was created in, storage cannot be a simple stack any more; you need a second, non-stack source of memory and a policy for choosing between them, which is exactly the cost that first-class functions already imposed. He notes that a system which was never stack-based in the first place pays nothing extra, and declines to pretend the allocation policy is a solved part of the story.

The habit that follows is to hunt for the hidden referent behind anything you were told cannot be abstracted over. A transaction, a request's ambient deadline, an open resource's cleanup path, the current position in a traversal, the rest of a pipeline — each of these is usually a "place" in someone's control flow, and each becomes a value the moment you identify and bundle the surrounding state it implicitly names. Two consequences come along with the gain and should be budgeted for at the same time: the reasoning laws you relied on may not survive the new object, and its lifetime will exceed the scope that created it, which is a memory-management decision and not just a semantic one.

**Source:** [A Generalization of Jumps and Labels](../works/generalization-of-jumps-and-labels.md) — the introduction of an intermediate result that pairs a function with a saved machine state as the thing a destination denotes, the transition rules describing how such an object is produced and what happens when one is applied, the insistence that the concept is separable from any chosen notation for it, and the implementation note on why non-stack storage becomes necessary.
