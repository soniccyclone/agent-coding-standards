# Specify the direction in which the mapping is a function: define the object, generate its representations, and let the spread of representations define what carries no information

**Lesson:** The instinctive way to relate a notation to a meaning is to start from the notation, because that is what you receive: text arrives, you take it apart, you decide what it means. Landin runs the relation the other way. He first defines a class of abstract objects standing for programs and their parts, then defines a function from an object to the whole collection of texts that would represent it. Recognizing text is not what he specifies at all; the specification he writes is a generator, and reading is left as the inverse problem. The reason to prefer this direction is that it is the direction in which the relation is single-valued. Going from text to object is a function; going from object to text is not, and that is exactly the interesting fact — so make it the thing you write down rather than the thing you quietly discard.

Once representation is a collection rather than a string, the freedom in a notation becomes an explicit, inspectable object instead of a folk belief. The set of texts for a given abstract program contains every variant that differs only in ways that cannot matter, and Landin enumerates precisely what those ways are for the language he is treating: optional whitespace, commentary, alternative punctuation for parameters, a type keyword that may be left out in certain places. Nothing else is permitted to vary, and the claim is checkable because the generator produces the set. He even builds the tolerance compositionally, defining text-class operations for concatenation and alternation so that permitted whitespace threads through the whole grammar by construction rather than by remembering to allow for it at each point. Anyone who has argued about whether two formattings of the same data are "the same" has been arguing for lack of this object.

The generative direction also buys the thing a parser cannot: an account of what a well-formed structure is, independent of anyone's ability to recognize it. Landin needs this twice over, because he defines two functions on the same abstract objects — one producing texts and one producing model expressions — so the abstract class is what makes the two halves commensurable. Change how programs are written and only the first function moves; change what they mean and only the second does. He is candid that the abstract class is defined by an informal, very long structural description with some points of rigour deliberately left begged, and that some questions about it should be settled by more experience with the technique rather than decided in advance.

A programmer who has absorbed this stops writing parsers as the definition of a format. Define the data, define what a valid rendering of it looks like by producing renderings, and let the reader be a separate, testable inverse whose correctness claim is that it recovers the object any generated text came from. The immediate wins are practical: round-trip testing becomes obvious rather than clever, the set of things that are allowed to differ between two renderings becomes something you wrote down instead of something you discover during a diff review, and canonical form becomes a choice from a known set rather than an accident of whatever the writer emitted.

**Source:** [A Correspondence Between ALGOL 60 and Church's Lambda-Notation: Part II](../works/correspondence-algol-60-church-lambda-notation-part-ii.md) — the setup of abstract program objects with a text-producing function and a meaning-producing function defined over them, the enumeration of exactly which textual differences make the text-to-object relation many-one, and the composable text-class operations that carry permitted whitespace and alternation through the whole definition.
