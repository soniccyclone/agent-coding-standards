# Hand the failure path in as an argument, and error handling stops being the part that escapes structure

**Lesson:** Landin reports from experience, not from theory, that the place where programming without imperative sequencing hurts most is the handling of success and failure — detecting that something has gone wrong and doing whatever must be done about it. That rings true for a reason that has nothing to do with his era. Everywhere else the shape of the code follows the shape of the problem, but the failure path is defined by abandoning that shape, so it is the one part of a program whose structure is negative: a hole punched through the nesting, going somewhere the nesting cannot express. His response is to make the abandonment itself an argument. A routine that might fail takes, as an ordinary parameter, the thing to do if it does; deciding what happens on failure becomes the caller's business, supplied at the call rather than wired into the callee.

The crucial detail is that the callee cannot tell what it has been handed. Whether the supplied behavior returns to its caller in the usual way or unwinds past several frames to a point chosen by whoever supplied it, the code that calls it is written identically. Landin points out the consequence in a substantial numerical program he rewrote: the failure behaviors are parameters of the entire program, so his converted version contains not one occurrence of the escaping operator anywhere, yet it is essential to correctness that the arguments passed in were escaping ones and not plain functions. The choice of control discipline moved entirely to the outermost caller, and every intermediate layer became indifferent to it. That is a strong form of separation — the policy is decided in one place, and the mechanism is invisible everywhere else.

Two further gains fall out. First, the dependency becomes visible in the program's structure instead of in its history. In an imperative version, whether some variable can influence the diagnostic action is answered by tracing what has been executed and what is still reachable; when failure actions are parameters, it is answered by looking at what is in scope where. Landin also notes the discipline this forces in a setting with no external variables to scribble on: everything a routine accomplishes must be in its result, even when what it accomplished was discrediting itself, so failure has to be given a representation rather than a side channel. Second, once failure behavior is a value, combining fallible things becomes ordinary composition. He demonstrates with text recognizers that take a failure action and a source and either produce a result with what remains unconsumed or hand the source to the failure action, then defines operators that build a recognizer out of two recognizers for sequencing and for choice — the branching structure of a grammar becomes application of functions to functions, with the backtracking that alternation needs carried entirely in the failure argument.

A programmer working this way stops treating error propagation as a language feature to be used and starts treating it as a parameter to be designed. Ask what a component should do when it cannot proceed, and then refuse to answer on the component's behalf: take the answer as input. The compensating cost is real and should be named — passing behavior in means the caller now owns a decision it did not previously have to think about, and every combinator you write over fallible things has to say what it does with the failure argument, including the awkward cases where it must be rebuilt rather than forwarded. Landin's own combinators show exactly that seam, where the failure action given to the second stage has to be reconstructed rather than simply passed along.

**Source:** [A Generalization of Jumps and Labels](../works/generalization-of-jumps-and-labels.md) — the section on use, reporting that success/failure situations are where non-imperative programming was weakest, that failure actions became parameters of the whole converted numerical program with no explicit use of the operator inside it, that a routine's entire outcome including self-discrediting must live in its result, and the text-recognizer definitions where sequencing and alternation are built as operators over failure-taking functions.
