# Control flow shows what can happen; a variable hides it, so do not encode the one into the other

**Lesson:** There is a move that looks like good practice and usually is not: replacing a piece of control structure with a variable. Leaving a loop early becomes setting a flag and testing it in the loop condition. A branch whose two arms share a tail becomes an assignment in each arm and a second branch further down. Duplicated work becomes a temporary holding the shared value. Each of these can be justified — fewer exits, less repeated code, less recomputation — and each of them trades something visible for something invisible.

The reason it is a bad trade by default is an asymmetry in what the two forms tell a reader. Control structure describes exactly what can happen: the shape on the page is the set of possible paths, and there is nothing else to check. A variable describes nothing of the kind. To know what values it can hold at a given point you must establish where it may have been assigned, and in most languages nothing marks the regions where it is safe from change. So you are obliged to verify that the generality a variable introduces is never actually used — that no other code writes it, that no aliasing reaches it — and that verification is work with no upper bound, done afresh every time anyone reads the code. Reasoning about data is harder than reasoning about flow, and the popular direction of that trade runs the wrong way.

This is not a defence of unconstrained jumping, which makes the paths unenumerable and is worse than either option. It is a narrower and more useful claim: between a disciplined early exit and a flag that simulates one, the exit is easier to reason about, and the widespread instinct to prefer the flag on stylistic grounds is mistaken. The same holds for a temporary introduced only to avoid recomputing something: it is a hand-made version of a transformation the compiler should be doing, and paying for it in a mutable name is a poor bargain unless you have evidence the compiler is not doing it.

The constructive form of the advice: when you find yourself reaching for a variable to express something about control, treat that as a signal to restructure the algorithm instead, because the need usually indicates that the shape is wrong rather than that the shape needs a workaround. And keep the exceptions honest — some problems genuinely become much simpler with an extra piece of data, a sentinel past the end of a collection being the standard case, and a second link in a structure being the only way to reach information in a direction the structure otherwise forbids. Those are real, and the way to tell them from the others is that they simplify the algorithm rather than encode a piece of it.

**Source:** [Software Development: A Rigorous Approach](../works/software-development-a-rigorous-approach.md) — chapter 22's "Variables and Flow" section: the paired programs in which a conditional with a shared tail is rewritten using a new switch variable, and in which a sign case is handled by a multiplier rather than by a branch; the note that many practitioners of structured coding will set and test a switch rather than exit from the middle of a loop; the conclusion drawn from applying formal methods to these examples, that it is in general more difficult to reason about data than about flow and that this runs counter to some conventional structured-coding dogma, because in most programming languages the places where variables are safe from change are not clearly marked so much of the generality introduced must be checked never to be used, whereas flow of control tends to show only what can happen; the accompanying qualification that this is not an argument for undisciplined jumps, which make proofs unmanageable, but that a simple loop exit is easier to reason about than the corresponding switch, and that the best solution is a restructuring of the algorithm; the treatment of the duplicate-array-reference example as work an optimizing compiler should be doing; and the closing enumeration of three uses of extra variables together with the acknowledgement that some problems are significantly simplified by slight changes to the data, citing sentinel values placed beyond the end of a vector and parent pointers in tree nodes.
