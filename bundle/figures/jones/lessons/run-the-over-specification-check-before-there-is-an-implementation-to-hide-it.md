# Run the over-specification check before there is an implementation to hide it, because the first builder never feels the cost and the second cannot avoid it

**Lesson:** A description that says more than the problem requires has a peculiar economics: whoever builds against it first almost never notices. They read the description, build something shaped like it, and everything matches — of course it does, the excess in the description is the shape of what they built. The defect is real and it is already paid for, but the invoice is held until someone arrives with a differently-shaped implementation that is perfectly adequate for the actual requirement and yet cannot be squared with the description. At that moment the cost lands entirely on the second party, who did nothing wrong, and who will be told their design is incorrect when what is incorrect is the description. Any defect whose cost is deferred onto a later, different party is one you should expect an organization to systematically under-detect, because nobody in the room when it is introduced has an incentive to look for it.

The reason this particular defect is worth singling out is that the check for it does not require an implementation at all. It is a question you can ask of the description in isolation, against its own vocabulary: is every distinction the description draws one that its own operations can detect? If two states it treats as different cannot be told apart by any sequence of the operations on offer, the difference is not part of the problem, it is residue from how you happened to write it down. That makes this one of the rare correctness checks available *before* the thing being checked has had any consequences — which is precisely the window in which fixing it is cheap, and precisely the window in which nothing yet forces you to look.

If you miss the window, the repairs get progressively worse and it is worth knowing the ladder in advance. Cheapest is to rewrite the description while nothing depends on it. Failing that, you can relate the description to the implementation by a correspondence that is many-to-many rather than a plain reading-out — which works, but every argument that used to be a simple substitution becomes an argument about a relation, and they compound badly. Or you insert a third, more abstract description between the two and go through it in two hops. Or you deliberately add machinery to the implementation whose only purpose is to reconstruct the excess the description demanded, so a straightforward correspondence exists again, and then argue at the end that the added machinery never affected anything and can be dropped. Each of these is a real technique and each of them is work you would not be doing had the description been checked when it was three days old.

The general form: prefer defect checks that can be run against an artifact alone over checks that require its consumers to exist, and be actively suspicious when the first consumer reports no friction — agreement between a description and the one thing built from it is very weak evidence, since the thing was built by reading the description.

**Source:** [Software Development: A Rigorous Approach](../works/software-development-a-rigorous-approach.md) — chapter 15's "Implementation Bias" and "Difficult Refinement Steps" sections: the characterization of sufficient abstractness as the definability of an equality predicate purely in terms of the external operators, worked through the stack variant that retains removed elements behind a counter and whose surplus is undetectable by any operator sequence; the statement that if the implementation to be justified happens to fit the bias no immediate harm results but a delayed penalty may occur when another implementation is undertaken; the noted advantage that the bias test can be applied independently of and prior to the implementation; and the three listed remedies for a biased description already committed to — a relation rather than a retrieve function between abstraction and representation, an intermediate more abstract description bridging two concrete ones, and auxiliary variables added to the implementation to rebuild the starting definition's mechanism and then shown irrelevant and dropped.
