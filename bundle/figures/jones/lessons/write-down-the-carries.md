# Write down the intermediate claims, because that is what turns one big check into several small independent ones

**Lesson:** Consider checking a column addition. If only the answer is written down, verifying it means redoing the whole computation, because any digit can depend on any earlier one. If the carries are written down too, the check falls apart into as many separate tasks as there are columns, each one small and each one checkable without looking at the others. Nothing about the arithmetic changed; the recorded intermediate values changed what checking costs, from one indivisible task to several independent ones. That is the actual function of assertions attached to points inside a program, and it is a different claim from the usual one about comments aiding comprehension. Recording what is true at a boundary is what makes the reasoning either side of that boundary separable, and separability is the only thing that makes review of anything substantial tractable.

The consequences for how you write are concrete. The annotations are not free-form prose; they are claims in the same vocabulary as the specification, which means a reviewer can check each fragment against the claims bracketing it using the rules for whatever construct is there, and nobody has to hold the whole program in mind. A walkthrough over annotated text is a fundamentally different activity from a walkthrough over bare code, because the participants can disagree about one bounded claim instead of arguing about the program. The same texts double as a record of what the author intended, so where the code and the claim disagree you learn which one is wrong rather than merely that something is.

Two calibrations. First, the volume worth writing shrinks with experience, and the irreducible minimum is the entry and exit claims for each separately-developed piece, since those constitute its specification and are what everything else depends on. Beyond that minimum, write for the reader who has to modify this later, which is quite likely to be you after enough months to have forgotten the reasoning entirely; the fact that more detail could be supplied on demand is not an argument for supplying none. Second, the same annotation carries the record of design in progress, not just of finished code — a step recorded as a claim, a not-yet-written component, and another claim is a complete and checkable statement of a decision, and the pieces underneath can be handed to different people with nothing but their bracketing claims. The notation that makes checking decomposable is the same notation that makes the work decomposable.

**Source:** [Systematic Software Development Using VDM](../works/systematic-software-development-using-vdm.md) — the assertions-as-annotations section: Turing's column-addition comparison, cited there, showing that recording the carry digits separates the checking task into four disjoint tasks whereas without them the whole sum must be checked; the argument that annotated programs are far easier to review in walkthroughs than uncommented code and that the assertions are precisely stylized comments checkable against the code by the decomposition rules; the observation that the minimum worth recording is the pre- and post-condition of each procedure and the appeal to write enough for future readers including the author after a long separation; and the annotated-design figure showing the same notation used to record a design step whose subcomponents are still only specified.
