# Treat a stated assumption as a licence you granted, and remember that correct only ever means meets this description

**Lesson:** An assumption recorded about a component's inputs is not a check the component has to perform; it is a grant of freedom. Where the assumption fails, the component owes nothing whatsoever — not a sensible answer, not a diagnostic, not even the courtesy of stopping. That is much stronger than it first reads, and the strength is the point: writing the assumption down converts something that was previously a hidden consequence of whatever algorithm happened to be chosen into an explicit term that two people can negotiate. The user of the component can now object that the restriction is unacceptable, which is the conversation that ought to happen, rather than discovering the restriction later by hitting it. The mirror case is easy to overlook and just as consequential: omitting the assumption is itself a commitment, and a large one, since it promises the component copes with every input of the declared shape. Absence is not silence.

Two practical notes on where such things live. The assumptions worth recording are the ones that relate several inputs to each other, because a restriction on a single input can usually be pushed into that input's own description instead, which makes it someone else's business to maintain. And once you notice that, you should also notice that the choice between expressing a constraint as part of a type and expressing it as a stated assumption is a matter of convenience rather than principle — the total obligation is the same either way, merely rearranged, and the proof you have to construct is the same length. That being so, pick whichever reads better for the reader you have in mind, and decline to argue about it. Constraints often want to move as the description matures, and a discipline that treats their placement as load-bearing makes that movement expensive for no benefit.

All of which rests on a framing worth stating flatly: correctness is not a property a program can possess. The word is always shorthand for meeting some particular stated description, so with no nameable description in view it means nothing at all, and almost every dispute about whether something is correct turns out on inspection to be a dispute about which description was intended. This has a consequence that saves real effort. Sequences of instructions are not the sort of object you can equate directly; establishing that two of them compute the same thing means finding some common ground to map both onto, which is work. Establishing that one of them meets a stated description is comparatively easy. So the description is the only tractable place to compare candidates — and, as a corollary that surprises people, two programs can both meet the same description and still not be interchangeable, which is exactly what you want when the description was deliberately leaving something open.

**Source:** [Systematic Software Development Using VDM](../works/systematic-software-development-using-vdm.md) — the functions-and-operations chapter: the treatment of the pre-condition as an explicit place to record assumptions about arguments that are otherwise hidden consequences of an algorithm, the statement that for arguments failing it nothing can be assumed about the result and the observation that a definition is even permitted to yield no result at all there, the convention that an omitted pre-condition means the implementation must cater for every argument of the required type, the note that the more interesting pre-conditions are those relating different parameters since a restriction on a single domain can be handled by restricting that set, the remark that the choice between showing a constraint by type information or by a post-condition clause is a pragmatic one that leaves the overall proof task unchanged, the insistence that the phrase about something being correct should be read as satisfying a specification and has no meaning without reference to one, and the argument that it is far easier to show a sequence of statements satisfies a specification than to show two sequences compute the same result, with the closing note that two programs could satisfy one specification without being equivalent.
