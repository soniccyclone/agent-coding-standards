# Find the right abstraction by looking at the implementations you would consider and keeping only what they agree on

**Lesson:** "Describe it abstractly" is easy advice and hard practice, because nothing in it tells you how abstract. Too abstract and the description no longer says what you need; too concrete and you have written one implementation and called it a description. There is a mechanical way to find the level, and it runs through the implementations rather than around them. Sketch the two or three realizations you would genuinely consider building. Then look at where they differ. Everything they disagree about is by construction not part of what the thing is, because you were willing to ship any of them. What survives the disagreement is the description.

The example is instructive because the candidates are so unalike. Something that tracks a collection of names might be an array plus a count, where adding is cheap and removing means shuffling; or a sorted sequence, chosen because looking things up dominates and a bisecting search pays for the ordering; or chained cells, chosen because there are many such collections and reserving worst-case room for each is unaffordable. Order, adjacency, capacity, cost profile — all different across the three. What all three answer identically is whether a given name is in the collection. So membership is the description, and every one of those realizations is a legitimate model of it. Notice that the reasoning did not require taste or experience with abstraction. It required listing candidates and taking their intersection.

Two things follow that are worth stating separately. First, the disagreements are not noise to be averaged away; they are the *evidence* that told you what to omit. If two candidates you would seriously build differ on some property, that property does not belong in the description, and you now know this rather than believing it. Second, the resulting description will look inefficient if you read it as code — the operation that is one line abstractly may be a linear scan concretely — and this is not a defect. A description exists to say what the result must be, not how to get it, and a description that would be slow if executed literally is in exactly the same position as a definition of a mathematical function that nobody would compute the way it is written. The test of a description is whether it is easy to reason with and whether every realization you want is permitted by it, never whether it would run well.

The failure this guards against is the common one: writing a description that quietly encodes the first implementation that came to mind, then discovering during construction that the description forbids the implementation you actually need. Deriving the description from several candidates instead of one makes that failure structurally impossible.

**Source:** [Software Development: A Rigorous Approach](../works/software-development-a-rigorous-approach.md) — chapter 8's opening classroom-membership example: the survey of realizations (an array of names with an index and a linear search, an ordered list searched by bisection when lookup dominates, a chained representation when many such collections make worst-case arrays unaffordable), the statement of the general approach that when faced with a choice of implementation possibilities one finds an abstraction of them possessing only the properties needed to specify the required results, and the conclusion that presence or absence is the only fact of importance so an unordered collection is the appropriate description; together with chapter 7's remarks that a constructive description is likely to be inefficient if built the same way, is intended to state what the result should be rather than prescribe how it is computed, and is a specification and not a proposal for implementation strategy, in the same way an obviously impractical recursive definition still serves as a description.
