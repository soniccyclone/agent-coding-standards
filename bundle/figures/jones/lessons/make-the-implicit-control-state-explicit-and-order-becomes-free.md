# Make the control state explicit data and the order of work becomes yours to choose

**Lesson:** A recursive formulation is usually the clearest way to say what a computation produces, and it is frequently a poor way to perform it. The standard response is to translate it into a loop, and the standard framing of that translation — "simulate the recursion with an explicit stack" — undersells what is actually happening and hides the real payoff.

What a recursive evaluation holds implicitly is a set of pending pieces of work, each identified by its arguments, and an order in which they will be undertaken that is dictated entirely by the shape of the definition. Write those pending items down as data — one record per distinct call, carrying exactly the arguments that call would have had — and two things separate that were previously fused. The set of work that must be done is one thing; the order in which it gets done is another. The recursion had bundled them, so the definition's structure silently decided the schedule. Once the work items are values in a structure you can iterate over, the schedule is a free variable, constrained only by the dependencies among the items and no longer by how the definition happened to be written.

That freedom is where the performance is. You can now choose an order that suits the machine rather than the definition — sweeping the input once from left to right, processing every pending item that concerns the current position before moving on, so that data is touched in a predictable pattern and nothing is revisited. You can share: two paths that would each have recursed on the same arguments now find one record and the duplicate work simply does not happen, which is often the whole difference between an unusable formulation and a practical one. And you can exploit independence: items with no dependency between them may be done in any order, or at the same time.

The method is worth stating as a sequence, because doing it in the other order is what makes it hard. First write the recursive definition and convince yourself it is right, since it is the version whose correctness is checkable. Then extend it with extra arguments recording anything the eventual data structure will need to carry — this changes no results, so it needs no new justification, and it is what makes the correspondence to the explicit form visible. Only then make the pending calls into records and choose a schedule. What remains to be argued is narrow and specific: that the chosen order still evaluates everything that must be evaluated. Everything else was settled while the problem was still small.

**Source:** [Software Development: A Rigorous Approach](../works/software-development-a-rigorous-approach.md) — chapter 18's third development step for Earley's recognizer: the observation that simply programming the recursion of the previously justified functions would not be efficient given typical compiler implementations of recursion; the deliberate intermediate step of extending the two mutually recursive functions with extra arguments recording which rule is being used and where its parsing began, explicitly noted as making no change to their results so that their correctness is obvious; the introduction of a structure recording the arguments of all calls, with the statement that because all information about calls is captured, the collection is sufficient to permit changes in the order in which elements are generated, and that changing that order amounts to changing the order of the calls; the resulting decision to let iteration through the recorded elements govern the calls rather than the recursive structure of a function; and the accompanying note that there are constraints on valid orders since every call must still be evaluated, with the argument that a left-to-right sweep is adequate because recognizer information is always generated for an index no smaller than the current one.
