# Fit your model to the subject matter when the operation list is still open, not to the distinctions today's operations can see

**Lesson:** There is a good test for a model that has committed to more than it should: two of its configurations count as excess if no sequence of the available operations can tell them apart. Apply it and it works. But notice what the test is relative to — the operation list — and notice what that dependency does. Trim a model until it is exactly as fine as today's operations can observe, and every operation someone wants to add later becomes a fight, because the distinctions the new operation needs are precisely the ones you removed on purpose and there is now nowhere to put them. The effect is not hypothetical or gradual: strip a queue down to what a set of operations that never reveals the removed element can observe and you are left holding a count; remove the removal operation too and you are left holding a single yes-or-no. Each of those is the correct answer to the question the test asks and a disastrous foundation for anything that has to grow.

So the decision rests on whether the operation list is closed. When it is, fit the model tightly and take the guarantee that comes with it. When it is not — which is the ordinary condition of anything with a future — fit the model to the essence of the subject matter instead, and accept the resulting technical excess as a price paid knowingly. This is not permission to model carelessly; it is an instruction to know which of two objectives you are serving and to be able to say so, because the same structure can be exactly right against one criterion and clearly wrong against the other. Occasionally the argument runs the same way even for a fixed operation list: a description that keeps the values it was given in order to talk about their average and spread is more committal than necessary and much clearer than one that avoids the commitment by relying on subtler properties. Clarity is allowed to win that argument, as long as you notice you are having it.

Two things keep this from becoming an excuse. The test is necessary, not sufficient: an over-committal structure can be made to pass it by adding a condition that admits only one representative of each indistinguishable group, which leaves you with something strictly more complicated that the test now approves of — so among the candidates that pass, still prefer the one needing the least machinery to stay legal. And the escape route matters: development from an over-committal description is possible, by relating it to the implementation with a relation rather than a function and giving up the coverage obligation, at the cost of harder proofs. Knowing the escape exists is what lets you take the extensibility trade on its merits, rather than being pushed into the tight fit because it is the only case the method handles comfortably.

**Source:** [Systematic Software Development Using VDM](../works/systematic-software-development-using-vdm.md) — the implementation-bias-in-models section: the definition of the test as the existence of distinct states indistinguishable by any sequence of the operations, and the worked demonstration of its relativity where replacing the dequeue operation with one that does not reveal the removed value reduces the sufficiently abstract model to a count and discarding that operation reduces it to a single Boolean; the argument, credited there to Michael Jackson, that a specification which is technically over-committal should be used when the full extent of the operation set is unknown, since tailoring the state too closely to a particular collection of operations makes subsequent extension all but impossible and the state must instead be chosen as the essence of the application; the average-and-standard-deviation case where the more committal state is clearer; the observation that an over-committal model can be made to pass the test by adding an invariant selecting one representative per class at the cost of a more complicated description; and the general proof rules allowing development from a biased specification via a relation with no adequacy obligation.
