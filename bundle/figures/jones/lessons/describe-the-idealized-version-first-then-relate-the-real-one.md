# To get something existing under intellectual control, describe the idealized version first and relate the real one back to it

**Lesson:** You are handed a fixed boundary — an existing subsystem you must build against, a format decided before you arrived — and its documentation specifies layouts to the byte while saying nothing whatsoever about meaning, which has to be inferred from field names and worked examples. The instinct is to work from the detail you were given, since it is what you have. The productive order is the reverse: write down a structure carrying only the essential information content, state what the operations mean against that, and only then relate the given concrete detail back to it by an explicit interpretation. The objection is always that there isn't time for this, and the honest answer is that there is no cheaper route — the reason people adopt it is not enthusiasm but the discovery that nothing else gets the boundary under intellectual control at all.

The side effect is arguably the main effect. You cannot write the idealized version without deciding what happens in all the cases the original prose never addressed, so the exercise enumerates the ambiguities as a by-product, and they come out in two clearly separated heaps: questions about what the thing is supposed to do, and questions about how information is represented. Each then becomes either a question for whoever owns the requirement or a decision you have recorded and can be held to. This is why the resulting document is genuinely more precise than the one it replaces even though the original had far more detail in it. Detail and precision are different quantities, and a specification of shapes and names with meanings merely suggested by the names is the more common and more expensive failure of the two.

The same technique has a second use, on systems that are cluttered rather than merely undocumented. Record the clean version first and then the successive approximations that add the awkward real features, and treat the distortion introduced at each stage as information rather than noise. If you are designing the thing, an ugly increment is a prompt to ask whether that complexity is actually necessary. If you are describing something already built and immovable, you have no choice but to absorb it — but recording the simplified stages first is exactly what makes an otherwise opaque system comprehensible, and more than one intermediate stage is sometimes needed to get there. The order is what does the work: essence first, then each layer of reality, each related to the one before, so a reader can stop at whatever depth their question requires.
