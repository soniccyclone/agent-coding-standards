# Admit a range of acceptable outcomes deliberately, because that is how a decision gets deferred to whoever should make it

**Lesson:** A description that pins down exactly one outcome has settled every question it mentions, including the ones you had no business settling. Describing a paged store, you can say that the referenced page must be resident afterwards and that nothing has been lost, and stop — which states exactly what callers depend on and leaves the choice of what to evict to whoever knows the access patterns. Name a replacement policy instead and you have made that choice in the wrong place, at the earliest possible moment, with the least information anyone will ever have about it. So admitting several outcomes is not vagueness or laziness; it is the mechanism by which a decision is postponed, and it only works if you use it on purpose. Turn the habit around and audit for the opposite: every place your description permits exactly one answer should be a place you intended to decide.

The same technique handles failure. Keep the exceptional cases out of the normal description rather than folding them in as extra disjuncts, since the normal case is the thing readers are trying to understand and it drowns quickly. For each abnormal condition, say when it applies and what state results — and say nothing about how it is announced, because that is a property of the language you eventually build in, and needing to choose one in order to write a description is a sign the description has sunk below its proper level. Leave undetermined, too, which of several simultaneously applicable conditions is the one reported; that freedom lets an implementation order its checks however is cheapest. Make them mutually exclusive only where it genuinely matters which one the caller sees, and notice that you now have to decide that question consciously.

Two refinements that are easy to get wrong. First, a loosely described thing without state and a loosely described thing with state do not permit the same freedoms: the former must still be realized by something that answers identically every time it is asked, while the latter may legitimately be realized by something that does not. Which of those you mean is part of what you are writing, not an implementation detail to be sorted out later. Second, keeping a range open costs something concrete — the description may have to hold information whose only purpose is to express how wide the choice is, information that an implementation which has made the choice genuinely no longer needs. That is a legitimate reason for a description to carry more than any correct realization of it, and recognizing the case saves you from mistaking it for a modelling error.
