# Split a program into input, process, and output so the part worth reasoning about is a relation

**Lesson:** Programs that talk to the outside world are harder to reason about than ones that do not, and the usual conclusion — that formal or careful reasoning is therefore only applicable to toy problems — has the diagnosis backwards. The difficulty is not that interaction is intrinsically unanalysable. It is that interaction and computation, mixed together in the same piece of code, deny you the one thing that makes reasoning cheap: the ability to say what a piece of code achieves purely as a relation between what it was given and what it produced.

Split the program in three. One part consumes what arrives. One part transforms. One part emits. The middle part can now be described entirely by a relation over values, with no mention of files, terminals, sockets, or the passage of time — and that description is the thing you can check against intent, argue about, refine, and test in isolation. The outer parts are not thereby exempt from care; they simply become a separate and much smaller problem, and one whose difficulties are of a different kind. Notice how much of a substantial program falls into the middle: nearly all of it, in most cases, once you stop letting the edges leak inward. Notice also that the split is not an artifact of wanting to prove things. It is the same split that makes the core testable without a harness, portable across whatever the edges become, and reusable when the same computation is wanted from a different source.

One modelling point matters when you do describe the edges, and it is easy to get wrong in a way that looks harmless. The tempting shortcut is to treat the outside world as extra pieces of state, so that emitting becomes an ordinary assignment to a component. It type-checks, and it quietly loses the property that distinguishes output from state: output only ever grows. You cannot un-print, and a model that permits an operation to replace what was already emitted is describing a system nobody has. Model what leaves the program as something that accumulates — a sequence that each step appends to and nothing shortens — and the reasoning rules follow the same shape as ordinary composition, with the emissions of the parts concatenating in order. The general instruction: when choosing how to model a boundary, pick the structure that preserves the boundary's irreversibility, not the one that is notationally closest to what you already have.

**Source:** [Software Development: A Rigorous Approach](../works/software-development-a-rigorous-approach.md) — chapter 19's opening observation that, despite the acknowledged importance of input/output statements, most of the book avoids them, and that inspection of the earlier examples discloses this was achieved by splitting problems into operations concerned with input, process, and output, with the core of each program developed from a post-condition for the process part while the input and output operations were left undeveloped; the treatment of input and output files as list-valued arguments and results by analogy with an operation's arguments and results, so that pre- and post-conditions relate the starting state and input file to the output state and output file; and the parenthetical rejection of the alternative of introducing state components holding the files, on the grounds that this approach fails to model the essential growing property of the output file, together with the composition rules in which the outputs of the component operations are concatenated in order.
