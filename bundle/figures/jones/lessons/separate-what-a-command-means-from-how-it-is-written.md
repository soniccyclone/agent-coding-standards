# Separate what a thing means from how it is written, and watch the notation improve the thing

**Lesson:** Descriptions of interfaces — command languages, configuration formats, protocols, APIs — routinely try to do two jobs in one pass: say what the construct means, and say how it must be typed out. Doing both at once makes the description far longer than either job requires and considerably harder to read than both of them separately, and the reason is that surface form carries a lot of detail that meaning does not care about. Optional clauses may be given in either order; the same content may be expressible several ways; punctuation exists to let a reader find the pieces. All of that swells the description of the writing rules and contributes nothing whatever to the description of the content.

Split them and both halves get better. The content description names a set of structured objects rather than a set of texts, and it locates each piece by name instead of by position in a string — which means every rule that existed only to permit an alternative ordering disappears, and every question of the form "where is the third component" becomes a selection instead of a scan. The surface description keeps the writing freedoms, which are genuinely valuable to whoever has to type the thing, and stays entirely separate from any statement about behaviour. The two are linked by a mapping from surface to content, and that mapping is the only place either half needs to know about the other. Notice that this is the same relationship as between a machine-shaped structure and the idealized one it stands for: many surface forms per content, so the mapping runs from concrete to abstract and is a function in that direction only.

The part worth taking away is a side effect rather than the main benefit. When a community got a notation for stating the structure of a language, the languages themselves became markedly more regular — not because the notation forbade irregularity, but because irregularity became visible and tedious to write down, and it stopped being possible to hide an inconsistent construct in a paragraph of prose. Having to state a structure exposes the structure's defects. So the argument for a formal description of what your interface accepts is not only that readers will understand it and tools can be generated from it; it is that you will design a better interface, because you will be able to see the one you have.

**Source:** [Software Development: A Rigorous Approach](../works/software-development-a-rigorous-approach.md) — chapter 14's introduction of abstract syntax: the reproduction of a conventional manual's rules for conditional and loop statements to show how much of the length of a concrete syntax comes from permitting clauses to be written in different orders when statements differing only in that order have no difference in meaning; the observation that information location in strings is awkward whereas a tree-like structure permits direct selection of components; the characterization of an abstract syntax as describing a class of objects each of which abstracts many different strings, with the relationship between the two documented by a retrieve function; the remark that even in informal descriptions of systems, describing simultaneously how a command must be written and its essential content is confusing; and the claim about the effect of a syntax notation on language development — that the first language defined with it set a new norm for the regularity of its constructs and the tightness of its definition, that all subsequent languages adopted some such notation, and that this both improved their structure and made automatic generation of parsers possible.
