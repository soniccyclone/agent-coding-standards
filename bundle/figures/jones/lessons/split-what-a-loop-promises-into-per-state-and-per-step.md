# Split what a loop promises into a claim about each state and a claim about each step, and let mutation decide which carries the weight

**Lesson:** What a loop guarantees has two parts of genuinely different shape, and it pays to write them separately. One is a claim about a single state — which configurations can hold when control reaches the top of the body — and it does the work of bounding where you can be. The other is a claim relating two states some number of iterations apart, and it does the work of establishing progress. The second must be transitive, so that it composes over any number of trips, and it must admit no unbounded descent, which is what makes the loop stop. That the same object which carries the loop's meaning also delivers termination is the reason to build the pair deliberately rather than writing an invariant and bolting on a separate decreasing quantity afterwards.

Which of the two carries the substance is decided by one question: does the loop overwrite the data it is reading? When the main structure is read-only, the single-state claim can hold almost everything — scanning a fixed collection, you can simply say the portion examined so far has been dealt with, and the relational part shrinks to noting that an index went up. When the loop mutates its data, the essential claim cannot be phrased about one state at all: that the current contents are a rearrangement of the original mentions two states by construction, so the ordering property lives in the single-state half and the rearrangement property necessarily lives in the relational half. Programs that overwrite their inputs push nearly all their content into the relational half, sometimes leaving the single-state claim empty. That is a useful diagnostic when you are stuck. If you cannot find an invariant that says anything interesting, stop hunting; the loop is one whose work is inherently a relation between successive states, and looking for a single-state characterization is looking for something that does not exist.

One further choice affects legibility much more than it affects difficulty. The relational claim can be framed as relating each state back to where the loop started, or as relating each state forward to where the loop will end. The backward framing forces the loop's essential operation to appear on both sides of an equation — what has been accumulated so far, plus what remains to do, equals the original — so the interesting operation is written twice and the reader has to reconstruct the point. The forward framing lets you state the loop's purpose once, as the thing that will hold when it finishes, and then read the not-yet-started case as a plain statement of what the whole loop computes. Same loop and much the same obligations, but one version says what the code is for and the other does not. Choose the framing that makes the intent readable; the convention is not worth the loss.
