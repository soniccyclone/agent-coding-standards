# Write down how a representation is to be read, then check every value you promised can be read out of it

**Lesson:** When you replace an idealized structure with one chosen for the machine, the link between the two is best recorded as a mapping that runs from the concrete thing back to the ideal one, and the direction is not arbitrary. A representation earns its keep by carrying extra detail — an ordering, a layout, a duplicated copy — so many concrete values stand for the same ideal value, which makes the concrete-to-ideal direction a function while the reverse is not. That mapping also does something more than bookkeeping: it supplies the interpretation. A list of words is only a dictionary because you said to read it as an unordered collection; read differently it is a book. Nothing in the bytes fixes which, so if the interpretation is not written down it exists only in someone's head, and it is the first thing lost when that person moves on. If you ever find you need the mapping in the other direction, treat that as a diagnosis rather than an inconvenience: several ideal values collapsing onto one concrete value means the ideal description was drawing distinctions nothing could observe, and those values should have been merged before design began.

Having written the interpretation, run one check on it: every value the abstract description admits must have at least one concrete counterpart. This is usually a couple of sentences of constructive argument — here is how to build a representation of an arbitrary value of that shape — and it is worth the two sentences because it catches errors that no amount of care over the operations will. A design can be beyond repair in a way that is invisible while you look at it feature by feature: an elegant nested-lookup structure that identifies a word by the path taken to reach it has no way to record that a shorter word ended part-way along the path, so it cannot represent one entry that is a prefix of another, and no choice of interpretation rescues it. That is a hole in the structure itself, not a bug in an operation, and the coverage check is what surfaces it while it is still cheap to change.

Two very different problems fail the same check, and telling them apart is most of its value. Either the representation genuinely cannot hold some case you need, in which case the representation is wrong and has to be rethought; or the abstract description was too permissive and admits configurations that no sequence of operations could ever produce, in which case nothing is wrong with the design and you tighten the abstract description instead — then re-confirm that it is still satisfiable at all. The wider point is about where to spend checking effort. Representation choices are made early, they determine performance in a way no later cleverness recovers, and a mistake in one invalidates everything built on top; yet writing the interpretation and arguing coverage costs almost nothing. The per-operation obligations that follow cost far more and, in practice, turn up far less. Put the effort where a mistake is expensive to undo, not where the checking is intellectually tidiest.
