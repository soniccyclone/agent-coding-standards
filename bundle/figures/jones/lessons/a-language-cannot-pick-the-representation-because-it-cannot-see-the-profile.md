# A language cannot pick your representation for you, because it cannot see how the operations will be used

**Lesson:** Once you have found that describing a problem in terms of unordered collections, orderings, and keyed lookups makes it short and clear, the next thought is irresistible: put those things in the language, and the description becomes the program. It is a real idea and it has been built more than once. It is also the point at which two distinct activities get confused, and the confusion is worth being precise about, because the answer is not that abstraction is impractical.

The difficulty is informational, not aesthetic. A representation is good or bad only relative to which operations are performed and how often. The same collection wants completely different storage depending on whether membership tests dominate, or insertions do, or whether it will be small and dense or large and sparse. That information is a property of the whole program's behaviour over time; the person doing the design has it, or can go and get it, while a translator staring at a set of operations does not. So a language that implements the abstraction directly must either choose naively — correct and frequently unacceptable — or attempt to infer the access profile, which is optimization across whole spans of a program and hard in exactly the way the naive version was easy. Note that this is not a new problem introduced by rich abstractions: even the humble indexed array already forces a translator into this position, and getting it right requires reasoning about sequences of statements rather than any single one.

The conclusion is a division of labour rather than a verdict against abstraction. Describe in the abstract, because that is where clarity, brevity, and the ability to reason live, and because a description shaped by storage decisions is a description you cannot check against intent. Then treat finding a representation that fits the actual operation profile as the programmer's own work — not a failure to have been abstract enough, and not something to wait for a compiler to do. It is the step where knowledge nobody else has gets applied, which is precisely why it cannot be automated away, and precisely why doing it before you know the profile is the mistake.

One honest qualification: this is a claim about where information sits, so it moves when the information moves. Give a system real evidence about how the operations are used — measurements, a closed and known workload — and more of the choice can legitimately be made for you. What does not change is the ordering: describe first in terms that admit every representation, gather the profile, then choose.

**Source:** [Software Development: A Rigorous Approach](../works/software-development-a-rigorous-approach.md) — chapter 14's closing discussion of whether abstract data types should be added to programming languages: the observation that current high-level languages already offer types abstracting from machine detail, the array example in which a naive implementation is likely to be unacceptably inefficient while one attempting to discern the programmer's indexing patterns faces optimization across sequences of statements, the judgement that implementing the richer objects introduced in the book would leave huge scope for inefficiency and demand complex optimization, and the concluding statement that while abstraction is a proper tool for specifications it remains a fundamental part of the programmer's task to find representations fitting the particular operations required. The preceding paragraphs, contrasting a specification usable as an implementation plan with the folly of computing a greatest common divisor by enumerating divisors, supply the distinction between saying what is required and saying how it is to be computed.
