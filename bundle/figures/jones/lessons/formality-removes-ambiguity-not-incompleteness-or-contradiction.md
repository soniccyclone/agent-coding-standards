# A formal notation removes ambiguity but not incompleteness or self-contradiction, so bring a discipline that tells you when you have said enough

**Lesson:** The reason for writing a description formally is usually stated as escaping the vagueness of prose, and that reason is sound as far as it goes. It goes exactly one step. A formal statement has one meaning where an English one had several, but a *set* of formal statements can still be internally contradictory, and it can still leave open questions the author never noticed were open. Both of those are the failure modes of the prose you were fleeing. When a description is assembled as a list of properties the parts must satisfy, this is the ordinary outcome rather than the exceptional one: two properties written months apart quietly conflict, or the collection simply never says what happens in some combination of circumstances, and the notation offers no complaint in either case because a notation only checks what you wrote, never what you failed to write.

What makes this worse than the prose version is the discovery schedule. An ambiguous sentence tends to get argued about early, because two readers disagree out loud. A contradictory or under-determined set of formal properties is discovered when somebody tries to build against it and cannot — which is after the description has been reviewed, agreed, and used as the basis for estimates. And the under-determined case is the more dangerous of the two, because it does not announce itself at all: an implementation gets built, it satisfies every stated property, and it does something in the unaddressed case that nobody chose. The freedom was unintentional, but the result is indistinguishable from a decision.

The fix is not more formality; it is a separate, mechanical discipline for generating the obligations you owe. Something that enumerates the cases — every combination of a constructor with an observer, every state a value can be in when a given operation arrives — and hands you a list of blanks to fill. The point of such a checklist is that it is derived from the shape of the interface rather than from your imagination, so it catches precisely the cases you would not have thought to ask about, which are the only ones that matter. Formality and completeness are two independent properties, and only the first is bought by choosing a notation. The second has to be engineered.

The corollary for descriptions built the other way — around a chosen structure, with each operation defined over it — is why that style is easier to get right despite being less elegant. The structure is a fixed frame that each operation must be given a meaning against, so the question "have I covered everything?" reduces to "have I defined every operation?", which you can answer by counting. Style that localizes meaning per operation trades away generality and buys back an obvious completeness criterion; the style that puts meaning only in the relationships between operations gains generality and loses any local way to tell that you are done.

**Source:** [Software Development: A Rigorous Approach](../works/software-development-a-rigorous-approach.md) — chapter 16's assessment of implicit definition of data types: the stated practical objection that correct implicit specifications are not easy to construct, the two named hazards of writing a list of properties containing a contradiction and of leaving unintentional freedom, the remark that these are risks of natural-language specification being run again, the observation that the flaw may only be discovered when an implementation is attempted, and the citation of Guttag's rule for generating a checklist of the left-hand sides as the mitigation; together with the closing contrast that in a constructive description the operators can be specified one at a time whereas in an implicit one the meaning is carried precisely by the combinations of operators.
