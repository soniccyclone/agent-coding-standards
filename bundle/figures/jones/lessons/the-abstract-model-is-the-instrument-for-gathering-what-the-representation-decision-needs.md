# The abstract description is the instrument you use to collect what the representation decision requires

**Lesson:** Everyone agrees in the abstract that you should not fix your data structures before you know what will be done to them. Almost nobody can follow the advice, because the alternative on offer is to write nothing until you know everything, and you never know everything at the start. The resolution is to notice that these are two different artifacts. You can commit to a description right away — one stated in whatever vocabulary fits the subject matter, with no storage layout in it — and it costs you nothing you will later regret, because it contains no representation decision to be wrong about. What you defer is only the representation.

The important half is what the abstract description then does for you, which is more than sit there waiting. It is the tool for asking the questions whose answers the representation decision depends on. Which operations exist? How often is each one performed relative to the others? Which ones are on a path where cost matters? These questions are askable and answerable against an abstract model in a way they simply are not against a half-built implementation, because at that level each operation is a couple of lines and the whole operation set is visible at once. So the sequence is not "wait until requirements settle" but "describe abstractly, use the description to elicit the operation set and its shape, then choose the representation with that in hand" — and the middle step is real work that the description makes possible.

The failure mode is worth being able to recognize from the inside, because it does not feel like a mistake at the time. You pick the obvious representation, an indexed table keyed by the thing you happen to be looking up, and every operation you have thought of so far is fast. Then a new operation arrives — count how many entries share a value, check whether any group has grown too large — and against the abstraction it is one line, while against the chosen representation it is a full scan on a path that cannot afford one. Nothing was wrong with the operations you had; what was wrong was that the structure had been shaped by an incomplete list and there was no cheap way back. That asymmetry is the whole argument: an abstract description is neutral among representations and therefore survives new operations, while a representation is a bet on the operation list being closed.

**Source:** [Software Development: A Rigorous Approach](../works/software-development-a-rigorous-approach.md) — chapter 12's introduction of mapping notation via the students' whereabouts problem: the identification of two dangers in basing a specification on the implementation approach of an array indexed by student, namely having to relate names to indices too early and making some operations very inefficient; the later addition of an overcrowding check, described as easy to specify at the abstract level but potentially disastrous to implement had the array representation been chosen; the accompanying statement that no competent programmer would choose a final data representation until he had a clear idea of the total set of operations, and that this should nonetheless not prevent writing the specification; and the claim that the abstract model is ideal for couching questions such as the relative importance of the various operations, whose answers must be determined in order to select a representation that will perform acceptably. Chapter 11's opening remark that stepwise development permits enough work to be done to understand the operations and their relative frequencies before the representation decision is required makes the same point from the process side.
