# Read the architecture off the state, because whatever the state does not say gets scattered everywhere else

**Lesson:** The most informative page of a system description is the one that says what the system holds, and it is informative mainly for what it forbids. If files are held as a table keyed by name, then two users cannot own files of the same name — you know this from the table alone, without reading a single operation and without writing any. If the table becomes a tree of nested tables, separate name spaces appear and a new limit takes their place: no file can be reached by two different paths, so nothing can be shared. Each of these facts is a decision about what the system fundamentally is, it is settled by the shape of the held data, and it is checkable in seconds. Compare that with discovering the same fact by inspecting a hundred operations for something none of them does. Design by writing a series of these sketches, and at each one ask what it makes impossible; the ones you cannot live with tell you what structure to add next, and the structure needed is usually specific — two names can refer to one thing only when the thing has an identity of its own, so sharing forces the introduction of an intermediate identifier and no amount of nesting substitutes for it.

The corollary is a warning about what happens to facts you decline to put there. Model something with a structure richer than the problem needs — an ordered sequence where the order carries no meaning — and the truth that the order is irrelevant now lives nowhere in the model. It is distributed across the entire body of operations, recoverable only by reading all of them and observing that nothing depends on position. A definition that made this mistake in a handful of places became a document where five pages of held data plus three hundred pages of operations were jointly required to answer a question that five well-chosen pages would have answered alone. The rule to take from that: choose the held structure so that a reader who reads only it has learned something true, and treat every excess degree of freedom as information you have chosen to hide in the bulk.

Two habits follow. Be genuinely willing to throw a state away and start again once an operation or a legality condition turns out awkward on it; the awkwardness is evidence about the model, and rewriting a few paragraphs early is trivial next to the cost of a description whose centre is wrong. And when comparing two candidate models that can both express everything required, do not stop at expressiveness — ask which one shows the intended system more plainly, because the honest comparison between a structure that makes the interesting operation trivial and one that needs an elaborate legality condition to stay sane is not about power at all. The state is the compressed statement of an architecture, and compression is exactly what makes it worth arguing over.
