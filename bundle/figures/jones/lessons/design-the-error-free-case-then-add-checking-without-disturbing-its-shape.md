# Design the error-free case first, then add checking in a form that does not disturb its shape

**Lesson:** Treat freedom from bad input as an idealization, in exactly the same way you treat any other simplifying assumption. Design the algorithm against the world where the data is well-formed, get it right, and then bring in reality as a further step. This is not optimism and it is not a plan to add validation later and forget; it is the recognition that the structure of the computation is determined by the valid case, and that trying to discover that structure while simultaneously handling every malformation produces something in which neither is clear.

What makes the second step work — and what makes most attempts fail — is the requirement to preserve the shape. The naive way to add checking is to wrap the algorithm in tests, which either duplicates its traversal or scatters conditionals through it until the original outline is no longer visible. The alternative is a construct that can abandon the computation from wherever it has got to, so a check sits at the point where it is meaningful, costs a line, and does not restructure anything around it. That construct is what lets the main algorithm stay legible while the checking is embedded efficiently, and its availability is a genuine design consideration rather than a language nicety.

Two rules govern where checks belong, and they are opposites, which is why both need stating. Internally, resist checking assumptions you have already established — a check whose failure is impossible is cost with no information. At the edge, where values arrive from outside your system, check stringently and assume as little as you can get away with. Take seriously that the declared shape of the incoming data is itself an assumption someone may violate; it is not enforced by anything just because it is written down. The boundary is exactly where the two rules meet, which is why identifying it is a design decision and not a formality.

One more case is worth separating out. Sometimes making the checking a distinct pass costs nearly as much as the work itself — determining in advance whether a search will succeed means doing the search. In those cases do not put a validating step in front; extend the algorithm so its own result can report the outcome. And note what widening what you accept actually costs, since it is easy to think it is free: you have to say what the program does in the newly admitted cases, and that means the promise grows too. A wider domain always comes with a longer description of what happens in it.

**Source:** [Software Development: A Rigorous Approach](../works/software-development-a-rigorous-approach.md) — chapter 22's "Input Independence" section and the related remark in "Programs and Their Data": the proposal that perfection, meaning freedom from errors, be viewed as an abstraction of reality so that refinement to a representation including bad data is handled in the normal way; the two ways of widening a pre-condition, by generalization with an unchanged post-condition or by admitting a check whose results must then be reflected in the post-condition; the observation that a program looping on invalid data can be fixed by changing its test, at the cost of extending the post-condition to cover the newly admitted inputs; the instruction that excessive internal checking of assumptions must be avoided while stringent checks must be applied where input values come from outside the system, with the specific warning that the type clause is itself a hidden assumption a user may be able to violate; the search example, in which pre-checking would duplicate the algorithm so the algorithm itself should be extended to reflect missing elements; and the stated design proposal to design the main processing first, then incorporate error checking using an abnormal-exit construct that preserves the structure of the basic algorithm, and only then achieve the same flow of control in the chosen programming language.
