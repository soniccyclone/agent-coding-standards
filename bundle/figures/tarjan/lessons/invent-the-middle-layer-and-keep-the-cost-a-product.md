# Invent the middle layer, then keep the cost a product of factors you can improve separately

**Lesson:** Sleator and Tarjan solve a hard problem about changing tree structures by declining to solve it directly. They first invent an interface: a list of operations on a much simpler object, a single path, spelled out completely — query its ends, step along it, ask for the cheapest edge, shift every cost on it, reverse it, join two, split one. Then they assume that interface exists and build the entire tree solution on top, expressing each tree operation as a short composition of path operations. Only after that layer is finished and proved do they turn to implementing paths. The discipline is that the upper layer is developed *without knowing* how the lower one works, which is what forces the interface to be honest: every capability the upper layer needs must be named as an operation rather than reached for opportunistically.

The reason this is more than tidiness is what happens to the cost analysis. The upper layer's analysis produces a count — how many lower-layer calls a sequence of upper-layer operations generates — and nothing more. The lower layer's analysis produces a per-call cost. The total is the product, and the two factors are established by completely unrelated arguments. That factoring is what makes the paper's own progression possible: with an ordinary balanced structure underneath, the product is a squared logarithm; substituting a better-chosen structure for the same interface drops it to a single logarithm, and *not one line of the upper analysis is revisited*. Later in the paper the lower layer is swapped again for a different guarantee. Each substitution is a local change with a global effect precisely because the interface was fixed first and the count was proved against the interface rather than against an implementation.

The habit worth extracting is to treat "what is the smallest set of operations on a simpler object that would make my problem easy" as a first-class design question, asked before any implementation. Two tests tell you the layer is real. Can you state the upper layer's correctness and its cost purely in terms of operation counts, without mentioning representation? And could you replace the lower layer entirely without touching the upper one? If the answer to either is no, some capability is being used that the interface does not name, and the cost will not factor — which in practice means every future improvement to the bottom requires re-deriving the top. Keeping a cost as a product of independently improvable factors is worth real design effort, because it converts one hard optimization problem into two easy ones and lets them be attacked by different people at different times.

**Source:** [A Data Structure for Dynamic Trees](../works/a-data-structure-for-dynamic-trees.md) — the top-down development that assumes a solution for paths and lists the eleven path operations as primitives before implementing them, the implementation of each of the eight tree operations as compositions of those primitives, the theorem bounding the number of path operations generated by a sequence of tree operations, and the successive substitution of ordinary balanced trees, locally biased trees, and globally biased trees underneath the same interface to obtain different overall bounds.
