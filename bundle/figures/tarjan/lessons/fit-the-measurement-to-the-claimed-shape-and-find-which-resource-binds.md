# Fit the measurement to the shape you claimed, and find out which resource actually binds

**Lesson:** The theoretical claim is that the running time grows linearly in the size of the input. The experimental section does not simply report that the program was fast; it generates inputs at a range of sizes, measures, and fits a straight line, so the *shape* of the claim is what gets tested rather than merely the magnitude. The fitted coefficient then doubles as a usable engineering number — a rate of input processed per second — which is a far more actionable statement than an asymptotic class. And the inputs were not arbitrary: they were generated to sit at the extreme of the parameter the bound is stated in, densest possible while still having the property, so the measurement lands where the algorithm has the most work to do. The authors also note what their generator cannot produce, which is the right way to report a sampling method whose coverage is incomplete.

The second finding is the more instructive one and it came out of the experiment rather than the analysis. The program turned out to be limited by memory rather than by time: the largest input they wanted to test could not be run in the available space, even though the time it would have required was small and predictable from the fit. An analysis that bounds two resources will usually have been *written* about one of them, and which one actually binds is a fact about the machine and the constant factors, not about the asymptotics. Discovering that the binding resource is not the one you optimized is common, cheap to discover by measurement, and impossible to discover by proof.

Three habits follow, and they cost very little. Fit the data to the functional form you predicted instead of eyeballing whether the numbers look good, because a fit can falsify the exponent while a spot check cannot. Generate test inputs that maximize the parameter your bound is expressed in, and say what region of the input space your generator misses. And after measuring, ask which resource ran out first — time, memory, bandwidth, file descriptors, cache — since the answer reorders your optimization priorities regardless of what the analysis emphasized. The paper adds a fourth, harder discipline worth copying: it reports honestly that the implementation measured was a more complicated earlier version than the algorithm being presented, so the numbers understate the presented method. Saying which artifact the measurements came from is what keeps a performance claim attributable.

**Source:** [Efficient Planarity Testing](../works/efficient-planarity-testing.md) — the implementation and experiments section, which describes generating test graphs by repeatedly subdividing a face so that the result admits no further edges without losing the property, notes that not all such maximal graphs arise from this construction but that the generated ones exercise the program adequately, reports a fitted linear relation between running time and input size along with the resulting processing rate, observes that non-planar inputs generally finish sooner because the algorithm exits on the first detected conflict, records that the program was limited by available space rather than time so that a larger graph could not be run despite its predictable and modest time requirement, compares timings against a previously published algorithm on the same input, and states that the version measured was a more complicated earlier program than the algorithm presented in the paper.
