# Order the work so the items nest, and the bookkeeping collapses to a stack

**Lesson:** The state this algorithm has to track is, in the abstract, an arbitrary set: which attachment points along the current cycle already have something committed to each side. Arbitrary sets need searching, deletion from the middle, and a data structure with logarithmic operations. What the algorithm actually uses is two stacks. That is possible only because the order in which pieces are processed is chosen so their attachment ranges *nest* rather than interleave: pieces are handled in decreasing order of where they attach, all pieces belonging to one region are finished before any piece of another region is begun, and consequently every entry that becomes irrelevant is on top when it becomes irrelevant. Retirement is therefore a pop, insertion is a push, and the whole bookkeeping question disappears. When the search retreats past a vertex, the entries for everything at or beyond that vertex are exactly the top run of each stack, so they are discarded by advancing a pointer.

The generalizable claim is that the choice between a stack and something more powerful is usually not a property of the problem but a property of the order you chose to do the work in, and that order is often free. Interleaved lifetimes force a general structure: you need to remove an item while items created after it are still live, which means addressing the middle, which means indexing. Nested lifetimes permit a stack, and a stack is not merely a faster structure but a simpler proof, because "the thing I need is on top" is an invariant you state once instead of a lookup you justify at every use. So before reaching for a priority queue or a map keyed by identity, ask what processing order would make the lifetimes nest, and whether anything prevents you from adopting it. Here the enabling order came from a preparatory pass whose entire purpose was to arrange the input so the main pass would encounter work in the nesting order.

Two further consequences show up in this algorithm and both generalize. First, nesting is what makes recursion and the data structure agree: because the sub-problem's items are exactly the ones above a known point, a recursive call can share the parent's structure instead of building its own, with the boundary being a position rather than a copy. Second, the discipline is fragile in a specific and detectable way — the algorithm's correctness argument repeatedly appeals to the claim that entries below a certain point cannot matter to the current step, and that claim is precisely what a violation of the ordering would break. So if you take this route, write down the nesting property as an invariant with a name, because it is load-bearing for the representation and invisible in the code: nothing about pushing and popping reveals that a subtler order would have made the stack wrong rather than merely slow.
