# Extract the constraint graph, and a yes/no procedure starts producing the witness

**Lesson:** The algorithm as presented answers a question with a bit: the object either has the property or it does not. That is rarely what a caller wants — someone testing whether a circuit can be laid out flat wants the layout. The authors close by pointing out that the procedure already gathers everything needed to produce one, and that the clean way to see it is to name the constraint structure explicitly. Build a graph whose nodes are the individual decisions the construction had to make and whose edges record the two kinds of dependency the construction discovered: these two must agree, those two must differ. The property then holds exactly when this graph admits a two-colouring consistent with its edges, and a colouring *is* the witness. A problem that looked topological has been reduced to a standard constraint problem over a structure whose edges were being computed all along and simply not recorded.

Two separate lessons live in that move. The first is about recognizing the general problem hiding inside a special one. Any incremental construction whose steps are binary choices with agreement and disagreement constraints between them is a two-colouring problem, and saying so buys you a body of existing theory, existing algorithms, and a vocabulary for talking about why a failure happened — a contradiction becomes an odd cycle of constraints rather than an opaque "could not proceed." The second is about the difference between deciding and producing. A decision procedure that discards its intermediate commitments answers the question and destroys the answer's content; the same procedure that records them answers the question and hands back the object. Since the recording is nearly free here, the deciding-only version was a design choice with no upside beyond exposition.

The habit to take away is to ask, of any procedure whose output is a boolean, what structure it would have to keep to output the witness instead, and whether that structure is something already known. Constraint recording is cheap, and its payoff is threefold: the caller gets a usable result rather than a verdict, a failure becomes explainable in terms of a specific conflicting set instead of a point of surrender, and the reduction to a named problem lets someone else improve or reuse the machinery. Type checkers that return the inferred substitution, satisfiability checkers that return the assignment, schedulers that return the schedule, and configuration validators that return the resolved settings are all the same upgrade. A procedure that says only no is also a procedure that cannot tell you why.

**Source:** [Efficient Planarity Testing](../works/efficient-planarity-testing.md) — the applications and conclusions section, which notes that the algorithm as described only tests the property and does not construct a representation, that it nonetheless collects enough information for the construction to be easy, and that the way to do it is to build a dependency graph whose vertices correspond to the paths found and whose edges are of two types according to whether the two paths must be embedded on the same side or on opposite sides of the relevant cycle, so that a two-colouring of that graph satisfying the edge constraints corresponds to an embedding, together with the remark that the embedding algorithm is easily modified to construct and colour this graph and that doing so is what makes the result usable for tasks such as laying out circuit boards.
