# Which functions a system can compute is the boring question — judge it by which algorithms it lets you write, and what they cost

**Lesson:** The reflex when comparing formalisms is to compare the classes of functions they can express, and that comparison is close to worthless for design. It saturates almost immediately: a modest system with one recursion scheme already reaches far beyond anything anybody could run, and every subsequent extension you might design is not going to add reachable functions, because the reachable set was already unusably large. So if the function class stops discriminating at the second rung, it was never the axis you cared about. The axis that keeps discriminating is which *particular procedure* for a given function you are able to write down. Two systems agreeing on every function they compute can disagree entirely on that, and the disagreement is where all the engineering consequence sits.

The canonical embarrassment makes the point better than any principle. Take the most trivial operation on a number you can name — go back one. In a system whose only means of consuming a number is to fold over it, the obvious cheap procedure is simply not expressible; what you can write instead walks the entire number apart and rebuilds it while omitting the final step, so a constant-time idea becomes linear in its input, and worse, the wrong end gets removed than the one you would have chosen. Nothing is incorrect. The result agrees with the specification. But an encoding chosen for its elegance has silently dictated an implementation, and the dictated implementation is absurd on a real machine. Recognizing this as a genuine defect rather than an acceptable abstraction cost is the whole of the lesson: the search for better systems should be driven by which algorithms are currently unwritable, not by which functions are currently unreachable.

The same yardstick reframes what a strong guarantee costs. A system in which every program provably finishes cannot express every terminating procedure — not by oversight, but necessarily, because the procedure that runs your programs would then have to be one of your programs. That is a fixed price on the guarantee, and knowing it is fixed changes the conversation: you stop hunting for the system that is both total and universal, and start asking whether the procedures you actually need fall inside the boundary. And it cuts the other way too, because the same accounting exposes procedures that are formally effective and practically imaginary — transformations whose cost function stacks exponentials deeply enough that no input of any interest will ever finish. "There is an algorithm" and "there is something you can run" are different claims, and a formalism that only tracks the first will let you ship the difference.

There is a bonus in this stance that is easy to miss. Once you insist on algorithms rather than functions, a good model of your system becomes a tool for proving *negative* results — for establishing that some procedure you would like is not merely undiscovered but unwritable, and therefore that no amount of cleverness inside the current design will produce it. That is the most valuable thing a semantics can tell you, because it is the signal to change the design rather than keep trying.
