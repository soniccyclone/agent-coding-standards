# Closure is what turns one facility into many

**Lesson:** Arrange for an operation's result to be the same kind of thing as its input, and a long list of separate features stops needing to be designed. Once a query over tables yields a table, the definition of a derived view is not a new language but an existing query given a name; nesting one request inside another's condition needs no new construct because the inner result is already an acceptable operand; materializing a result into storage is the same operation with a destination; and a cursor's accumulated rows can be promoted to a stored table without conversion. Each of these arrived essentially free, and the contemporary field reports single out precisely this — that no separate definition language had to be learned, because the full power of the query language was already the view-definition language. The economy is not aesthetic. Every distinct facility you avoid is a grammar you don't write, an implementation you don't test, a chapter you don't document, and a concept your users don't hold.

The property generalizes past tables. A later design in the same lineage pushes it to the limit by making every value a flat sequence: a single item is not a different kind of thing from a one-item sequence but identical to it, sequences never nest into sequences, and any expression's operands are themselves expressions with no restriction. That eliminates the scalar-versus-collection distinction that forces most languages to duplicate operators, and it removes the special cases that a nested-collection model would demand. The cost of the discipline is that it constrains what you may add: a construct whose result is not a value of the one kind cannot be admitted, however convenient it looks in isolation.

The most useful part of this way of thinking is its diagnostic power, because the places closure fails predict where users will hit walls. The same system's honest self-assessment identifies its non-closed corners as exactly its rough edges: a view derived from a combination of tables is not updatable, so the view mechanism is admittedly not transparent; and the assignment operation produces a snapshot that is thereafter independent of what it came from, unlike a view, which stays live — a semantic seam that a user must remember rather than derive. A programmer holding this lesson audits an interface by asking, for each operation, whether the result can be fed back in wherever the input could go. Every "no" is either a feature waiting to be discovered or a leak that will surface as user confusion, and it is worth knowing which before shipping.
