# Prefer a medium the user can produce and edit

The comparison this work draws with picture-driven interfaces is not about
aesthetics — it concedes that the pictures are prettier. The argument is about
what the user can *do* with the medium. A picture must be made in advance by
someone else; the set of available actions is therefore fixed at the time the
program was written, and reaching one costs travel through menus. Text can be
created on the spot, edited character by character, saved, generated by another
program, and pasted from anywhere. So if the medium of interaction is text, and
any text can be invoked, the interface's action set is open and the user extends it
by typing. Adding an option to a command is editing a word; there is no
corresponding gesture in a world of pictures.

The structural consequence is that a whole category of construct disappears.
There are no menus here — not because menus were rejected on taste, but because a
line of text held in a convenient place already is one, and a better one, since it
can be modified in place and can hold anything expressible rather than anything
anticipated. That is the general shape worth extracting: when the medium your
interface is built from is also the medium your users can author, features that
would have needed a mechanism become conventions of use instead. Fewer mechanisms,
more reach.

The same reasoning generalizes past user interfaces to any place a system meets a
person or another program: prefer the representation that the recipient can
inspect, diff, store, generate, and hand-edit over the one that requires your tool
to interpret. This is what makes the collection of small editing programs in this
work sit in a plain-text file of example invocations — a directory becomes a
toolbox whose documentation is itself executable, because the examples and the
commands are made of the same stuff. A programmer who takes this seriously stops
asking what the interface should offer and starts asking what the user could
assemble if the parts were writable.

**Source:** [Acme: A User Interface for Programmers](../works/acme-a-user-interface-for-programmers.md) — the comparison section's argument that text is self-referential and editable where pictures are not, together with the user interface section's claim that any text anywhere can serve as a command, and the editing-tools directory whose guide file is edited and executed in place.
