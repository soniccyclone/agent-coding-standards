# The price of combining two pieces of code determines how well a system will be factored

**Lesson:** Programmers factor their code exactly as much as factoring is cheap. When invoking a named piece of work requires establishing a calling convention, deciding which registers survive, arranging where arguments live, and reserving somewhere for the return path, then every small unit costs more than it saves, and the rational response is to write large units. Remove that price and the calculation flips: units shrink until each does one thing, they nest without anyone tracking the nesting, and recursion stops being a special case requiring thought. The design lever here is not exhortation about modularity but the mechanics of invocation, because the mechanics decide what the exhortation costs.

Two structural choices do the work. Arguments and results live on a shared last-in-first-out store, so no caller and no callee has to agree on where values go, and intermediate results simply remain available without anyone naming temporary variables to hold them. Return information lives on a second, separate store, which means the argument store is never obliged to be balanced across a call and can be used freely across nesting depths. Separating control information from data this way is what makes invocation nearly free, and the observable consequence is code composed of very many very small named operations, since there is no longer any reason to inline something for the sake of avoiding a call.

The cost is honest and worth stating: an interpretive step per invocation is pure overhead, and as the work behind each name shrinks toward the size of that step, overhead approaches and passes half the running time. That is not a refutation, because the alternative arrangements charge comparable amounts through their own machinery, and because the overhead is concentrated in code that directs work rather than performs it. The practical stance is to place the computation-bound part where the machine can be addressed directly and let everything above it be composed of small named operations, accepting overhead exactly where it buys clarity and refusing it where it would show up in a measurement. A programmer who thinks this way judges an abstraction mechanism by what it charges per use, on the grounds that a mechanism nobody can afford to use is not one.
