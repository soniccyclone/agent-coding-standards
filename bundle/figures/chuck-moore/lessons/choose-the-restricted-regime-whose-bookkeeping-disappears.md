# Accept a restriction that makes the bookkeeping vanish rather than a generality that makes it permanent

**Lesson:** Most accounting machinery inside a system exists to support a freedom nobody exercises. Permit storage to be released in any order and you owe a compaction strategy, a relocation strategy, and a way to reason about fragmentation forever; permit release only of the most recently acquired storage and the entire apparatus reduces to moving one pointer back. The striking part is that the restricted regime turns out to match how the work actually proceeds: things get added, something is found wrong, the recent additions are discarded, the fault is fixed, and they are added again. The generality was never being used, but its cost was being paid on every operation.

The same move recurs at every level of a system once you look for it. Values passed between operations can live in a shared last-in-first-out store instead of a negotiated argument area, which removes the negotiation. Fixed-size units of secondary storage addressed by number need no directory at all, since the physical location is computed rather than looked up, and a simple flag marking a modified unit removes the question of when to write it back. Concurrency can hand off control only at points the code itself designates, and because the suspension points are known, there is almost no context to preserve, the scheduler shrinks to a few instructions, and the handling of shared resources becomes something a person can reason about instead of guess at. In each case a freedom is surrendered and a whole category of mechanism disappears with it.

Choosing this way requires being honest about the exposure. Cooperative handoff is defenseless against a computation that never yields, and only survives because the systems in question are dominated by waiting rather than by computing; when that assumption breaks, the fix is to insert yields deliberately rather than to install a general preemption scheme. Refusing to release storage out of order does leak space in the case where something built other things and is no longer wanted, and the honest answer is that the leak is tolerable. A programmer working this way asks, before building any manager, which freedom the manager exists to protect and whether the actual usage ever needs it, because a restriction accepted early is usually cheaper than a generality maintained forever.
