# Latency between writing something and watching it run governs quality more than any methodology does

**Lesson:** When the gap between expressing an intention and observing its effect is long, the programmer's attention is consumed by the apparatus that spans the gap rather than by the problem. Assembling inputs, running a translator, resolving references, arranging a load, and starting a separate observation tool each take the mind off the question that was being asked. Compress that gap to the point where a newly written unit can be exercised by naming it and looking at what it left behind, and something qualitative changes: units get tested while the intent behind them is still fresh, and they get tested individually, which is where testing actually catches things.

The mechanism explains a productivity difference large enough to be startling to observers, and the explanation is not that the tools are clever. It is that all of the system's own machinery is available at the same prompt the programmer is already using. The thing that breaks text into words, the thing that builds definitions, the thing that reaches storage, the assembler for the local processor, all of it is callable in the same way as application code, so there is no boundary to cross and no second dialect to learn in order to inspect or extend the system's behavior. The uniformity is what makes the short loop possible; separate tools with separate notations reintroduce the latency no matter how fast each one is individually.

Fast feedback also changes what a system can afford to be. If regenerating executable form from source takes no perceptible time, then keeping compiled artifacts as durable objects stops being worth its trouble, and the whole business of maintaining and linking object libraries can be dropped. And the argument runs all the way down to the beginning: even bringing a system into existence on bare hardware is best done by first building the smallest things that shorten the loop, something to preserve work and something to display memory, before attempting anything substantial. A programmer who takes this seriously invests early in the means of observation, and treats a long build or an opaque runtime as a defect in the working conditions rather than a fact of life.
