# A specification is an instrument you can run against a candidate, not a description you generate code from

**Lesson:** Almost everything the field calls a specification language is an implementation language at a higher level: you write a description and a tool produces the artifact, so the artifact is correct because of how it was made. This work argues that a discipline built only on such tools is missing half of its instrumentation, and points at the historical pair to show which half. Interchangeable parts did not become possible because someone invented a machine that could shape a part from a template; they became possible when someone realized that shaping tools are insufficient without measuring tools — that you need an independent instrument you can apply to a finished part, made by any means, to decide whether it falls inside tolerance. The gauge is not a fancier lathe. It answers a different kind of question, from the other side of the interface.

The programming version of a gauge is a predicate over a candidate implementation: something you hand an unknown thing, which exercises it and reports whether it behaves as required. Built this way, a specification becomes composable in its own right — a requirement can be assembled out of smaller behavioral requirements, and those requirements have a lineage of their own that has nothing to do with how any implementation is descended. This buys several things that a derivation-based view cannot. It survives reimplementation, since the same instrument can be applied to a rewritten, ported, or competing version. It lets producers work in whatever language suits them, because the consumer's acceptance no longer depends on the production method. And it establishes a shared vocabulary between the two sides, which is the ordinary function of measurement everywhere else: a request for a pound of a particular kind of fastener works only because both parties can reach for a procedure that decides what counts as a pound and what counts as that fastener. Software has no natural senses to fall back on, so the terms of trade have to be constructed deliberately or they do not exist.

The pointed part of the argument is what it concedes. A gauge reports conformance within a tolerance; it does not prove absence of defects, and this work treats the reflex objection to that — that testing only reveals the presence of faults — as a preference that has cost the field its instrumentation. Separating measurement from production also frees the measuring tool from the constraints that bind the producing one, since a gauge does not have to be efficient, only decisive, which opens the door to expressing requirements in machinery far richer than a compiler could afford. A programmer who works this way writes the acceptance instrument as a first-class deliverable that ships alongside the interface rather than inside the implementing team's repository, keeps the old instrument runnable when a new requirement lands so that a change can be shown not to have disturbed what was already promised, and treats a set of behavioral checks that any candidate must pass as the real definition of a type — a notion of type that covers what a thing does and not merely how its storage was declared.

**Source:** [Planning the Software Industrial Revolution](../works/planning-the-software-industrial-revolution.md) — the "Adopting the product-centered paradigm" section, which sets Blanchard's pattern lathe against Hall's inspection gauges, proposes test procedures as the primitives of a specification language with a duck-recognition example, and argues that specification and implementation tooling should be coequal partners in the development process; the closing account of Stepstone's difficulty in re-releasing components without such instruments supplies the empirical motivation.
