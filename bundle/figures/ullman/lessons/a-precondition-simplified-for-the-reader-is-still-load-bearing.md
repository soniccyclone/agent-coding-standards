# Record the precondition you actually need, not the one you tell people

**Lesson:** Every reusable procedure ships with a stated condition for when it works, and that statement is almost never the theorem's actual hypothesis. It is a stronger, more memorable, easier-to-check surrogate that implies the real one on everything anybody expects to encounter. Substituting the surrogate is a good decision. Forgetting that you substituted is not, because the difference between the two is precisely the set of inputs on which the procedure fails while every documented check passes.

The gap usually has a specific character worth naming: the real condition rules out a coincidence, and the surrogate rules out a structure. An iterative process converging to a unique limit needs both connectivity and the absence of a shared periodicity in its cycle lengths. Connectivity is easy to state, easy to picture, and easy to test. Aperiodicity is fiddly to explain and, on any large naturally-grown instance, satisfied by overwhelming accident: one odd cycle anywhere in a billion-node component destroys the periodicity, and there is no plausible process that would produce a huge structure whose every cycle length shares a divisor. So the honest version of the claim is not "connectivity suffices" but "connectivity suffices for instances nobody built on purpose."

That last clause is the part that must be written down, because it converts a mathematical caveat into an operational one. An input assembled by an adversary, generated by a synthetic benchmark, or produced by a code generator with a regular structure is exactly the kind of thing that hits the gap, and all three are common. A layered pipeline graph, a bipartite dataset, a test fixture built from a repeating template: each of these is periodic by construction and each will be presented to your procedure by someone who checked the documented condition and found it satisfied. The failure will not look like a violated assumption. It will look like the procedure not terminating, or oscillating, or returning an answer that changes when you change the iteration count.

There is a second reason to keep the exact hypothesis somewhere retrievable even when you never state it in the interface. Preconditions are what tell you which generalisations are safe. If your recorded condition is the surrogate, then any question about extending the method to a new class of inputs gets answered against the wrong criterion, and you will either refuse cases that would have worked or accept cases that will not. The discipline is cheap: state the checkable condition where users will read it, keep the true condition adjacent to the implementation with a note on why the surrogate implies it for the inputs you expect, and name the kind of input that breaks the implication. Two sentences, and they are the two sentences that make the eventual bug report legible instead of mysterious.
