# Build the vocabulary that forces a complete description, then make the description itself the program

**Lesson:** When a class of problems is hard to program, the obvious diagnosis is that the notation is clumsy, and the obvious remedy is better notation. That diagnosis is true and shallow. The deeper shortage is conceptual: people confronted with wildly different systems — a network of cells, a shop floor, a road, an organization — have no shared set of terms in which all of them can be approached at all, so each is understood ad hoc and none can be compared with another. The valuable thing to build is that set of terms, chosen so that describing a system in them requires answering every question that determines the system's behavior. A good vocabulary is not merely convenient; it is interrogative. It tells you what you have not decided yet, and it makes two superficially unrelated systems look either alike or different for reasons you can name.

The second move is what makes the first one stick. If the description is written in a vocabulary the machine can execute, then the artifact people read, argue over, and circulate is the same artifact that runs. There is no translation step in which the description's claims quietly cease to be true of the implementation, and no drift, because there is only one text. This reverses the usual relationship between documentation and code: the description is not a shadow of the program, the program is the description, and its readability for humans is a first-class design requirement rather than a courtesy. It also means the price of a sloppy description is immediate and local — the thing does not run, or runs visibly wrong — instead of being deferred until someone notices the document and the system disagree.

The design consequence is a specific priority ordering that is easy to state and hard to hold. The concepts come first and must be small in number, because a person can only reason precisely about a few things at once. Executability is then a constraint the concepts must satisfy, not a source of new concepts: the vocabulary is not allowed to grow warts because the machine is awkward. And general computation has to be included in the description language rather than bolted alongside it, since real descriptions contain procedure as well as structure, and splitting them across two notations reintroduces exactly the gap this whole approach exists to close. A programmer who works this way treats designing the terms as the main work, and treats any document that describes a system but cannot be run as a liability with a known expiry date.

**Source:** [SIMULA - an ALGOL-Based Simulation Language](../works/simula-an-algol-based-simulation-language.md) — the design-objectives discussion, which sets the need for a shared set of basic concepts above the need for easier programming, asks the language to expose similarities and differences between systems and to force the analyst to confront every relevant aspect, requires descriptions to be readable enough to serve as communication, and states that a system description doubles as the program that simulates it. Also [SIMULA 67 Common Base Language](../works/simula-67-common-base-language.md) — the introduction's decomposition argument, which grounds the small-vocabulary requirement in what a human mind can hold while thinking precisely.
