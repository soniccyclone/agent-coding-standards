# Comment the part of a program that holds still, because the code already shows you what moves

**Lesson:** Code is a complete record of the dynamics — every state change is spelled out, in order, with nothing hidden. So a comment that names the change an instruction makes carries no information at all; it repeats what is already there in a second notation. What code does not record is the statics: the relation among the variables that every instruction is arranged to preserve, the property that survives the loop rather than the property the loop body destroys and rebuilds. That relation is the thing a reader has to reconstruct, and reconstructing it is exactly the hard part, because nothing in the text says what a program is trying not to disturb. Comment that, and only that.

There is a sharper version of the rule, and it tells you precisely which comments earn their space. Work out what a reader would need in order to rebuild the whole correctness argument mechanically, with no guessing. Given a program's overall contract, most of the intermediate reasoning can be regenerated by pushing the contract backwards through the straight-line steps — the demand on each statement is forced by the demand on the one after it, so writing it down adds nothing. Loops break that mechanical regress: no procedure recovers the loop's preserved relation from the surrounding text, because the relation is a genuine design choice made by whoever wrote the loop. It is the one piece of information the code cannot be made to yield. Therefore it is the one piece that must be written down. Everything recoverable is noise; everything unrecoverable is documentation.

That criterion is worth carrying past assertions and loops. Whenever you are deciding what to record about a component — a comment, a docstring, a design note — ask what a competent reader could derive from the artifact alone and what they could not. Choices that were forced need no explanation; a reader will re-derive them or never need them. Choices that were free, and that the code merely obeys without exhibiting, are the whole content of documentation. The habit also improves the code, because a design whose free choices are few and stateable is a design that can be written down cheaply, and one whose free choices are everywhere is telling you it has no structure to record.

**Source:** [The Craft of Programming](../works/the-craft-of-programming.md) — the section on assertions as comments, which contrasts the redundant restating comment against the assertion that exposes the unchanging aspect of a computation; and the closing discussion of the Fibonacci proof, where working backwards through assignments makes every intermediate assertion derivable and isolates the loop invariant as the single item that must appear as a comment.
