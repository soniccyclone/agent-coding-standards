# Describe only what a component touches, and make the extension to a larger context somebody else's rule

**Lesson:** The scalable way to describe a component is to mention exactly the resources it actually reads, writes, acquires or releases, and nothing else — then to have a single metarule that lifts that description into any larger context by asserting the rest is untouched. Two dual properties make this honest. Everything the component touches must appear in its description, so nothing is used behind the reader's back; and everything its description mentions must actually be touched, so the description does not overclaim territory. A component whose description satisfies both is intelligible in isolation, and reasoning about the enclosing program becomes composition rather than re-analysis. The alternative — describing components against the whole world and hoping the irrelevant parts stay irrelevant — puts the size of the system into the cost of understanding any part of it.

What makes this a real discovery rather than an obvious policy is that the naive version of the extension rule is unsound as soon as resources can be reached by more than one name. Take a component that stores through one handle, and try to carry along an unrelated-looking fact about a second handle: the step fails, because nothing said the two handles were different, and the fact you carried along may be exactly what the store destroyed. The lesson generalizes well past pointers. Any "this fact is about something else, so it survives" argument is smuggling in a disjointness assumption, and if your description language cannot state that assumption, the argument is unsound rather than merely informal. Recovering local reasoning therefore requires the ability to say that two descriptions concern separate resources — and once you can say that, the extension rule becomes both sound and, in a precise sense, sufficient: anything derivable from knowing only a component's local description follows from that description by this rule plus routine structural steps.

The same locality discipline suggests how to describe a structure caught mid-surgery, which is where naive specifications usually collapse into a case analysis over intermediate states. Rather than describing the mangled arrangement directly, describe it as an obligation: the part you are holding, joined with a promise that if the displaced piece were handed back in a specified form, the original global property would hold again. The intermediate state is then characterized by what it needs in order to become whole, which is stable across the whole traversal, instead of by an enumeration of how far the damage has spread. Reserve the device for where it earns its keep — most uses of it are formal rather than illuminating — but for algorithms that temporarily destroy the structure they are traversing it is the difference between a legible invariant and an unreadable one.
