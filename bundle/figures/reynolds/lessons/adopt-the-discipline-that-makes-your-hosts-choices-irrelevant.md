# To stop depending on a choice your host made, find the discipline that makes the choice irrelevant

**Lesson:** When a program's behaviour turns on some convention of the system it runs inside, the useful question is not how to detect the dependence case by case but what discipline would make the convention unable to matter at all. Work it out by finding the narrowest condition under which the two possible conventions produce identical behaviour. For evaluation order, that analysis is short: postponing an operand's evaluation, or repeating it, can only change the outcome by *skipping* it, so the outcome differs only when an operand would not terminate and the function receiving it never consults it. Hence the sufficient condition — no argument position may contain anything that could fail to terminate.

Two things about that condition are instructive. First, applying it requires a classification of which computations might run forever, which is not decidable, so the classification must be made conservatively: assume the worst unless termination can be shown. Design rules that depend on undecidable properties are still usable as long as the conservative direction is the safe one. Second, the condition appears at first to rule out all interesting programs, and following that appearance through is where the insight is rather than a refutation. If no argument may be a possibly-nonterminating call, then a function calling one must hand back that call's result untouched, and must itself be possibly-nonterminating, so by induction the first such result to be produced is the final result of the entire program. A condition that forces every program into that shape looks fatal — and yet there is a transformation putting any program into exactly that shape, by giving each such function an extra argument representing what to do with its result. What looked like a condition no program could satisfy was a condition every program can be *converted* to satisfy.

The most transferable part is a warning about the scope of the audit. The first attempt at the transformation here treats the interpreter's own procedures as the things that might diverge and misses a spot, because the class of possibly-nonterminating computations also includes the function values the interpreter is manipulating on behalf of the program it runs. Those are data from the interpreter's point of view, and they still have to be brought under the same discipline. Generalize: when auditing which parts of a system can fail, block, or diverge, the audit has to cover the callable things flowing through as values, not merely the procedures you wrote. Anywhere your program invokes something it received rather than something it defined, the discipline you imposed on yourself has to be imposed on the interface too.

**Source:** [Definitional Interpreters for Higher-Order Programming Languages](../works/definitional-interpreters-for-higher-order-programming-languages.md) — section 7's analysis that call by value and call by name can differ only when a nonterminating operand goes unused, the fail-safe classification of functions into serious and trivial, the induction showing the resulting condition forces every serious result to be the program's final result, the continuation-passing transformation that achieves it, and section 8's correction of the first attempt on the meta-circular interpreter once the defined language's own functional values are recognized as serious.
