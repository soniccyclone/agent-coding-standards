# Spend leftover freedom to stay inside a cheaper encoding, and collect the structural guarantee it implies

**Lesson:** There is a move available when a general-purpose container looks expensive to represent, and it runs backwards from the usual direction. Instead of hunting for an encoding that covers every value the container could hold, pick a drastically cheaper encoding that covers only a thin slice of them — a set of positions stored as a single upper bound rather than as a set — and then go back through the program and check whether you have enough remaining freedom to guarantee it never leaves that slice. Very often you do, because a well-built description still has unmade choices in it: which element to remove, which slot to fill next. Those choices were left open because correctness did not depend on them. Now they have a job. Resolve each one in the way that keeps the value inside the representable slice, and the cheap encoding becomes not merely adequate but exact.

What makes this more than a space optimization is what tends to come with the slice. A restriction narrow enough to encode in a single number is narrow enough to have strong structural consequences, and you inherit those consequences whether or not you asked for them. Confine the shape to prefixes of one canonical enumeration and every value is automatically near-balanced, so the repair operations that walk from a leaf to the root are logarithmic without any rebalancing logic existing anywhere in the program. That is a performance property nobody coded, arising as a corollary of a representation restriction adopted for storage reasons. Restrictions that pay twice like this are worth actively looking for; they are the reason canonical forms are so often the right call.

The obligation this creates is a discipline, and it is the same one every restricted encoding carries: the restriction is now a standing invariant, maintained by convention at every site that modifies the structure. Someone who later adds an operation resolving one of those choices differently — removing an interior element instead of the last one — will have written something that is perfectly correct against the abstract description and silently unrepresentable. So the restriction has to be written down as an invariant on the concrete variable, not left as a property that happens to hold because of how the three existing call sites were coded.

**Source:** [The Craft of Programming](../works/the-craft-of-programming.md) — Section 5.2.4, which represents tree positions by positive integers numbered level by level so that the father and son operations become halving and doubling, then observes that it is unnecessary to represent arbitrary finite integer sets because, by resolving the program's indeterminacy appropriately, the position set can be constrained always to be an initial interval; introduces a single limit variable with that representation invariant; notes that this representation is incomplete since there are trees that are not intervals, but that preserving the invariant guarantees unrepresentable values are never assigned; records as an added benefit that the set is then always almost-balanced, so the ascending and descending repairs run in logarithmic time; and resolves the two indeterminate position choices as taking the last position and taking the next one, augmenting each with an adjustment of the limit.
