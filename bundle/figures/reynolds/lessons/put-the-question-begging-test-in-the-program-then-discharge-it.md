# Write the question-begging test into the program on purpose, so the hard invention is isolated to one obligation

**Lesson:** When a program's difficulty is concentrated in one decision — is this collection the thing we were looking for? — there is a strong temptation to solve that decision first, because nothing else seems to make sense until you have. Do the opposite. Write the decision into the program as a predicate phrased in the vocabulary of the problem statement, which is to say a test that assumes the answer you are trying to compute, and get on with everything else. The scaffolding around it — what to accumulate, when to output, what gets removed afterwards, why nothing is emitted twice — can all be built and proved correct against an oracle, because those parts only need to know what the test *means*, never how it is decided.

What this buys is a change in the shape of the remaining work. Instead of an algorithm to invent, you have a proof obligation with a precise statement and a large stock of hypotheses: at the point of the test, every invariant you have accumulated is available — the global ones about what has been emitted so far and what remains unclassified, the per-activation ones about what this call has added, the postcondition of the traversal it just finished. The obligation is to find a decidable predicate over the concrete state that, under all of those hypotheses, is equivalent to the oracle. That is still hard, but it is a self-contained mathematical question with a stated context, rather than a design problem entangled with everything else in the program.

There is a further dividend that is easy to miss. Proving the equivalence forces you to examine both directions, and the failing direction usually hands you something. Showing that the oracle can be false only when a certain intersection is non-empty means that in exactly that case a witness exists — and a witness of that kind is frequently the very fact the caller needs in order to make progress. So the case analysis that discharges the placeholder also supplies the strengthened postcondition that makes the recursion go through. Placeholders paid for honestly tend to give change.

**Source:** [The Craft of Programming](../works/the-craft-of-programming.md) — Sections 5.4.2, where a strongly-connected-components program is written containing the test "is this set the strongly connected component generated by x", with Reynolds noting that this begs the question of how one finds such components but that a more constructive test will replace it later; the surrounding invariants about the output set, the not-yet-classified set, and each call's own contribution are established against that placeholder, and the test is then proved equivalent to emptiness of the intersection of the current call's reachable set with the saved value of the unclassified set — the non-empty case simultaneously yielding the path witness that establishes the strengthened postcondition of the recursive call.
