# In a cyclic network, buffer capacity is a semantic parameter, and behaviour can depend on it non-monotonically

**Lesson:** In a straight chain flowing one way, whether messages are buffered and how deeply makes no difference to what the chain computes; capacity is purely a performance setting. Generalize to a network where messages can travel in both directions and paths can loop, and that stops being true. It is possible to build an arrangement that seizes up if any buffer is allowed to grow beyond a certain size, and a different arrangement that seizes up unless some buffer exceeds that same size. Capacity has become part of the meaning, and worse than that, behaviour is not monotone in it — you cannot reason "more buffering can only help" or "less can only help", because both are false. A parameter usually delegated to operations, tuned by whoever is on call, is now something the correctness argument depends on.

Two ways out exist and both cost something worth knowing in advance. Make every buffer unbounded, which restores regularity by removing the parameter, and pay for it twice: storage is consumed without limit when a consumer falls behind, and every network becomes an infinite-state system even when each component is finite, so the analysis techniques that work on finite systems stop applying. Or keep capacities finite and treat each one as part of the specification — stated, justified, and included in whatever argument establishes that the system does not seize up. The second is usually right and is almost never done, because a number that lives in a configuration file does not feel like part of a proof.

There is a separate argument against buffering that has nothing to do with correctness and deserves to be weighed alongside. Every buffer inserts delay between a stimulus and its response, which is precisely wrong wherever interaction is meant to feel immediate. And a fault that occurs while processing a buffered stimulus is much harder to attribute and recover from, because the thing that caused it happened at an earlier time and possibly under different conditions, and the connection between the two is exactly what buffering removed. Buffering is a technique for keeping expensive processors busy; where responsiveness and diagnosability matter more than utilization, its cost is paid in the two currencies hardest to reclaim.

**Source:** [Communicating Sequential Processes](../works/communicating-sequential-processes-book.md) — the multiple buffered channels subsection of the discussion chapter's communication section, which observes that in a linear one-directional pipe it does not matter whether the message sequence is buffered, but that once the pattern is generalized to a possibly cyclic network the presence or absence of buffering can make a vital difference to logical behaviour — citing a program that deadlocks if a buffer is allowed to exceed a given length and a different one that deadlocks unless it does — recommending unbounded buffers to avoid such irregularities while noting the grave implementation cost and that every network then becomes an infinite-state machine even with finite components, and closing with the observations that buffers interpose delay between stimulus and response, make faults harder to trace and recover from, and are a batch-processing technique to be avoided where fast interaction outweighs processor utilization.
