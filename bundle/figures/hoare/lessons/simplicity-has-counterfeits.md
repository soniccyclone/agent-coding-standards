# Simplicity has counterfeits: modularity and orthogonality are means, and adopting either as the goal produces complexity

**Lesson:** Two design virtues are routinely substituted for simplicity, and both substitutions fail in the same way — they are harder to achieve than the thing they replace, so a designer who reaches for them as primary goals ends up with neither.

The modularity substitution says: a user who cannot hold the whole system in mind may safely learn only a part of it. This is true exactly while the user's work is correct, and false at the moment it stops being correct. A mistake reaches into the parts of the system the user never learned; if the tooling catches it, the diagnostic is phrased in vocabulary the user does not have, and if it does not, the user is worse off still. Layer that partial understanding on top of a complex implementation, a complex runtime environment, and complex local conventions for use, and the practitioner facing a hard task is overwhelmed by accumulated incidental complexity rather than by the task. So the honest reading of "you only need to know this subset" is: you only need to know this subset until something goes wrong, which is precisely when you needed to know more.

The orthogonality substitution says: if the system supports dimensions A and B, it should support every combination of them, since some user will find a use for each. The trouble is that a clever user will always find a use for anything, so "somebody could use it" cannot discriminate between a feature that earns its place and one that exists only because the grid had an empty cell. Combinations generated by the shape of the notation rather than by demonstrated need enlarge the surface every user must understand in order to be sure what their own code means.

Neither of these is a bad property. As means toward overall simplicity both are excellent, and it is a real virtue when a design is decomposable or when its dimensions compose freely. The failure is one of ordering: simplicity is the condition under which a designer can evaluate the consequences of their own decisions, an implementer can be reliable and fast, and a user can actually master the tool and spend their attention on the problem instead of the instrument. Pursue it to an extreme when you are asking people to abandon something they already understand — a practitioner has learned to work around every defect in their current tool, and often to exploit those defects, so nothing but a large and legible reduction in complexity will move them.

**Source:** [Hints on Programming Language Design](../works/hints-on-programming-language-design.md) — the Simplicity discussion, which treats modularity and orthogonality as displaced objectives and argues from the mastery-of-tools case that simplicity is the user's benefit before it is the implementer's.
