# Enforce a discipline through an interface so pleasant that nobody wants an escape hatch

**Lesson:** When a limited real resource must serve an unknown number of users, do not let the users touch it. Interpose a per-user stand-in that each user declares and works with exactly as though it were privately owned. The stand-in has two jobs, and they are usually mistaken for one job with a side effect. The first is presentation: it assembles a coherent object out of whatever scattered pieces of the real thing it managed to obtain, so the user handles one continuous item rather than a set of allocations with a mapping to remember. The second is enforcement: it makes the rules of correct use structurally unbreakable — this user can reach only what was allocated to it, and cannot fail to give things back, because giving back is not an action the user performs.

The relation between those two jobs is the entire lesson, and it is not that they conveniently travel together. The presentation is what makes the enforcement painless, and painless enforcement is the only kind that survives contact with people working under deadline. A discipline that is enforced but inconvenient generates a steady demand for an exemption, and the exemption, once granted to anyone, dismantles the guarantee for everyone — because a guarantee that holds for all users except the ones who asked nicely is not a guarantee, it is a default. So interface quality is not a courtesy extended to users; it is structurally load-bearing for the safety property. When a restriction and the convenience that makes it tolerable appear as two work items with separate priorities, that split is itself the defect.

Two tests are worth applying to any such stand-in. Is using the mediated version textually identical to using a private one, so that code written against the private thing runs unchanged against the shared thing? If so the mediation is invisible and cannot be resented, and the two implementations can be swapped for testing or for a change of scale. And what happens when the underlying pool runs out? A layer presenting an unlimited illusion over a limited reality owes an answer, and the good answer is to stop handing out new allocations while some remain rather than when none do. Deferring the refusal until genuine exhaustion produces the failure at the worst possible moment — when every user holds a partial allocation, none can complete, and none can be persuaded to let go.

**Source:** [Communicating Sequential Processes](../works/communicating-sequential-processes-book.md) — the multiple resources section of the shared resources chapter: the filing system in which users never communicate with the sectors of backing store directly but declare and use a virtual scratch file as though it were a private subordinate; the statement of that paradigm's two functions, first providing a clean interface by gluing scattered sectors into a single contiguous file and second guaranteeing disciplined access so that each user reads only from its own sectors and cannot forget to release them, followed by the remark that the first is what makes the second painless; the requirement that use of the virtual file have exactly the same effect as a private one apart from resource limitations; and the closing note that a finite backing store risks deadlock if it fills while all users are still writing, a risk reduced by delaying acquisition of new files when the store is nearly full.
