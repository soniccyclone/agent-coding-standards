# Coarsen the model to exactly the property you are proving, and structural certificates appear

**Lesson:** A proof about a system need not be conducted in the model you designed the system with. Name the property first, then ask what the model could stop recording without that property becoming unstatable, and stop recording it. For the question of whether parties can get stuck, the contents of their messages are irrelevant — whether two of them can agree on a next step does not turn on which value would pass — so every exchange collapses to a bare occurrence named for the connection it happens on, and connections leading nowhere outside the system can be dropped entirely. The gain is not incremental. A system whose configurations were indexed by unbounded data becomes a system with a handful of configurations, and a question that needed an argument becomes one that can be settled by algebra.

The discipline is in choosing the coarsening honestly, and the criterion is directional. A coarsening is sound for a property when every behaviour of the detailed system appears in the coarse one, so that ruling the bad thing out up there rules it out down here. The direction that is safe is the one that admits *more* behaviour, not less. Discarding message contents qualifies for stuckness precisely because it can only add possibilities — a party that would have declined a particular value now appears willing to take any — so if the coarse system cannot seize up, neither can the real one. The instant a property depends on something you discarded, the coarsening is worthless and actively misleading, which is why the property has to be named before the abstraction is chosen and never after.

The reward for coarsening well is that structural facts become visible which the detailed model concealed. Once exchanges are bare occurrences, the system is a graph, and graph properties start earning their keep: two parties joined by exactly one connection cannot fail to agree with each other, so any network whose connection graph contains no cycle can be split repeatedly into halves joined by a single connection and certified without anyone examining a component's internals. A cycle destroys that decomposition and with it the free proof, which is exactly why a cyclic arrangement can be broken by swapping two adjacent steps inside one participant while an acyclic one cannot. That is a design rule derived from the coarse model and inexpressible in the detailed one: topology carries the safety argument, so choose the topology deliberately and treat every cycle you add as a proof obligation you have just signed up for.

**Source:** [Communicating Sequential Processes](../works/communicating-sequential-processes-book.md) — the communications section of the communication chapter: the observation that two concurrent processes communicating on a single channel cannot deadlock, and hence that any acyclic network of non-stopping processes cannot deadlock because an acyclic graph decomposes into subgraphs joined by a single arrow; the remark that the worked network contains an undirected cycle and so cannot be decomposed that way, with the note that reversing two adjacent outputs inside its loop would deadlock rapidly; and the following paragraph stating that in proving absence of deadlock one may often ignore message contents, treating each communication as a single event named for its channel and ignoring communications on unconnected channels, after which the network is reduced algebraically to a single non-stopping process.
