# An access restriction is what turns polling into event-driven re-evaluation: prove only one thing can falsify a condition and you know exactly when to retest

**Lesson:** A participant that must wait until some condition holds appears to face a choice between two bad options: re-evaluate the condition constantly and burn the machine, or re-evaluate it on a timer and be late. The third option is available only if you can answer a question about the *causes* of the condition — what could possibly change its value. If every variable the condition mentions is either owned exclusively by the waiting participant, and therefore cannot change while it waits, or belongs to a shared item that may only be touched under a discipline you control, then the condition's value can change only at the moments when that shared item is modified. Re-evaluating precisely at those moments is complete: not an approximation of continuous checking but exactly equivalent to it, with a fixed and knowable cost.

The point worth extracting is that the efficiency came from the restriction, not from cleverness in the waiting mechanism. Because access to the shared state is confined to identifiable places, the set of moments at which a waiting condition could become true is finite and known, and the machinery need only act at those. Loosen the restriction — let any code touch the shared item anywhere — and no such argument exists, so the only sound implementation is continuous re-evaluation, and every practical system then quietly substitutes an unsound one on a timer. This is the general shape: a constraint on who may write is what converts an open-ended search into a bounded, exact one, and the same reasoning underlies cache invalidation, incremental recomputation, dependency-triggered rebuilds and change notification. In each case the question to answer first is not how to detect a change but who is permitted to cause one.

Two practical notes. The cost is real and should be stated rather than hidden: every modification of the shared item obliges re-evaluating the pending conditions of everyone waiting on it, which is a cost proportional to the number of waiters and can be substantial where a coarse mechanism would have been cheaper per operation. That is the honest trade — more work at each write, none at all in between, and exact behaviour. And notice that the entire scheme rests on being able to *check* the restriction rather than merely intend it. If a compiler, a type system or a review tool can confirm that shared state is never touched outside the sanctioned places, the argument holds; if it is a convention, the argument is a hope and the implementation is unsound in exactly the cases nobody thought about.

**Source:** [Communicating Sequential Processes](../works/communicating-sequential-processes-book.md) — the shared storage section of the discussion chapter: the account of conditional critical regions, in which entry to a region is postponed while its condition is false and the condition is retested on completion of each update by another process, followed by the remark that although the overhead may be high because the conditions of all waiting processes must be retested on every exit, they need not be retested more frequently, because restrictions on access to shared variables ensure that a waiting process's condition can change value only when the shared variable itself changes, all other variables in the condition being private to the waiting process which obviously cannot change them while waiting; read together with the earlier note that a compiler can check at compile time that no shared variable is accessed or updated outside a critical region protected by the relevant semaphore.
