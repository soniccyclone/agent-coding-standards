# When state is a participant, reading it is a forced case analysis — and if reading requires acting, a repair obligation too

**Lesson:** Model a stored value as an active party rather than as a location, and there is no longer any operation that returns a value. The holder offers one alternative per possible answer, the reader offers all the answers it is prepared to deal with, and whichever occurs *is* the answer — arriving as a branch already taken rather than as data waiting to be examined. Three things follow immediately. Exhaustive handling becomes structural rather than checked: a reader that omits a possible answer has not left an unhandled case, it has withdrawn a possibility, and if the holder happens to be in that condition the interaction simply cannot proceed. No stale copy of the value can exist, because no copy is ever made. And a holder that has nothing to report — a value not yet assigned — offers nothing at all, so a use-before-initialization stops exactly at the offending step with both parties still standing there, which is close to the most diagnosable failure a system can have, and nobody wrote a check to get it.

The awkward case is when the holder's vocabulary does not contain the question you want answered. A counter offering only increase, decrease, and a signal available precisely when it is empty has no "are you empty" — so the way to find out is to attempt the decrease and the empty-signal at the same time, let the counter select between them, and then, in the branch where it decreased, put back what you took. The observation was made by acting, and the read is not finished until its own disturbance has been undone. That generalizes well past the toy: draining a queue to count it, opening a connection to test reachability, popping to inspect the top — each is a transaction whose restoring step is not cleanup but the second half of the operation. Two disciplines follow. Write the perturbation and its repair as a single unit so that no path can exit through the middle. And recognize that the compound is not atomic with respect to anyone else unless something is made to enforce that, which is exactly the vulnerability this style of read is notorious for.

The design question to carry away is which interrogations a holder ought to offer outright. Every question that can be answered without disturbance, and that you provide as its own alternative, deletes a repair protocol from every client at once instead of once per client. Every question you leave out becomes a small dance that each client reinvents, slightly differently, and those dances are where the defects accumulate. So interface size is not a quantity to be minimized on principle: too small a vocabulary exports complexity to callers in the form of multi-step protocols they must get right individually. The useful test for admitting an operation is not whether it feels primitive but whether clients are already simulating it, imperfectly, out of the operations you did give them.

**Source:** [Communicating Sequential Processes](../works/communicating-sequential-processes-book.md) — the change-of-symbol examples in the concurrency chapter: the Boolean variable derived by renaming from a dispenser, which refuses to yield its value before one has been assigned so that an attempt to fetch an unassigned value deadlocks — described as the kindest failure mode because the simplest postmortem pinpoints the error; the labelled-variable example in which the current value is discovered by letting the variable choose between the two fetch events, that choice determining the user's subsequent behaviour; and the counter example, where a test for zero is made by simultaneously attempting to decrement and to take the zero-signal, with the decremented case immediately restored, and where addition is performed by counting one variable down to zero and then restoring it while incrementing the other.
