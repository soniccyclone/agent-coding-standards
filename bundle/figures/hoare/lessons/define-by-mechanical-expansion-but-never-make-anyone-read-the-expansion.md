# Give a construct its meaning by mechanical expansion into something simpler, then make sure nobody ever has to read the expansion

**Lesson:** There is a cheap and durable way to define a new construct: say what text it stands for in a language you have already explained, and give the rewriting rule precisely enough that anyone could carry it out by hand. Declaring an instance of a structured resource means taking a copy of its text, planting the user's block where the placeholder sits, and prefixing every internal name with the instance's name. Nothing further is needed — no separate semantic apparatus, no new proof rules, no argument that the feature is consistent with the rest of the language, because it is not a new thing at all, only an abbreviation for an arrangement of old things. Nested instances are handled by applying the same rule again. This is how to add power without adding primitives, and it is also how you make the addition auditable, since a reader who doubts your account can simply perform the expansion and look.

The second half of the discipline is the part that gets dropped. The expansion is a definitional device, not a mental model, and an experienced user of the construct should never want to see the expanded form or even think about it. If they do — if debugging, or reading an error message, or reasoning about performance routinely forces someone back into the rewritten text — then the abstraction has failed even though the semantics is impeccable. Meaning-by-expansion buys you a small trusted core; it does not by itself buy you a usable surface. Those are separate properties and they are achieved by separate work: the first by the rule, the second by making sure every tool that talks to the user talks in the source vocabulary rather than the target one.

Worth noticing too what the expansion makes possible beyond mere definition. Because the user's own block ends up textually enclosed by the resource's setup and teardown, there is no arrangement of user code that can skip either — the guarantee is a consequence of the shape of the rewriting rather than of any rule the user must obey. That is the general reason to reach for this technique when the thing being added is a lifetime, a scope, or a protocol with obligations at both ends. And it is also the honest warning: when a notation acquires enough decorations governing what is visible where, the expansions grow large and the explanations get hard to follow, at which point the cheapness of the definition has been paid for out of the user's comprehension.

**Source:** [Communicating Sequential Processes](../works/communicating-sequential-processes-book.md) — the monitors and nested-monitors subsections of the discussion chapter's shared-storage section: the explanation of an instance declaration by a variant of the ALGOL 60 copy rule (copy the monitor text, substitute the using block for the inner statement, prefix all local names with the instance name), the accompanying remark that this makes it impossible for the user process to forget initialisation or the final action on exit, the repeated application of the same rule to derive the meaning of a nested virtual-resource instance, and the following observation that the explicit expansion is shown only for initial explanation because a more experienced programmer would never wish to see it or even think about it.
