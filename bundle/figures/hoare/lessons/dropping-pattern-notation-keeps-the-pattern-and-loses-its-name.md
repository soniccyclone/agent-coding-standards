# Dropping the notation for a pattern keeps the pattern and loses its name: intent moves from the text into convention, where nothing can check it

**Lesson:** A small language earns its smallness by noticing that several apparently distinct structuring devices are all the same underlying mechanism used differently. A chain in which each stage feeds the next, a helper that exists to serve exactly one user, a service shared by many users — all three can be built from nothing but components that take their connections as parameters, plus care about which connection names are shared with whom. Once you see that, the case for providing three separate constructs collapses: they would be three notations for arrangements of one thing, and the arrangements are short. The language stays small, the semantics stays small, and every one of the three patterns remains perfectly expressible.

What is lost is not power but nameability, and it is worth being precise about the consequences rather than treating this as a matter of convenience. When the pattern has its own construct, the intent is in the program text: a reader knows immediately that this component is subordinate to that one, and a tool can enforce what that implies — that no third party holds the connection, that the helper's lifetime is contained in its user's. When the pattern is an idiom, the same facts are true of the program but are stated nowhere. They live in how the connection names happen to have been distributed, which is a global property recoverable only by reading everything, and which the next edit can silently break because nothing declared it. Intent has moved from the text into convention, and convention is exactly the category of thing that cannot be checked.

So the trade to weigh when deciding whether a recurring arrangement deserves its own notation is not power against parsimony — that comparison always favours parsimony, since by construction the idiom already works. It is whether the arrangement carries an invariant you would want stated and enforced. If it does not, leave it as an idiom and keep the language small; naming it would add vocabulary for no guarantee. If it does, the construct is buying you a place to put the invariant, and the right description of its cost is one more thing to learn in exchange for a property a tool can verify and a reader can see locally. This also explains why the same design can be right in one setting and wrong in another: a language whose users are few and expert can afford idioms that a language spanning many teams and many years cannot, because the convention that holds an idiom together is exactly the thing that does not survive scale.

**Source:** [Communicating Sequential Processes](../works/communicating-sequential-processes-book.md) — the occam subsection of the discussion chapter's communication section, which notes that the language provides no distinct notations for the pipes, subordinate processes and shared processes developed earlier in the book, so that all required patterns of communication must be achieved by explicit identity of channel names, aided by procedures declared with channels as parameters; followed by the worked reconstructions of a double buffer, a chain of buffers over an array of channels, a subordinate doubler declared alongside its single user, and an integrator shared among many users via arrays of channels and a replicated alternation.
