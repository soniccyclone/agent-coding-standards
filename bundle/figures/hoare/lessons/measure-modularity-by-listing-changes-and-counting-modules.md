# Measure modularity by listing prospective changes and counting the modules each touches — including the ones that come out badly

**Lesson:** Modularity is usually asserted and rarely evidenced. Make it an evidenced claim by writing down the changes the system is actually likely to face and, for each one, the number of components that would have to be edited. Changing how many of a device there are: one component. Changing how many activities run at once: one. Now the awkward entries, which are the informative ones. Changing the value that separates one job's input from the next: three components, because the value is known to the reader, to the spooler and to the job itself. That asymmetry is the real description of the design, far more useful than any diagram, and it is obtained by an exercise anyone can perform in an afternoon.

The discipline is only worth something if the unflattering entries are published alongside the flattering ones. A design write-up listing the easy changes and stopping there is advertising. The valuable artifact is the second list: improvements everybody wants which this structure will not accommodate without significant rework — here, letting user jobs reach the filing system, making files outlive the job that created them, adding checkpointed recovery, controlling the order in which queued work starts. Naming them does three things. It stops each one being rediscovered as a surprise. It concentrates attention on whether the structural change is worth making now, while the system is small. And it separates "we chose not to support this" from "we did not notice this", which are very different statements about a design and are indistinguishable in silence.

There is a third category worth reaching for, and it is the one people almost never write down: limitations not of your design but of the notation or framework you built it in. If your composition mechanism cannot express something the problem plainly needs — here, a subordinate that shares a resource with its own master — say so explicitly and mark it as an open problem rather than contorting the design around it or pretending the requirement is unreasonable. Recording where the tool ran out is what turns a private frustration into a stated research question, and it is the only way a reader can tell whether an awkward-looking structure was a poor decision or a forced one.

**Source:** [Communicating Sequential Processes](../works/communicating-sequential-processes-book.md) — the operating systems section of the shared resources chapter, whose closing discussion emphasises modularity by noting that large parts of earlier systems were reused in later ones and that every detail decision is isolated within one or two modules, lists the changes that are easy — the number of line printers, of card readers, of concurrent batches — then names a change that is not, the value of the separator card affecting three modules; enumerates four valuable improvements requiring significant structural change, including access to the filing system from user jobs, files persisting between jobs, checkpointing for recovery, and control over the order in which waiting jobs start; and ends by identifying the impossibility of sharing resources between a subordinate and its main process as a limitation of the notation itself, requiring a new definition of subordination and left for future research.
