# Draw the encapsulation boundary so the discipline you need becomes a textual property a machine can check

**Lesson:** Concurrency disciplines are usually stated as obligations on the programmer: take this lock before touching that structure, do not hold two of these at once, never read this field outside a critical section. Obligations of that form are unverifiable in practice, because the evidence for compliance is spread across every site that touches the data and the reviewer must find all of them. The alternative is to choose a unit of program structure such that compliance becomes a property of a single piece of text. Collect the shared state and every operation on it into one named unit; make entry to any of those operations exclusive by construction; forbid the operations to reach any shared state other than their own; and forbid anything outside from touching the state directly. Now the question "is this discipline observed?" is answered by reading one unit, which means it can be answered by a compiler rather than by a habit.

The essential move is not the encapsulation itself but the pairing of the code with the *reason* the code needs protecting. Critical sections scattered through client programs protect the same data, and are exactly as correct, yet they place the burden of finding all of them on whoever needs to reason about the data. The grouped form makes the set of possible interleavings finite and locally visible, which is what converts a class of timing-dependent errors — the kind that appear rarely, under load, in customer environments — into errors that cannot be written down. Note what the extra restriction buys: without the rule that a protected operation touches no other shared state, the local text is no longer sufficient evidence, and the whole property collapses back to a global one.

Generalized, this is a way to choose module boundaries. For any invariant you intend to rely on, ask what unit of text would have to be examined to confirm it holds, and prefer the decomposition that makes that unit small, named and mechanically identifiable. A boundary drawn for tidiness gives you nothing to check; a boundary drawn so that the property becomes syntactic gives you an automatable check, and the difference is visible only when someone is under time pressure and skips the review. The same reasoning explains why a mechanism with this shape can be recommended without qualification while the synchronization primitive layered inside it — whose correct use is not a textual property — remains genuinely uncertain.

**Source:** [Monitors: An Operating System Structuring Concept](../works/monitors-an-operating-system-structuring-concept.md) — the introduction, which requires that only one program at a time execute inside a monitor's procedures, that those procedures access no nonlocal variables other than the monitor's own, and that the monitor's variables be inaccessible from outside, and observes that under these restrictions a guarantee against the more obscure time-dependent coding errors can be underwritten by a visual scan of the program text that could readily be automated in a compiler; also the conclusion, contrasting textual grouping of critical regions with the data they update against critical regions scattered through user programs, and recommending the former without reservation while withholding the same confidence from the condition concept.
