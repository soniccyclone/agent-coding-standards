# A timeout is an admission of unmodelled failure, and in a model without time it can only appear as pure nondeterminism

**Lesson:** Add a timeout branch to a waiting construct and it looks like an ordinary alternative: the system waits for one of several things, and one of the things it waits for is the clock. It is not ordinary, and the way to see why is to ask what it is protecting against. If the other participants behave as specified, the timeout branch is unreachable — someone will eventually arrive. The branch exists precisely for the cases the specification does not cover: a partner that crashed, a link that dropped, a defect that left something in a state your model does not contain. A timeout is therefore not a feature of the design; it is a confession that the design's failure assumptions are incomplete, installed as a runtime hedge against the part you did not model.

That reframing has an immediate consequence for how you reason about the program. In any model that abstracts away from real time — which is most models worth proving things in, because carrying elapsed time makes everything harder — the timeout branch cannot be given its intended meaning, since "long enough has passed" is not a statement the model can express. The most faithful reading available is that the branch may be taken at any moment, arbitrarily, with nothing forcing or forbidding it. So a construct introduced to make behaviour more robust arrives in your reasoning as an unconstrained choice: every timeout you add widens the set of behaviours you must prove things about, and it widens it in the least tractable direction, since the choice belongs to no participant and satisfies no condition. What was meant as a safety measure is, formally, a licence for the system to do the alternative thing at any point at all.

The practical guidance is to keep the two concerns apart rather than to avoid timeouts, which you cannot. Reason about correctness in the timeout-free system, where the interaction protocol either works or does not, and treat every timeout branch as belonging to a separate, explicitly labelled failure-recovery layer whose job is to restore the system to a state the main argument covers. Then two questions become askable that are otherwise buried. First: what invariant does the recovery path re-establish, given that it fires with no knowledge of why it fired? Second: which of my correctness claims survive the possibility that this branch is taken spuriously, at a moment when nothing was actually wrong? A timeout you cannot answer both questions about is not a hedge against failure but a source of it, and the tell is that it appeared in the design at the same time as the deadline rather than at the same time as the failure model.

**Source:** [Communicating Sequential Processes](../works/communicating-sequential-processes-book.md) — the Ada subsection of the discussion chapter, where the delay alternative of the select statement is described as selectable when no other alternative is taken within the given period, its stated purpose being to guard against hardware or software error causing an indefinite wait, followed by the observation that since the book's mathematical model deliberately abstracts from time, such a delay cannot be faithfully represented except by allowing wholly nondeterministic selection of that alternative; read with the adjacent remark that an else clause taken when nothing else is immediately selectable amounts to a zero delay.
