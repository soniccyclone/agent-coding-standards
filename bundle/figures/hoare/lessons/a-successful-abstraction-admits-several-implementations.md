# The mark of a successful abstraction is that it admits several implementations, each efficient in different circumstances

**Lesson:** Abstractions are usually defended on the grounds that they are clean, or that they hide detail, and both defences are weak because they are unfalsifiable. Here is a criterion that can actually be checked: an abstraction has earned its place when the same description can be realized in genuinely different ways, each of which is the right choice under some real constraint, with the results indistinguishable. Consider a computation expressed as stages passing items to one another. On a machine with ample memory, every stage is live at once and items flow between them as they are produced. On a machine without, one stage runs to completion writing everything to storage, then the next starts and reads it back. These are not variants of one implementation; they have different resource profiles, different failure characteristics and different code. The answer they produce is the same, and that is the whole claim.

The value of the criterion is that it tells you when to stop designing. If the description you have written admits only one sensible realization, the abstraction is not doing any work — it is a paraphrase of the implementation, and it will change every time the implementation does. If it admits several, then the choice among them becomes a deployment decision that can be revisited when the constraints change, without touching the description, and one product can span a range of machines rather than being rewritten per machine. Notice that this is a much stronger property than portability: portability asks that the same implementation run in several places, while this asks that several implementations answer to the same description.

Two working consequences. When evaluating a proposed abstraction, deliberately try to construct a second implementation with a different cost profile — not to build it, just to establish that it exists and would be correct. Failure to find one is the signal to look again at what has been abstracted. And when documenting an abstraction, describe it in terms that do not presuppose any of its realizations, because a description containing implementation vocabulary will quietly rule out the alternative that turns out to be needed on the machine you did not anticipate. The description's job is to be the thing all the implementations agree on; anything in it that only one of them needs is a defect.

**Source:** [Communicating Sequential Processes](../works/communicating-sequential-processes-book.md) — the communication section of the discussion chapter, which credits Conway with the idea of the pipe and his proposal to structure a multiple-pass compiler that way, noting that on a machine with adequate main storage all passes are simultaneously active with control transferring along with the messages, while on a machine with less storage only one pass is active at a time and sends its output to a file which the next pass reads, and that the final result of the compiler is exactly the same despite the radical difference in manner of execution — with the accompanying statement that it is characteristic of a successful abstraction in programming that it permits several different implementation methods efficient in differing circumstances, valuable across a computer range offering widely varying store sizes.
