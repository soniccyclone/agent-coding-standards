# Every point where an operation can block is a public boundary, so the invariant must hold there too

**Lesson:** In sequential code the consistency rule for a module is simple: the invariant holds when nobody is inside, and an operation may violate it freely in the middle as long as it restores it before returning. The rule breaks the instant an operation can block, because blocking gives up exclusive occupancy — that is the whole point of blocking, since the condition being awaited can only be brought about by somebody else getting in. So a wait in the middle of an operation is not an internal step; it is an exit and a later re-entry, and the next caller will find the state exactly as the blocked operation left it. Half-finished bookkeeping that would have been invisible in a sequential module becomes the state a stranger reads. The obligation, therefore, is that the invariant holds before every blocking point, not merely at entry and exit, and correspondingly that after resuming you may re-assume the invariant but nothing you had established locally about the state you left.

That reframing gives a constructive procedure for designing anything with blocking clients. Start from the externally visible operations. Choose the concrete state, and write down what relates that state to the abstraction it is representing, so there is something specific to be invariant about. Then enumerate the reasons a caller can be made to wait — one distinct reason per queue, each annotated with the predicate whose truth the waiter is owed — and only then write the bodies. Working in that order, the bodies come out nearly forced: each begins by testing whether its reason to wait applies, and each ends by announcing whichever condition its own effect has just made true. The enumeration of blocking reasons is doing most of the design work, because it is what turns vague concurrency into a fixed, small set of states and handoffs.

Two further consequences are worth carrying away. First, when the count of blocking reasons is not obvious, that is a signal about the design rather than a gap in your notation: reasons to wait correspond to distinct ways the resource can be unavailable, and if you cannot list them you do not yet know what the module is. Second, the properties this method proves and the properties it cannot are cleanly separated. Reasoning about invariants and awaited conditions establishes that whoever proceeds finds the state they expect; it says nothing about deadlock, thrashing, or a participant being overtaken forever. Those are real risks, they remain the designer's responsibility, and they need arguments of a different kind — which is worth saying explicitly rather than letting a successful invariant argument imply safety it never covered.
