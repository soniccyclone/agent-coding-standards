# Efficiency comes from never re-examining the same evidence: build a structure that accumulates what you learn instead of a search that retries combinations

**Lesson:** The naive approach to a combinatorial problem is to try promising configurations, abandon the ones that dead-end, back up, and try again. Edmonds notes that a well-known improvement of exactly this shape was already in circulation for matching, and that it was still not good enough, because backing up and trying again permits the same elements to be revisited in exponentially many combinations, and demands a memory large enough to know when the possibilities are exhausted. His diagnosis locates the cost not in the number of configurations but in the retrying. The fix is structural: grow a single object that records everything discovered so far in a form that makes re-examination unnecessary, so that each element of the input is consumed at most once and never becomes a candidate again.

Two properties make the accumulating structure work, and both are worth stealing directly. The first is that every question the method needs to ask can be answered from the structure without search. Once the tree is grown, the route from any of its vertices back to the root is unique, so recovering a path or identifying a newly found cycle is a traversal rather than a hunt. Uniqueness of paths is what converts a search problem into a lookup, and it is the property to look for when you are designing the intermediate representation. The second is exhaustiveness by construction: a case analysis over what can happen when you look at one more element shows that only a small fixed number of outcomes exist, that two of them consume input, and that the input is finite. The termination argument and the cost bound fall out of the same analysis, and both are stated in terms of how many times each element can be touched.

The consequence for the programmer is a reframing of what "optimize" means. When something is slow, the question is not which operation to make faster but what work is being repeated, and what would have to be recorded so that it need not be repeated. The papers make the accounting explicit at each level: how many trees can be grown, how many elements can enter one tree, how much relabelling a single step can trigger, and then multiply. That accounting is only possible because the design guarantees monotone consumption. A method whose work you cannot decompose into "each thing happens at most this many times" is usually a method that is still retrying something.

**Source:** [Paths, Trees, and Flowers](../works/paths-trees-and-flowers.md) — the critique of the earlier trace-and-backtrack proposal, the theorem that paths back to the root are unique so no trial-and-error retrieval is needed, the five-way case analysis on looking at one more edge, and the explicit level-by-level cost accounting in the digression. Also [Maximum Matching and a Polyhedron with 0,1-Vertices](../works/maximum-matching-and-a-polyhedron-with-0-1-vertices.md), whose opening claims the weighted method avoids testing large numbers of combinations, and [Optimum Branchings](../works/optimum-branchings.md), whose main loop is stated as monotone accumulation into two collections that are only ever added to, with each node admitted once per stage and the partial answer carried forward across collapses rather than rebuilt.
