# Find what your subroutine's answers are invariant under, then use that freedom to keep its input inside the regime where it is cheap

**Lesson:** Most reusable components have a fast regime and a general regime separated by a condition on their input, and the gap between the two is usually large. The shortest-path computation Edmonds and Karp lean on is the textbook case: if every quantity is nonnegative, each element is settled once and the cost is proportional to the structure's size; admit negative quantities and a factor of the node count appears, and admit a negative closed loop and the thing does not terminate at all. The naive way to build on such a component is to accept whichever regime the data happens to land in. Edmonds and Karp instead maintain a per-node offset and hand the subroutine a systematically adjusted version of the data, arranged so the adjusted quantities are never negative. The subroutine then always runs in its cheap regime, and the authors point out — pointedly — that this consideration had been neglected in prior work on the problem.

The move is licensed by an invariance, and identifying the invariance is the whole intellectual content. Adjusting each quantity by the difference of offsets at its two endpoints leaves the total around any closed loop untouched, and changes the total along an open route only by the offsets at its two ends. Since the subroutine is asked to compare routes sharing their endpoints, every comparison it makes is unaffected: the reshaped input is a different input with the same answers. So the general question to ask of any component is not "how do I make this faster" but "what transformations of the input leave the output I care about fixed" — because that set of transformations is exactly the freedom available for steering the input into the good regime, and anything outside it changes the answer and is off limits. A transformation that happens to help but is not covered by such an argument is a bug with good luck.

Two further points make this practical rather than cute. The offsets are not conjured per call; they are maintained across the whole computation and updated by the subroutine's own output, so keeping the precondition true is an ongoing invariant rather than a preprocessing pass — the same discipline as carrying any other invariant alongside a running method. And the precondition being maintained is not arbitrary: it is a meaningful property of the partial answer, so the invariant does double duty as a statement about where the computation stands. When a cheap-regime condition coincides with something you wanted to know anyway, that is a strong sign the representation is right.

The transferable practice is to read the performance documentation of anything you call for the shape of its input, treat that shape as a precondition you are responsible for, and then look for the equivalence under which you may legally reshape data to satisfy it. Sorted input, nonnegative weights, keys within a range, batches within a size limit, values already interned — each defines a fast path, and each has some class of input rewrites that preserve the result. Working out that class once, and maintaining the property continuously, beats paying the general-case cost forever or, worse, reshaping the data on a hunch and quietly changing what the program computes.

**Source:** [Theoretical Improvements in Algorithmic Efficiency for Network Flow Problems](../works/theoretical-improvements-in-algorithmic-efficiency-for-network-flow-problems.md) — the minimum-cost section, which first states the shortest-path routine's cost under nonnegative versus mixed-sign weights (including its non-termination with a negative cycle), then introduces the node-offset reweighting, shows it preserves closed-loop totals and shifts open-route totals only at the endpoints so shortest routes are unchanged, and finally folds the offsets into the main loop so the nonnegativity precondition holds at every call.
