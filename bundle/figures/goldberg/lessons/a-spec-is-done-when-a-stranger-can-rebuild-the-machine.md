# A specification is finished when a stranger can rebuild the machine from it — which means fixing behavior and leaving code shape free

**Lesson:** This book sets an uncommon completeness standard for itself: after describing the language as a user sees it, it turns around and specifies the machine underneath in enough detail that someone with no access to the authors can construct a working one. That standard is what makes the difference between a document that describes a system and a document that *defines* one. And it forces a decision most specifications dodge — what exactly is being fixed. The answer here is behavior only. The specification is written as an unoptimized, deliberately plain implementation, and it says outright that a real implementation will differ in how it dispatches, will inline much of what appears as separate routines, and will keep in registers what the specification refetches. Those differences are not deviations; they are outside what was specified. Fixing observable behavior while explicitly declining to fix code shape is what makes multiple independent implementations possible rather than merely permitted.

The second decision is stranger and more instructive: the machine is specified in the very language the machine implements. That is openly circular, and the book says so, then does two things to keep the circularity from becoming confusion. It states the danger explicitly rather than hoping readers cope — two systems are in play at once, the describing one and the described one, and each has its own methods, its own variables, its own integers. And it enforces a vocabulary split, reserving one set of words for the describing level and another for the described level, so that every sentence in the specification is unambiguous about which world it is talking about. The lesson generalizes past this book: self-description is a legitimate and often the most precise specification technique, and its characteristic failure mode is level confusion, which is defeated by naming discipline rather than by cleverness.

There is a third property worth extracting, about how far down to go. The specification stops at a genuine boundary and states its assumptions about what lies below in plain terms: a processor of unconstrained size, a memory large enough, and then a short list of devices the described behavior actually depends on — a bit-addressable display, a pointing device with a given number of buttons, a keyboard, storage, and clocks at two resolutions. Nothing more is demanded of the hardware, and the natural word size is offered as a convenience rather than a requirement. That is a model of how to write the bottom of an abstraction: name exactly what physical capability the semantics rest on, and refuse to constrain anything else.

A programmer who internalizes this writes interface documents that would let a competent stranger produce a compatible implementation, and audits them by asking two questions — is there anything a reimplementer would have to guess, and is there anything here that is merely how the current version happens to be written. The first kind of gap makes the spec incomplete; the second kind makes it a straitjacket.
