# When a concept keeps showing up only in explanations, promote it to a thing the program can hold

**Lesson:** A recurring move in this book is to notice a concept that exists only in the narration around a program and give it a first-class existence instead. "Where I am in this collection" is the clearest case. A collection can hand out all of its elements, but it cannot serve them one at a time, or interleave reading with writing, without something remembering the progress — and because a collection may be traversed by several parties at once, that memory cannot live in the collection. So position becomes an object in its own right. Once it does, unexpected things unify: an index into stored elements, a seed that computes the next value on demand, and a reference to a node in a linked structure are all the same kind of thing, which is why a random number source and a file turn out to be the same abstraction. Better still, traversal order stops being a property of the data and becomes a property of the traverser, so one structure can be walked in an order its own definition never mentions.

The move repeats at every level of the system, and the pattern is always the same: something that was previously a fact about the machine becomes a value the program can name, pass, and modify. The state of a computation in progress is an object, which is what makes it possible to inspect a halted program, and to give a deferred piece of activity its own life so control structures need no syntax. The identity relation itself becomes addressable, so a structure that must grow can be replaced wholesale while every existing reference to it silently follows — impossible if identity is a property of the runtime rather than of the object graph. The act of sending a request becomes data, so a dispatch table can be a table of request names rather than a switch. And notification of change becomes an explicit registered relationship, distinct from the structural relationships that carry meaning, precisely so that multiple views of one thing can stay coordinated without the thing knowing what a view is.

The general lesson is about where to look for missing abstractions. They are hiding in the sentences you write to explain the code — the shared assumptions, the invariants tracked in your head, the "of course the caller has to remember" clauses. Each of those is a concept the program is using without naming. Reifying it costs a class and buys three things: it can be inspected, it can be substituted, and it can be shared or duplicated deliberately rather than by accident. The concurrency treatment here is the sharpest illustration of the payoff: making the deferred computation and the running process into objects means concurrency needs no new notation at all, because starting one is just a different request to a thing that already exists.

The cost is real and this book pays it visibly: a reification is another class, another vocabulary, another thing to learn. The book's own justification for one such class is telling — it was added to make a single diagnostic message better. That is the right calibration. A concept worth reifying pays back in what becomes sayable and inspectable, not in lines saved.
