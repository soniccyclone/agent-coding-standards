# Identity can stand in for equality only if something guarantees canonicity at construction time

**Lesson:** Comparing two things for identity — are these the same object — is the cheapest comparison available, usually a single word test. Comparing them for equality is arbitrarily expensive, since it means walking whatever structure they have. It is enormously tempting to use the first where you mean the second, and it is correct to do so under exactly one condition: that equal values are guaranteed to be the same object. That guarantee is not a property of the comparison, it is a property of construction, and it has to be established by whatever builds these values, once, for all of them.

The mechanism is a table of everything already built. Before constructing a value, look for one already equal to it; if found, hand back the existing one instead of building another. From then on, the cheap test is exact — two things are equal precisely when they are the same object — and every consumer downstream gets the fast comparison without knowing why it is safe. Note where the cost went: it did not disappear, it moved from every comparison to every construction, which is the right trade whenever things are compared more often than created, and the wrong one otherwise.

The failure mode is partial adoption, and it is quiet. If some values of a type are canonicalized and some are not — a fast path that bypasses the table, a value built by a subsystem that does not know about it, a value deserialized rather than constructed — then identity comparison silently becomes a test that yields false negatives. Two equal things compare unequal, the lookup misses, the branch takes the wrong arm, and nothing anywhere reports an error. Because the guarantee is enforced at construction and consumed at comparison, no local reading of either site reveals the dependency; it lives in the invariant that all constructors respect the table.

The general form worth carrying is that any cheap operation standing in for an expensive one is doing so under an invariant, and the invariant is the real object of maintenance. The same shape shows up in the choice of how to represent a small value: put the value directly in the reference and equal values are automatically identical; put a reference to a stored copy and they are identical only if you are careful never to store the same value twice. Two representations, indistinguishable at the interface, differing in whether an entire class of comparisons is legitimate. When you are choosing a representation, the question is not only what it can hold but which cheap tests it makes truthful.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 5 section 5.3.1 on representing Lisp data: the statement that two data objects are considered the same if their pointers are identical; the account of symbol representation as a typed pointer to a character sequence, with the requirement that two instances of a symbol be recognized as the same by the pointer-identity test, met by having the reader maintain a table of every symbol it has ever encountered, check that table before constructing a new symbol, and return the existing pointer when the same character string is seen again — a process the text names interning; and the footnote on numeric representation, which observes that the decision whether a pointer contains the number itself or the index of a location where the number is stored determines whether the pointer-identity test can be used to test numeric equality, since in the first case equal numbers necessarily have the same pointer while in the second they do so only if the implementation is careful never to store the same number in more than one location. Also the footnote noting that this is the same tagged-data idea used for generic operations in chapter 2, moved down to the primitive machine level.
