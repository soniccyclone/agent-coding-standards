# A component that must see all its input before emitting anything cannot be placed in a loop

**Lesson:** Wiring a system as a graph of components connected by channels is only as expressive as the graph's topology permits, and whether the topology may contain a cycle is decided not by the wiring notation but by a property of the components. If every component is required to consume its input completely before any output appears, then two components in a cycle each wait for the other and nothing in the system can start. Feedback is not a feature you add to such a language; it is a shape the language cannot express at all. Since feedback is what makes a network model anything self-influencing — an integrator in an analog circuit, a controller reading back its own effect, a definition that refers to itself — the restriction is not a corner case.

The enabling property is productivity: a component must be able to emit a prefix of its output from a prefix of its input, including the empty prefix. An integrator has this in the cleanest possible form, because its first output is its initial value, which owes nothing to the signal being integrated. That single fact is what lets the loop turn over: emit one element, which lets the downstream component emit one, which supplies the input the integrator needed for its second, and the cycle bootstraps itself one element at a time. So when you are deciding whether a component may participate in a cycle, the question to ask is not whether it is pure or how it is implemented, but how much of its input it must inspect before it can commit to any of its output. Zero is what buys you feedback. That is the same condition, seen from the component's side, that makes a self-referential definition well founded.

Where this gets uncomfortable is that the property has to be visible at the call, not merely true of the implementation. It is not enough that a component *could* start early; the argument must actually arrive unevaluated, or the caller will have computed it before the call and the cycle will have deadlocked before the component saw it. Push that requirement out to the caller and you have divided your procedures into two kinds, the ones that take suspended arguments and the ones that do not — and the division propagates, because every higher-order procedure that could be applied to both kinds must now exist twice. A distinction in calling convention is more contagious than a distinction in data, since it cannot be hidden behind an interface; it is part of how the interface is invoked.

The authors face the obvious remedy squarely and decline it. Making every argument suspended by default erases the two classes and makes the machinery uniform, and if the only thing you cared about were networks of this kind it is what you would do. But an argument whose evaluation happens at an unpredictable moment cannot safely be an argument whose evaluation has effects, so uniform suspension is bought by giving up assignment, mutation, and ordered input and output — and the authors say plainly that nobody has found how to have both. Note the shape of that conclusion, which is the part worth carrying: a local convenience (one hidden suspension inside one constructor) was pleasant, generalizing it to a language-wide rule was principled, and the generalization collided with an unrelated feature that the local version had left alone. Uniformity is not free just because it removes a distinction.
