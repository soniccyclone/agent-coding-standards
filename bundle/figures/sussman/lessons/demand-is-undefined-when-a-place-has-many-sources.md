# Demand-driven evaluation silently assumes one producer and a final answer; drop either and pulling has no definition until interest itself becomes data

**Lesson:** Computing only what somebody asked for is such a familiar optimization that it is easy to treat as universally available — laziness, pull-based pipelines, on-demand recomputation. It is not universally available, and the two conditions it depends on are worth naming because they are invisible while they hold. First, demanding a value requires knowing whom to ask, which is trivial only because the usual arrangement gives each location exactly one producer. Where a location can be fed by several contributors, a demand has no unambiguous destination, and nothing in the request itself says which contributors are the right ones to wake. Second, demanding a value requires knowing when the answer has arrived, which is trivial only because the usual arrangement makes a produced value final. Where contributors are permitted to supply partial knowledge and refine it later, no arriving answer announces itself as the last one, so the pull has no termination condition; the only genuinely unrefinable outcome is a contradiction, which is not the outcome you were hoping to wait for.

Diagnosing it that way is more useful than concluding that the two designs are incompatible, because it converts a stuck point into a specification. If demand cannot be a control operation, it has to become a datum: a request that says what is wanted, travels through the same structure that everything else travels through, and is combined at each location by the same rules that combine ordinary knowledge. That reframing also pays a dividend the original scheme could never offer. Once a system admits that knowledge comes in parts, a request need not be for a whole value at all — it can name a region of the information space, and the most valuable form turns out to be exclusion rather than selection: give me whatever can be concluded without relying on this particular assumption. A system that can express that request can decline to compute every conclusion whose justification would have contained the excluded assumption, which is a kind of thrift no whole-value demand can express, since a whole value has no parts to leave out.

The generalizable habit is to check, whenever you reach for demand-driven anything, whether the substrate still supplies the two preconditions. Multiple writers to a shared location, incremental refinement, eventual convergence, monotone accumulation — each of these individually breaks one of the assumptions, and systems that mix them with a pull discipline usually do so by quietly reintroducing single-producer, final-value behaviour at some boundary, which is where the surprises then live. Either restore the preconditions honestly at that boundary, or promote demand from a mechanism into a message and let it be subject to the same laws as everything else the system carries.

**Source:** [The Art of the Propagator](../works/the-art-of-the-propagator.md) — the closing section on remaining work, which asks what normal order would mean for a network in which propagators pull rather than push, identifies as the novel problem that information can enter a location from multiple sources with no way to know in advance which are right to pull from, adds that because sources may produce partial information and refine it later there is no way to know when to stop pulling apart from the arrival of a contradiction, and then observes the compensating opportunity: since partiality is acknowledged by the architecture, one may pull on a portion of the information space — for instance only answers not requiring some premise, letting computations whose supports contain it be skipped — and speculates that such requests could be represented explicitly and propagated as a kind of information in their own right.
