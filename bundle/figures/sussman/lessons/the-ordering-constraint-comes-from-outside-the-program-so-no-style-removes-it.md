# The ordering constraint is imposed from outside the program, so no programming style can remove it

**Lesson:** A style that forbids mutation looks like it should dissolve concurrency problems, and for a long stretch it does. Then you reach the point where two independent agents must act on the same thing, and the difficulty comes back in full, wearing different clothes. Two parties sharing one account, in a style with no objects to send requests to, must have their request sequences combined into one before the processing function can be applied. The combining step is where everything that was supposedly eliminated reappears.

The naive combination — take one from each side in turn — is not merely inefficient, it is wrong, because it makes one party's ability to act depend on the other party acting. Someone who touches the account once a year would hold the other party's every subsequent request hostage. So the combination has to be responsive to when requests actually occurred, which means it is constrained by real elapsed time and not by anything visible in the two sequences themselves. And the reason it is so constrained is entirely outside the program: the two parties can meet in the world and compare notes, and whatever they agree happened before the meeting must have been processed before whatever they agree happened after. The consistency requirement is a fact about the parties' shared reality, not about the code, which is exactly why rewriting the code in a different style cannot repeal it.

Follow that to its formal consequence, which is the sharpest part. Under this requirement the combination is not a function of its two inputs. The same pair of request sequences admits several acceptable outputs, and which one is right depends on timing information that does not appear in the inputs. Something the program must perform is therefore genuinely a relation and not a mapping — non-determinism is not sloppiness in the implementation or a failure to specify hard enough, it is essential, forced by the problem. A style built on the premise that every procedure denotes a function has, at this exact point, run out of premise.

The general lesson for anyone choosing an architecture on the promise that it makes a class of problems disappear: check whether the problem originates inside the system or is imposed on it from outside. Difficulties that are artifacts of a mechanism can be removed by changing the mechanism, and the shift away from mutable state removes a great many of them honestly. Difficulties that encode a requirement of the surrounding world survive every rewrite and simply relocate to whatever seam is left. Look for that seam early, because it will end up carrying the coordination cost the rest of the design was built to avoid, and it is usually a component nobody thought of as interesting — here, a merge.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) - chapter 3 section 3.5.5's discussion of a joint bank account under the stream formulation, which models the shared account by merging two parties' streams of transaction requests and feeding the result to a single account process, rejects strict alternation on the ground that a rarely acting party would block the other from issuing a second transaction, argues that however the merge is implemented it must interleave the two streams in a way constrained by real time as perceived by the two parties in the sense that if they meet they can agree which transactions were processed before the meeting and which after, identifies this as precisely the same constraint that forced explicit synchronization for objects with state in section 3.4.1, concludes that the need to merge inputs from different agents reintroduces the very problems the functional style was meant to eliminate, and notes in a footnote that since more than one interleaving is generally acceptable the merge is technically a relation rather than a function and illustrates the nondeterminism that is essential when dealing with concurrency.
