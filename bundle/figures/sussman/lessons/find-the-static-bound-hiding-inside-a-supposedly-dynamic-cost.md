# When a cost is believed to grow with runtime behaviour, look for the semantic rule that pins it to a static property of the text

**Lesson:** Folklore about performance survives because it is never stated precisely enough to be checked. The received wisdom that resolving a name through a chain of naming contexts is expensive rests on an unexamined picture in which the chain grows as the program runs, so that a deeply recursive computation must search a correspondingly long chain. Adopt the rule that a function carries the naming context in force where it was written rather than where it is called, and the picture is simply false: the context consulted at any moment contains entries only for names bound by constructs lexically enclosing the expression under evaluation, so its depth is bounded by a number you can read off the source text and which no amount of recursion increases. The cost of a lookup is then a distance in the program, not a distance in the program's history — and anything determined by the text is available to a compiler, which can replace the search with a precomputed position. A rule adopted for semantic reasons, to keep substitution honest and references transparent, turned out to hand over a static bound on a cost people had assumed was dynamic.

The honest version of the argument also names what the rule costs. Because functions may escape the constructs that created them, the naming contexts cannot be a single stack reused in place; they form a tree, and a tree cannot be indexed by arithmetic the way a flat frame can, so reaching a known position still means walking there. The right conclusion is neither the folklore's "too expensive" nor a defensive "free," but a specific statement: a short traversal whose length is a compile-time constant, paid in exchange for the ability to return a function that outlives its birthplace. Design arguments become tractable at exactly the moment costs are stated this precisely, and stay unresolvable as long as both sides are gesturing at magnitudes.

The same imprecision hides a second confusion worth separating out. Retaining many contexts is not the same phenomenon as any one context being deep, and a recursive computation exhibits the first while the lexical rule forbids the second. Each pending level must remember which context to resume in, so the count of remembered contexts tracks the depth of pending work — whether the remembering is done by the evaluator on the programmer's behalf or done explicitly by a program that passes along what to do next. An iterative computation remembers nothing, because it has nothing pending. Diagnosing a memory cost therefore requires asking which quantity is actually growing: the size of an individual structure, or the number of structures nobody is finished with yet. Confusing the two produces optimizations aimed at the wrong thing.

**Source:** [Scheme: An Interpreter for Extended Lambda Calculus](../works/scheme-an-interpreter-for-extended-lambda-calculus.md) — the consequences drawn immediately after the closure discussion in the implementation-issues section: that the naming context can never be deeper than the lexical depth of the expression being evaluated even under recursion, that lookup time therefore depends only on lexical distance and can be resolved at compile time, that the tree shape forced by upward-escaping functions still requires traversal, and that recursive and continuation-passing styles accumulate saved contexts per level while iterative style accumulates none.
