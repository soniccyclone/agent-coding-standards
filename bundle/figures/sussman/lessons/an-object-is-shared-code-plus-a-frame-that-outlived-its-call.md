# An object turns out to be shared code plus a frame that outlived the call that made it

**Lesson:** The environment model is introduced to explain assignment, and it explains objects as a side effect. Two rules do the work: a procedure is created only by evaluating a lambda, and it consists of that text plus a pointer to the environment where the evaluation happened; applying it builds a fresh frame for the parameters whose enclosing environment is the one the procedure carries, not the one the call came from. Nothing in either rule mentions state, encapsulation, or objects. Run a maker procedure twice and you get two procedures with byte-identical code whose only difference is which frame they point at, and that difference is the whole of their independence.

Watch what survives a call and the notion of "an object" resolves into ordinary lifetime bookkeeping. The frame binding the argument of a particular withdrawal is created, used, and abandoned, because when the call finishes nothing points at it. The frame created by the maker is not abandoned, because the procedure it produced points at it, and that procedure is still reachable. The state is not stored anywhere special. It is in a frame that happens to be kept alive by a reference, and that is the entire mechanism behind "this object remembers things between calls."

The lesson worth taking is about how much can be derived rather than designed. Instance state, instance independence, encapsulation of that state against outside access, and shared behaviour across instances all fall out of the two rules above with nothing added — the book gets objects without ever introducing a class, an instance, or a field. When a facility appears to need dedicated machinery, it is worth asking whether some mechanism you already have would produce it as a consequence, because the derived version costs no new concepts and its odd cases are decided by rules you already understand rather than invented one at a time.

The dual reading is a debugging instrument. If an object's behaviour depends on which frame it captured at creation, then two objects that should be independent and are not have captured the same frame, and two that should share and do not have captured different ones. That reframes a large class of bugs — a callback closing over a loop variable, handlers sharing a config that was meant to be per-request, a factory returning things that alias when they should not — as one question with one answer: what environment existed at the moment this thing was made? The authors also note that whether the two objects share one physical copy of the code is an implementation detail, which is the right way round. Identity lives in the captured environment; the code is incidental.
