# An abstraction costs what it costs because of when its dispatch resolves, not because of how it was expressed

**Lesson:** Defining data as behaviour — an object is a procedure, and the only thing you can do with it is ask it something — is generally treated as an elegance you pay for at run time. Reading a field becomes a call, a comparison of the request against the ones understood, and a branch, where a conventional record would have been one fetch. The reasoning is wrong, and seeing why is more useful than the conclusion. The expense is not created by expressing data as behaviour; it is created by resolving the dispatch at run time. Every step of the apparent overhead is a decision about a value that is available earlier, and once the caller's request and the object's origin are both known statically, entirely ordinary optimizations — substituting a procedure's body at its call site, folding a comparison of two known constants, deleting the branches that can no longer be taken — grind the whole construction down to the single fetch, with nothing invented for the occasion.

What that argument demands is knowledge of which procedure a given object is, obtainable either from a declaration or from analysis of how values flow. And that requirement is worth staring at, because it is the same requirement conventional systems satisfy by storing a tag. The bookkeeping that identifies which behaviour an object carries is what a type tag has always been; a system that reaches the code by following a pointer, and a system that reaches it by consulting a few bits, differ in encoding and not in kind. So the objection that behaviour-as-data costs an extra word per object answers itself: the word is the tag, other systems have always paid for it, and a compiler free to choose the encoding can compress or eliminate it exactly as those systems do.

The transferable move is a reframing in both directions. Treat data as behaviour and you get integrity for free, because there is no underlying representation available to be reached around — the escape hatch that abstract-data-type mechanisms keep having to define, and then having to restrict, does not exist when there is nothing behind the procedure. Treat behaviour as data and the implementation stops being frightening, because the closures produced by one piece of code are just a record layout, with all of them sharing a type. The same objects viewed either way are what let an abstraction be both airtight and cheap. And the general rule survives far past this example: when an abstraction seems to cost something, locate the decision being made at run time and ask what would let it be made earlier, because that, and not the abstraction, is what you are actually paying for.

**Source:** [Lambda: The Ultimate Declarative](../works/lambda-the-ultimate-declarative.md) — the procedural-view-of-data-types section, which walks a procedurally defined pair through procedure integration, constant folding and dead-code elimination down to a single machine instruction given knowledge of which closure the value is, notes that this knowledge comes from declarations or global flow analysis, argues that the pointer to code in a closure is playing exactly the role a type tag plays and can be encoded as cheaply, and observes that the approach removes the need for the representation-lowering escape mechanism that earlier abstract-data-type designs had to introduce and then restrict.
