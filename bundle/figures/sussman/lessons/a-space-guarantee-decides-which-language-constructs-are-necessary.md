# A space guarantee in the implementation decides which constructs the language needs at all

**Lesson:** Some implementation properties are optimizations, meaning that without them the same programs run slower. A few are not optimizations at all, because without them a whole class of programs stops being expressible and the language has to grow a construct to compensate. The clearest case is what happens when a call in final position does not need to preserve anything: with that property, unbounded repetition is available through the calling mechanism alone, and no looping construct is needed for anything. Without it, every repetition consumes space in proportion to its length, unbounded repetition eventually fails, and the language must supply a separate iteration facility whose entire reason for existing is to avoid the calling mechanism. One property of the implementation is the difference between a language with one control mechanism and a language with two.

The way the property is lost is instructive because it looks like tidiness. Handling every element of a sequence the same way — preserve context, evaluate, restore, advance — is uniform, obviously correct, and shorter to describe than a version that treats the final element specially. Both give identical answers on every program. The uniform version merely does some preservation that turns out to be unnecessary, and that unnecessary preservation is what forces a return, and the return is what makes the space accumulate. A change with no effect on any result destroys a property the language's users will design around.

This is worth generalizing into a habit of classifying implementation properties by whether anything above them can be written differently because of them. A property that only changes speed can be traded away against complexity. A property that changes what programs are possible is part of the language's specification whether or not anyone wrote it down, and it must be stated, tested, and defended against exactly the kind of harmless-looking uniformity that removes it. The users cannot discover its absence by reading; they discover it when a long-running program fails.

There is a second point about where such a property should live. Applied by a compiler, it holds for the code that compiler processed. Built into the evaluation mechanism itself, it holds everywhere in the language, uniformly, including in code nobody analyzed and in code generated at runtime. That difference matters for anything programmers are entitled to rely on: a guarantee available only where a particular tool ran is not a guarantee, it is a likelihood, and a likelihood is not something you can build a language's control structure on top of.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 5 section 5.4.2, on sequence evaluation and tail recursion: the observation that the syntactically recursive iterative square-root procedure requires no information to be saved in passing from one call to the next, that an evaluator able to run such a procedure without increasing storage is called tail-recursive, and that the metacircular evaluator of chapter 4 does not settle the question because it inherits its state-saving from the underlying system; the explicit-control evaluator's handling of the final expression of a sequence, which restores the pending return point before transferring to evaluation so that nothing is placed on the stack; the alternative formulation given immediately afterwards which treats every expression in a sequence identically, is noted to give the same value for every expression, and is called fatal to the property because the useless saves must now be undone by returning, so that the saves accumulate through a nest of calls and an iterative process requires space proportional to its number of iterations; the concluding contrast that with the property an endless loop can be written using only the procedure-call mechanism while without it expressing a true iteration requires some control mechanism other than procedure call; and the footnote observing that compilers commonly apply this transformation when compiling a procedure ending in a call, whereas building it into the interpreter provides it uniformly throughout the language.
