# An enumeration of an unbounded space is correct only if every element has a finite arrival position

**Lesson:** Combining two collections is a decision nobody thinks about while the collections are finite, because every reasonable combining rule produces the same set and the only difference is order. Make one of them unbounded and the choice stops being cosmetic and becomes the difference between a correct program and a program that silently omits most of its answers. Concatenation is the natural default and it is fatal: it commits to exhausting the first source before touching the second, so if the first source never ends the second is unreachable, and the elements it holds are not delayed, they are absent. The failure produces no error and no hang. It produces plausible output forever, drawn from a fraction of the space you asked about.

The correctness condition is worth stating in the abstract, because it is the thing you check and not the thing you code. For a combination over unbounded sources, there must exist a function from an element's coordinates in the sources to its position in the output — that is, every element must be assigned a finite index at which it will have arrived. Interleaving satisfies this and concatenation does not, and that is the whole argument. This is not a statement about fairness in a scheduling sense or about performance; it is a statement about whether the enumeration denotes the set it claims to denote. Notice also that the condition is compositional in a fragile way: a recursive construction that interleaves at each level can still starve if the recursion is arranged so that a sub-enumeration must be entered before any of it can be produced. Getting the local rule right is not sufficient; the recursive decomposition has to leave something emittable at every level.

The second half of the idea is that having secured arrival, you can go on to choose *which* arrival order, and this is where the technique becomes a design tool rather than a repair. Interleaving gives an order that is correct but arbitrary — nothing about position in the output means anything. Replace it with a merge governed by a weight assigned to each element, and the output becomes sorted by that weight, on a space that could never have been sorted because it was never finite. That changes what questions the enumeration can answer. Asking for numbers expressible as a sum of two cubes in two ways is intractable against an arbitrary order and trivial against a weight-sorted one, because "two ways" becomes "adjacent entries with equal weight" — a local test on a window of size two. The weight must increase monotonically as you move outward along either coordinate, which is exactly the condition that makes each output position decidable from a finite prefix.

The transferable pattern is that unbounded search spaces should be exposed as ordered enumerations, and the order should be chosen so that the property you are hunting becomes local. Correctness of arrival first, then the ordering that turns a global search into a sliding window.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) - chapter 3 section 3.5.3's subsection on infinite streams of pairs, which decomposes the stream of pairs drawn from two infinite sources into the first pair, the rest of the first row, and the recursively generated remainder, rejects the append analog because it would run through all pairs with the first coordinate fixed and never reach the others, gives the interleave procedure that alternates between two sources so that every element of the second eventually appears, and states in a footnote the precise required property that there be a function mapping the indices of the two sources to the position of the corresponding pair in the output; together with Exercise 3.68, where dropping the separated first element makes the recursion unproductive, and Exercises 3.70 and 3.71, which replace interleaving with a merge ordered by a weighting function required to increase along rows and columns, and use the resulting sorted enumeration to find Ramanujan numbers by looking for consecutive pairs of equal weight.
