# Bookkeeping attached to an aggregate can never be finer than the aggregate, and its errors are silent because the answers stay right

**Lesson:** Attach an annotation to a value and you have implicitly asserted that the annotation applies to the value as a whole. When the value is really a conjunction of independently established parts, that assertion is false, and the annotation is forced to over-report. A range with an upper and a lower limit is the clean example: the two limits are typically established by different sources and refined at different moments, so one record of what the range depends on has to be the union of what each side depends on. Now suppose contributions arrive in sequence, and a later contribution supersedes what an earlier one established on one side while adding nothing on the other. The superseded source is still in the union, so the final answer claims to rest on something it does not rest on — not through a bug in the merging logic but because there was no place to record the distinction. The remedy is granularity: annotate the parts that are independently established, not the composite. The same reasoning extends to any compound value, where per-component records, plus a separate record for believing the thing is that shape at all, are typically much smaller than one record for the whole and are also correct.

The reason this class of defect deserves special attention is that it does not announce itself. The over-reporting is conservative — it never omits a genuine dependency, only includes spurious ones — so every answer the system produces remains correct, and only the explanations are wrong. Nothing crashes, no test comparing outputs fails, and a reviewer reading the code finds each step locally defensible. Metadata is exactly the part of a system that ordinary verification does not check, because its correctness is a claim about the relationship between the answer and the inputs rather than about the answer.

So the discipline has to be active. The available test is to withdraw the suspect input and observe whether the answer changes: if it does not, the dependency was spurious and you have both diagnosed the over-reporting and obtained the correct account. That test is worth building into the system rather than performing by hand, and it generalizes past provenance to every derived summary a system maintains about itself — cache invalidation sets, change-impact estimates, permission derivations, alert-cause attributions. All of them are prone to being safe and wrong, all of them go unchecked by tests aimed at outputs, and all of them can be probed the same way: remove a supposed cause and see whether the effect actually moves.

**Source:** [The Art of the Propagator](../works/the-art-of-the-propagator.md) — the overlap anomaly in the provenance subsection, where three intervals arriving in sequence leave an irrelevant premise in the justification because it was superseded by a later one, which the authors note actually occurs in their own worked example; the subsequent demonstration that withdrawing belief in the suspect measurement leaves the answer unchanged while producing accurate dependencies, after which the system retains the improved account and discards the ones it obsoletes; and the closing discussion's observation that maintaining separate justifications for the components of a compound value, and specifically for the two bounds of an interval, would have eliminated the anomaly.
