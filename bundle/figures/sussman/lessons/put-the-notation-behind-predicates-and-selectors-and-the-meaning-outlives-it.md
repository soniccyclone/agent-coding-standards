# Put the notation behind predicates and selectors, and the rules of meaning outlive any notation

**Lesson:** Every program that interprets structured input contains two things that are easy to write as one: rules about what the input *means*, and knowledge of how the input is *written down*. The habit of treating them as one is nearly invisible, because the natural way to ask whether something is an assignment is to check whether it starts with the assignment keyword, and the natural way to get its target is to take the second piece. Do that and the meaning rules have been dissolved into the notation. Change the notation and there is nothing left to keep.

Separating them requires no cleverness, only discipline: for each syntactic category, one predicate that answers whether an input belongs to it and one selector per part that pulls that part out, and nothing else in the program may look at the input's shape. What is left over — the code that decides what to do once the category is known — turns out to be a complete statement of the language's semantics that mentions no notation at all. The evaluator's rules for what a conditional means, what applying a procedure means, what a definition does to an environment, survive verbatim across an arbitrary change of surface form. That is the practical claim and it is a strong one: the same interpreter serves a different concrete language when supplied with a different set of classification procedures, and the interpreter's own text is not edited.

The generalization is that any recursive traversal of structured data has this decomposition available, and the authors point directly at the parallel between an evaluator and a symbolic differentiator to make the point that it is not special to languages. The traversal's shape — operate on the parts, combine according to the category — is identical in both; only the categories and the combining rules differ. So when writing anything that walks a tree of expressions, configuration, documents, protocol messages, the question to ask is which lines would have to change if the encoding changed, and to push every one of them behind a name.

Two things worth noticing about what this buys and what it does not. It buys genuine independence, not merely tidiness: the semantics can be reviewed, argued about, and reused without anyone knowing the encoding, which is the difference between a specification and an implementation detail. But the boundary must be honest about its own status — the authors mark certain look-alike helpers as deliberately *not* an abstraction, just mnemonic names for list operations, so that nobody reasons about them as though they carried a guarantee. A named accessor that is not part of the barrier is worse than a bare operation, because it invites reliance on a promise nobody made.
