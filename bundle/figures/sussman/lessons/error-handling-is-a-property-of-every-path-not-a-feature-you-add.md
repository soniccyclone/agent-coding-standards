# Error handling is a property of every value-producing path, which is why it cannot be added afterwards

**Lesson:** A system built without a story for failure does not have a hole in one place; it has the absence of a convention in every place that produces a value. Adding the story later therefore is not a feature but an edit to each of those places, and the effort is proportional to how much of the system exists rather than to how complex the error mechanism is. Faced with that, teams usually do the cheap thing available at the boundary — let the layer underneath abort whatever is running — which means a fault in something a user supplied takes down the machinery that was supposed to be supervising it. That is the same relationship as a user program crashing the operating system, and it is worth recognizing as such rather than as an inconvenience, because it means the system had no supervisory role at all.

Two distinct sub-problems hide under the single word, and they have different costs. Failures the machinery detects itself are the tractable half: the detecting operation can return a distinguished result that no legitimate value could be, and every caller that might see it is edited to test for it and divert. The technique is sound and its precondition is absolute — the distinguished result must be outside the entire space of ordinary results, and if it is representable as a legitimate value then some day it will be one, and the check will fire on valid data. The cost is that you must find every place the check belongs, and finding them is not a search you can automate in a system where the convention did not previously exist.

The harder half is failures inside the primitives, the operations you did not write and cannot instrument from outside. There the only real answer is that each one validates its own arguments before proceeding — a check on every operation, on every call, forever. That is a cost paid by every correct program to protect against incorrect ones, it is unavoidable if the system is to survive its users' mistakes, and it is precisely the cost that gets skipped when the priority is raw speed. Knowing that this is the trade being made is more useful than any opinion about which side to take: the question is whether the system is supposed to outlive the failure of what it is running.

There is a corollary about recovery that is easy to omit. An aborted computation leaves the machinery in whatever state it had reached, so any shared structure it was partway through — a working area, a partially built result, an unwound stack — is now inconsistent, and the path back to a usable state must explicitly reset it rather than assume it is clean. A system that can report an error but cannot restore its own invariants has caught the error and remains broken, which is often worse than crashing, because it continues.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 5 section 5.4.4, the explicit-control evaluator's handling of errors, which catches only unknown expression types and unknown procedure types while all other errors escape to the underlying system; Exercise 5.30, which notes that this is analogous to the computer crashing when a user program makes an error, calls building a real error system a large project, and splits it in two: errors arising within the evaluation process, such as reference to an unbound variable, to be caught by having the lookup operation return a distinguished condition code that cannot be a possible value of any user variable and by finding and fixing all the places in the evaluator where a test for it is required, which the exercise says is lots of work; and errors signalled by primitive procedures such as division by zero or taking the first component of a non-pair, described as much worse and answered by the observation that in a professionally written high-quality system each primitive application is checked for safety as part of the primitive, with every call to a selector first verifying its argument's type. Also the same section's note that the driver loop reinitializes the stack on each interaction because it might not be empty after an error has interrupted an evaluation, and the footnote comparing the unhandled case to the crash behaviour of conventional compiler-based language systems.
