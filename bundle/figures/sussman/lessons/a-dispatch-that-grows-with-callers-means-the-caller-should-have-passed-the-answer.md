# A dispatch whose arms grow with the number of callers means the caller should have passed the answer, not a token for it

**Lesson:** Sharing one piece of machinery among several users creates a question the machinery cannot answer on its own: when it finishes, which user should it go back to. The first solution anyone reaches for is a token. Each user deposits a distinct marker before handing off, and the shared piece ends with a chain of comparisons on the marker, one arm per user. This works, and it is worth noticing exactly why it is unsatisfying: the chain of comparisons grows with the number of users, so every new user edits the shared piece, and the shared piece accumulates knowledge of everyone who calls it — which inverts the dependency you were trying to establish by sharing it in the first place.

The fix is not a better encoding of the token but the elimination of the indirection. The token is a name for a destination; the comparisons are a lookup from name to destination; the lookup is only necessary because destinations are not things you can hold. Make them things you can hold — let the destination itself be a value that can be stored and later acted on — and the caller deposits the destination rather than a name for it, the shared piece ends by simply going where it was told, and it contains no reference to any caller at all. Adding a user becomes a change at the new user's site only. This is the difference between a token that must be interpreted and a value that already is what it denotes, and it is the same move whether the destination is a return address, a callback, a queue, a continuation, or a handler.

The price is explicit and should be acknowledged: the substrate must be extended. Somewhere, a kind of thing that was previously only writable in the text — a location in the program — has to become storable and usable at runtime. That is a genuine addition of power, not a refactoring, and it is exactly the kind of addition worth making, because it is one capability that removes an unbounded family of dispatches rather than a feature that serves one case. A large fraction of the moves that simplify a system have this shape: promote one thing to first-class status and a whole category of bookkeeping stops existing.

The diagnostic to carry away is the growth rate. A conditional whose number of arms is fixed by the problem is fine. A conditional whose number of arms equals the number of places that call the enclosing code is a report that a value is being passed by name when it should be passed directly, and it will keep growing, and each addition will touch shared code that had no business knowing about the addition. Whenever you find yourself adding an arm to such a dispatch, the question is what would have to become a value for the dispatch to disappear.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 5 section 5.1.3 on subroutines, which develops the problem in stages: two separate copies of the same computation with duplicated data-path components; then shared components with two controller sequences differing only in their entry labels; then a single shared sequence entered from both sites, with a distinguishing constant placed in a dedicated register beforehand and a test on that register at the end selecting which of the two return points to branch to; the observation that this is reasonable for small problems but awkward with many call sites, since deciding where to continue would require tests and branches for all the places that use the subroutine; and the resolution, described as a more powerful method, of having the register hold the controller label itself, which requires a new kind of connection between data paths and controller so that a label can be assigned to a register as a special kind of constant and a jump can continue at the entry point named by a register's contents rather than only at a literal label.
