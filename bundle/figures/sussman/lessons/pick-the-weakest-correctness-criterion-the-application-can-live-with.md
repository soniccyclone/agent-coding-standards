# Concurrency correctness is a graded scale; pick the weakest rung the application can live with

**Lesson:** Asked what it means for a concurrent program to be correct, the authors decline to give one answer and lay out three, from strongest to weakest. The strongest forbids any two operations on shared state from overlapping — easy to state, and for a distributed banking system it would mean one transaction at a time worldwide, which they call both inefficient and overly conservative. The middle one requires only that the outcome match what *some* sequential order would have produced, which permits genuinely simultaneous execution wherever the touched state does not overlap. The weakest imposes nothing at all: a diffusion simulation in which each cell repeatedly averages itself with its neighbours converges to the same answer regardless of the order operations happen in, so there is nothing to protect.

The framing is the lesson. Correctness under concurrency is not a property a program has or lacks; it is a criterion you choose, and every rung you climb buys safety by spending parallelism. Choosing the top rung by default is the common failure — a global lock, a single-threaded write path, a serialized queue for everything — and it is not conservative in the good sense. It is a decision to give up the speed advantage the concurrency was for, made without examining whether the application needed the guarantee.

Two features of the middle rung repay attention because they are routinely misread. It does not require the processes to actually run in sequence, only that the result be one a sequence could have produced — so the implementation is free to overlap anything whose overlap is undetectable. And it does not pick out a unique answer: with a deposit and a proportional withdrawal running concurrently, more than one final balance is legitimately correct, because more than one sequential order exists. A concurrent program is therefore not described by a function to a value but by one to a set of possible values, and a test asserting a single expected outcome is asserting something stronger than correctness.

The bottom rung is the one worth hunting for, because it is where concurrency is free. It is available when the operations have a structure that makes order irrelevant — averaging converges from any schedule, as do accumulating a commutative aggregate, adding to a set, or taking a maximum. Before reaching for a mechanism, the question is whether the update can be reshaped into one of those forms, since an operation that does not care about order needs no protection and scales without coordination. Reach for serialization when the operation genuinely reads shared state and writes a value derived from it — and then scope it to the state involved, one lock per account rather than one per bank, so that everything not actually shared stays concurrent.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) - chapter 3 section 3.4.1's subsection on correct behaviour of concurrent programs, which presents the stringent restriction that no two operations changing shared state may occur at once and calls it inefficient and overly conservative for distributed banking, illustrates with the diagram of a joint account and a private account that some pairs of operations may safely overlap, states the weaker requirement that a concurrent system produce the same result as some sequential order while emphasizing that processes need not actually run sequentially and that more than one correct result may exist (with the concurrent deposit and half-withdrawal yielding two legitimate balances), adds the footnote that concurrent programs are inherently nondeterministic and described by functions whose results are sets of possible values, and gives the diffusion simulation whose repeated local averaging converges to the right answer independent of operation order so that no restriction on concurrent use of the shared values is needed; together with section 3.4.2's serialized bank account, where each account holds its own serializer so that transactions on different accounts proceed concurrently.
