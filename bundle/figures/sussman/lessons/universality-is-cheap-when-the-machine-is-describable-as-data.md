# Universality is cheap in a medium where machines are describable as data

**Lesson:** A program can be read as the description of a machine — a wiring of parts that decrement, compare, multiply, with a switch and, in a recursive procedure, a copy of the machine inside itself. Under that reading an evaluator is not one more machine among these. It is a machine whose input is a description of a machine, and which then behaves as the described machine behaves. That is the whole content of universality, and everything usually said about it follows from that one sentence.

The consequence worth internalizing is that the reach of an evaluator is not bounded by the language it directly understands, because one of the machines it can be handed is another evaluator. Feed it a description of an evaluator for a second language and it becomes an evaluator for that language, and thereby for every machine describable in it. So any evaluator can emulate any other, and what is computable in principle stops being a property of the language, the machine, or the notation — leaving a notion of computability that belongs to none of them. That is a statement about limits, and it is the reason arguments about which language is more powerful are, at this particular level, empty.

Then the observation the authors linger on, which is the one that transfers to engineering rather than to theory. Ask what a universal machine costs in another medium: a circuit that accepts a signal encoding the plans of some other circuit and thereafter behaves as that circuit. Such a thing is nearly unimaginable, and certainly not simple. The universal evaluator is a short program. The asymmetry is not about computation at all — it is about the medium. In a medium where a machine's description and the material the machine manipulates are the same kind of stuff, interpretation is a small program, because "reconfigure yourself into that machine" reduces to walking a data structure. In a medium where structure is physical, description and material are different kinds, and there is no cheap way to turn one into the other. Whenever you find yourself wanting reconfigurability, plug-in behaviour, or a system that can be told what to be rather than built as what it is, the question to ask is whether your medium admits descriptions in the same currency as its data. If it does, universality is a small piece of code. If it does not, you are building a simulator the expensive way.

The bridge that makes this work is deliberately thin and worth stating out loud: what the user regards as an expression to be executed, the evaluator regards as an ordinary list to be traversed by rules. Nothing mediates between those two views, which is why one can be turned into the other in either direction — constructing a list at runtime and handing it to the evaluator is indistinguishable from having written that program. The authors note the price honestly in a footnote: a real system's environments are not manipulable as ordinary lists, so the equivalence between program and data is cleaner in the model than in the implementation. Universality of this kind buys undecidability with it, too — a machine that can be handed its own description is a machine on which questions like halting can be posed and shown unanswerable.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) - chapter 4 section 4.1.5 on data as programs, which reads the factorial program as the description of an abstract machine wired from decrementing, multiplying and testing parts together with a switch and a copy of itself, describes the evaluator as a machine that takes a machine description as input and configures itself to emulate the described machine, calls this a universal machine, argues in a footnote that the description language is inessential since an evaluator handed an evaluator for another language emulates that language, and that therefore what can in principle be computed is independent of language and computer, citing Turing's 1936 universal machine and the undecidability results that follow; the passage inviting the reader to imagine an analogous evaluator for electrical circuits that takes a signal encoding the plans of another circuit and behaves like it, calling such a universal circuit almost unimaginably complex and remarking that the program evaluator is a rather simple program; the discussion that an input expression is a program from the user's perspective and merely a list of symbols to be manipulated by rules from the evaluator's perspective, and that making evaluation available inside programs lets a list constructed at runtime be run; and Exercise 4.15, which derives the impossibility of a general halting test from feeding a procedure its own description.
