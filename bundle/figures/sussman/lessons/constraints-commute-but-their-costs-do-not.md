# The constraints commute; their costs do not, so place each one where its inputs first exist

**Lesson:** Write a problem as a set of choices followed by a set of requirements and you get something with an unusual property: the requirements can be listed in any order at all without changing which answers are legal. That is the whole appeal of describing a problem this way, and it is genuine. It also produces a specific and predictable performance disaster, because the ordering that is irrelevant to the answer is the only thing that determines the cost. Every requirement stated after a choice is a requirement that the machinery will re-check once per combination of choices, including the vast majority of combinations that a requirement stated earlier would have refused to build in the first place.

The corrective is mechanical once you look for it. For each constraint, find the earliest point at which the quantities it mentions are determined, and move it there. A constraint naming one variable belongs immediately after that variable is chosen and nowhere later; a constraint naming two belongs immediately after the second. What this does is not filter faster, it prunes: the choices downstream of a violated constraint are never enumerated, so the saving is multiplicative in the size of everything that would have followed. The reason this is so easy to miss is that a declarative formulation actively encourages you to write all the choices first and all the requirements after, because that arrangement reads best. Readability and cost point in opposite directions here, and the arrangement that reads best is the one that explores the entire space.

There is a second and sharper version of the same move: a constraint that determines a value should not be written as a constraint at all. If some quantity is fixed by the others, generating candidates for it and then testing them wastes the entire range you generated over. Compute it and test only that the computed value is admissible. The general form of the question is worth internalizing — for each quantity in the problem, is it genuinely free, or is it a function of the free ones that you have been guessing at out of habit? Reducing the number of free quantities by one collapses a dimension of the search space; making a test cheaper does not.

The transferable point is about what a declarative interface actually gives you and what it does not. It gives you the freedom to reorder, which means it has taken the ordering decision away from the language and given it to you as an optimization knob nothing will tune on your behalf. When cost matters, do not treat a set of constraints as an unordered set just because the semantics say it is one. Read the dependency of each constraint on each variable, and let those dependencies impose the order the semantics declined to.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 4 section 4.3.2, the multiple-dwelling logic puzzle written as five ambiguous choices followed by a block of requirements, described as working but very slow; together with Exercise 4.39, which asks separately whether the order of the restrictions affects the answer and whether it affects the time to find one; Exercise 4.40, which asks for the number of assignments before and after the distinctness requirement, observes that generating all assignments and leaving backtracking to eliminate them is very inefficient, notes that most restrictions depend on only one or two of the variables and can therefore be imposed before all the choices have been made, and hints that the fix is a nest of nested binding forms rather than a flat one; and Exercise 4.37, which asks whether a Pythagorean-triple search that computes the third value from the first two and tests it for admissibility beats one that guesses all three, with the hint to consider the number of possibilities that must be explored.
