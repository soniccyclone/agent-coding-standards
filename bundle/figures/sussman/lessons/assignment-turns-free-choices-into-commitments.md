# Assignment converts choices that were free into commitments nothing writes down

**Lesson:** Rewrite an iterative loop so that instead of passing its accumulator and counter as arguments it updates them by assignment, and nothing about the result changes. The authors point out what did change: the two updates now have to be in a particular order, the version as written is right and the swap is wrong, and no part of the program records why. The dependency exists, it is load-bearing, and it lives nowhere except in the sequence of two lines. That is a new obligation created purely by the change of style, since in the argument-passing version there is no order to get wrong.

The same thing happens one level down and is easier to miss. Evaluating a combination requires evaluating its subexpressions, and the order among them had been genuinely unspecified — an implementation detail a compiler could vary for optimization. Introduce assignment and it becomes possible to write an expression whose value depends on which subexpression ran first. A freedom that belonged to the implementation has been converted into an observable, and the language must now either pin it down or forbid you from depending on it. The authors take the second route: the order should still be considered an implementation detail and programs should never rely on it, which is discipline standing in for a guarantee.

The general form is worth having as a rule of thumb, because the pattern repeats far beyond assignment. Any feature that makes an effect observable turns every previously arbitrary ordering decision into a specification question. Adding logging with side effects, adding lazy initialization, adding a shared cache, adding concurrency — all do this, and in each case the tell is the same: a decision that used to be safely arbitrary now has a right answer, and the right answer is not written anywhere. The cost is not the effect, it is the number of previously free choices that have silently become part of the contract.

The practical consequence is to treat ordering constraints as things that need to be represented, not merely obeyed. If a sequence of updates must run in one order, the argument-passing formulation states that by data flow and cannot be misordered; the assignment formulation states it by adjacency and can. Prefer the formulation where the constraint is a consequence of the structure rather than a fact somebody has to remember, and where a violation is impossible to express rather than merely wrong. The authors note in passing how odd it is that beginners are taught the imperative form first, saddling them with "should I set this before that" worries that obscure the actual ideas — a reminder that this cost is paid earliest by the people least equipped to see it.
