# When you wrap a value in a richer representation the operations complain but the total predicates lie, so audit the tests that cannot fail

**Lesson:** Replacing a plain value with a richer object that carries the value plus something about it — its justification, its confidence, its provenance, its unit, the range it is known to lie in — creates two very different classes of breakage, and only one of them is easy to find. Operations that consume the value are partial: arithmetic on a wrapped number either raises a type error or has already been extended to unwrap, so the compiler, the runtime, or a quick test finds these. Predicates that classify the value are total, and that is precisely the danger. A truth test typically answers yes for every object that is not one specific false value, so a wrapper containing false answers yes — the test does not fail, it silently returns the opposite of the truth. Equality and hashing have the same shape: defined for all inputs, therefore incapable of announcing that they were handed something they do not understand. When you enrich a representation, the audit to perform is over the total predicates and the decision points that use them, not over the arithmetic.

There is a second obligation at the same sites, and it is easy to satisfy the first and forget it. If a decision was made by consulting an enriched value, then whatever the decision produced depends on that value, so the extra information the wrapper carried has to be attached to the result — the outcome of a branch inherits the grounds of the test that selected it, and this is true even though the selected outcome may have been computed without reference to the test at all. A system that unwraps richness in order to make a decision and then forgets it has broken the invariant the wrapper existed to maintain, and the failure is invisible for the same reason as before: the answers stay right, only the accounting is wrong. Any place your code strips a decoration to make a control decision is a place that owes the decoration back on the way out.

The last part is a way to find the sites you missed. Two constructs that coincide under an encoding must have the same defect, whether or not they look related in your implementation: a two-way branch and the application of a procedure are the same operation once you notice that a boolean can be encoded as a procedure discarding one of its arguments, so the obligation to propagate a test's justification into its chosen branch is the same obligation to propagate a procedure's justification into its returned value. Having fixed one, you are required to go check the other. This is a generally useful search strategy — when a defect turns on the shape of an operation rather than on its name, look for every operation that reduces to that shape, because the encoding relationships are where the remaining instances are hiding, and they are exactly the places nobody thinks to look.

**Source:** [The Art of the Propagator](../works/the-art-of-the-propagator.md) — the conditionals appendix, which notes that the branching device is nontrivial once justified values circulate because a justified false value would read as true if handed to the host language's native branch, that the support of the predicate must be attached to the result produced by the chosen branch, and that the same argument applies to procedure application given the encoding of booleans as procedures that ignore one or the other of their arguments.
