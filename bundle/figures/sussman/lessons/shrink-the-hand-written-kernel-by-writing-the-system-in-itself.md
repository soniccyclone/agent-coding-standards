# Measure a port by the size of the part that cannot be written in the system's own language, and spend your design effort shrinking that part

**Lesson:** Moving a system to a new substrate looks like a job proportional to the system's size, and it is not. It is proportional to the size of the piece that has to be re-expressed by hand in the new substrate's terms; everything else can be carried across by whatever mechanism already turns the system's own language into substrate operations. So the real design question, asked long before any port is contemplated, is how much of the system can be written in the system's own language rather than in the substrate's. Every facility you implement in the language rather than beneath it moves work out of the hand-written region and into the region that transports itself.

The reason this is not obvious is that the boundary appears fixed. Some set of operations gets called primitive early on and thereafter is treated as the floor. But which operations are primitive is a decision, and most of the things sitting below the line are there for expedience — storage management, input and output, arithmetic on the representations, the library — not because they are unexpressible above it. Push them above and the floor drops. What remains at the bottom is genuinely irreducible: the thing that manages raw storage, and the thing that actually invokes substrate operations. That residue is small, and smallness is the whole objective, because it is the only part that must be rewritten from scratch each time.

The second half of the technique is that the translator itself is a program in the language, so it can be fed to itself. Once you have one working translator anywhere, you can produce a translator for the new substrate by pointing the existing one at code generators that emit the new substrate's instructions, run that on the source of the translator, and obtain a translator that runs on the new machine and can now translate everything else. Notice that the old substrate did all the work and is then discarded; the new machine never had to host a bootstrap. The same trick applies to the interpreter, giving you either kind of implementation on the new machine from the same source. This is not a curiosity of language implementations. Any system whose transformation stage is itself expressed in the language it transforms — a build system built by itself, a code generator whose input format its own definition is written in, a configuration system that configures itself — inherits the same property, and any system whose transformation stage is written in some other language forfeits it and must maintain two things forever.

The transferable habit is to keep a running census of what is written in the foreign language, treat every entry on it as a liability with a rewrite cost attached, and prefer any design that lets a facility move off that list even at some cost in performance. Systems accumulate foreign-language components silently, one convenience at a time, and the accumulated cost is not visible until something forces the move.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 5 section 5.5.7, the paragraph on porting a language to a new computer: the two strategies of translating the explicit-control evaluator's instructions to the new machine versus retargeting the compiler's code generators, with the note that the second lets any program be compiled on the original system and linked against a compiled runtime library; the further suggestion of compiling the compiler itself and running the result on the new machine to compile other programs, or of compiling one of the chapter 4 interpreters to obtain an interpreter that runs on the new machine; and the accompanying footnote, which observes that either strategy still requires implementing storage allocation, input and output, and everything else that was taken as primitive, and that the way to minimize this work is to write as many of those operations as possible in the language itself and compile them, so that everything reduces to a small hand-coded kernel — garbage collection and the mechanism for applying actual machine primitives.
