# Treat a name as something a quantity acquires, not something a location holds, and the whole storage question changes shape

**Lesson:** The default mental model of a variable is a container: a named place whose contents change over time, so that reasoning about a program means tracking, for each name, which value is in it now. Invert the relation and read the same construct the other way: a computed quantity exists, and a binding gives it an additional name valid over a stated region of text. Under the container reading, entering a procedure with parameters is an operation on storage, and a shadowed outer binding is a value being displaced. Under the naming reading, nothing happens to any storage at all — a quantity that already exists simply becomes referable by a further name inside a bounded region, and shadowing is incidental, since renaming the parameter would remove it without changing the program's meaning. The second reading is not merely a nicer story. It says binding is free, which the container reading cannot say, and everything downstream follows from that.

The immediate consequence is that the distinction between a programmer's variables and the anonymous intermediate results a compiler invents evaporates. Both are names for quantities; the only difference is that one kind was written down by a person and the other was written down by the compiler because the notation offered no way to write it down by hand. So the machinery for placing intermediate results — grouping names that would prefer to occupy the same location, biasing a group toward a particular register because of how its members are eventually consumed — applies verbatim to declared variables, with no separate mechanism and no rule that named variables live in some canonical home. A quantity may sit in two registers at once with neither copy privileged, because there was never a place that owned it; there were only names, and names are gone by the time anything runs. That the notation forced a person to invent a name at all is a fact about the notation: a diagram with arrows would need none.

The general habit is to notice when a relation you have been reading in one direction can be read in the other, and to check which direction makes the accidents disappear. Here, the container reading makes binding look like work and makes user variables look categorically different from compiler-generated ones, and both of those apparent facts are artifacts of the reading rather than features of the computation. Choosing the direction in which a phenomenon has fewer special cases is not a matter of taste — it determines which mechanisms you end up needing, and a design that adopts the wrong direction pays for the difference in permanent extra machinery.

**Source:** [Lambda: The Ultimate Declarative](../works/lambda-the-ultimate-declarative.md) — the section presenting binding as a renaming operator, which argues for focusing on quantities that hold several names over time instead of names that hold several values, works through the register-preference example in which parameter binding generates no code because binding only merges preference classes, concludes that a programmer's variables and a compiler's temporaries are conceptually the same thing, and notes that names are only a textual device for indicating where a quantity is referred to and are gone by run time; together with the compiler-organization section's statement that no variable has a home and that a quantity may have several simultaneous copies with none of them original.
