# Adding a true statement can break a system that reads statements procedurally

**Lesson:** A rule base looks like a collection of independently checkable claims: each one is either true of the domain or not, and adding a true one can only let you conclude more true things. That is correct about the logic and false about the artifact, because the artifact does not merely hold the rules, it runs them, and running them imposes obligations the truth of a rule says nothing about. A rule stating that a relation is symmetric is unimpeachable as a claim and, read as a procedure, says that to establish the relation you should establish the relation with the arguments swapped — which is an instruction to do the same thing forever. The rule is true. The system that acquired it no longer terminates.

Two things about this deserve to be internalized. The first is that whether the damage shows depends on details nobody considers part of the specification: which order the store is scanned in, which clause of a conjunction comes first, which of several applicable rules is tried first. A system can absorb such a rule and appear fine because it happens to reach an answer before it reaches the loop, and then start hanging after an unrelated insertion changes the traversal. That means the correctness of the rule base is not a property of the rule base; it is a joint property of the rules and the strategy, and the strategy is usually neither specified nor stable.

The second is that there is no general remedy. You can trade the strategy for one that explores more evenly and does not fall into this particular trap, at the price of losing the ability to exploit ordering for efficiency, which was a large part of why the system was usable. You can install detectors for specific loop shapes and catch the cases you anticipated. What you cannot do is have a scheme that reliably prevents a deduction system from going down an infinite path, because a rule can always reduce a goal to a strictly more elaborate instance of itself, forever, while remaining a perfectly true statement. This is not a maturity problem to be engineered away; it is what a procedural reading of an unrestricted formalism costs.

The practical stance that follows is to treat adding a rule as a change to a program rather than as an addition to a set of facts, with the review that implies: not only is this claim true, but what does it instruct the machine to do, does anything guarantee that instruction makes progress, and does its presence change the behaviour of rules that were previously fine. This applies to every system where declarative-looking entries are executed — rewrite rules, type-class instances, build dependencies, routing tables, policy engines, style cascades. In all of them the entries are individually reviewed for truth, and the failure that matters is a global property of the collection that no individual review can catch.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 4 section 4.4.3, "Infinite loops": the marriage example, in which a data base holds a single assertion, a query in the reverse direction returns nothing because the system does not know the relation is symmetric, and adding a rule asserting that symmetry drives the system into an unbounded regress, traced step by step through the rule unifying with the query, the body reducing to the reversed query, and the rule applying again; together with the observation that whether the system finds the directly asserted answer before entering the loop depends on implementation details concerning the order in which data base items are checked, that collections of interrelated rules produce loops much harder to anticipate, and that the appearance of a loop can depend on the order of clauses within a conjunction; and the accompanying footnote, which states that this is a problem of the procedural interpretation rather than of the logic, that a breadth-first enumeration of derivable proofs would avoid it at the cost of making it harder to exploit the order of deductions, that special loop detectors are a less disruptive alternative, and that there can be no general scheme for reliably preventing a system from going down infinite deductive paths, illustrated by a rule that reduces establishing a property of a value to establishing the same property of a transformed value. Also Exercise 4.64, where a small reordering within a recursive rule turns a working rule into a looping one.
