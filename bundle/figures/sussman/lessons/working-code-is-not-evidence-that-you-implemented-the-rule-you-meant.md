# Working code is not evidence that you implemented the rule you meant

**Lesson:** A construct can look sequential and mean something simultaneous. Definitions written one after another inside a block appear to take effect in order, but if two of them refer to each other, no ordering of "in effect from here down" gives either one a meaning — the only reading under which both make sense is that all the names come into scope over the whole block at once. So the intended rule is simultaneity, and the text's left-to-right appearance is an accident of having to write things in a line.

Now the uncomfortable part. An implementation that processes definitions strictly in order, extending the scope one name at a time, computes the right answers anyway in the ordinary cases. It agrees with the intended rule whenever the definitions come first in the block and none of them actually uses another's *value* while the definitions are being processed — which is nearly always. The agreement is a coincidence, in the strict sense that it holds under a condition the implementer never stated and the mechanism does not enforce. The code passes its tests and models a different rule than the one it is supposed to model. This is the general hazard: a mechanism that produces correct output on the inputs you tried is not thereby the mechanism you intended, and the gap is invisible from outside. The way to find it is not more testing but an argument — state the rule you meant, state what your mechanism does, and derive the conditions under which they coincide. If those conditions are narrower than the input space, you have discovered them; if you cannot derive them at all, you do not know what your program means.

The repair is instructive because it is not a smarter ordering. It is to bring all the names into existence before evaluating any of the expressions that supply their values, so that the scope really is the whole block, and to put in each of those bindings a value that is not a value at all — a marker that makes any attempt to read it fail loudly. The construct now implements simultaneity, and the cases where sequential processing would have quietly produced a different answer are exactly the cases that now raise an error. Note what that pattern achieves in general: instead of choosing between two behaviours in an ambiguous case, it creates the binding so scope is right, and poisons the value so timing is checked. Structure and readiness are separated, and the second gets its own detectable failure.

The last move is a design judgment worth copying. Several defensible meanings survive: definitions taken strictly in order, definitions simultaneous with premature reads reported as errors, and definitions genuinely simultaneous with later values available to earlier ones. The third is the principled one, and nobody knows how to implement it generally and efficiently. Faced with that, the implementers took the second — not because it is what the construct ought to mean, but because in the absence of a mechanism for the right answer it is better to signal an error in the hard cases than to return an answer that is confidently wrong. Meanwhile the language standard declines to pick at all, and instead makes the restriction the programmer's obligation, leaving implementers free. That is a real pattern for underspecified constructs: name the restriction, put the burden on the caller, and let implementations differ inside the space the restriction excludes — which is honest, and also means a program relying on any particular resolution is relying on something nobody promised.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) - chapter 4 section 4.1.6 on internal definitions, which argues from mutually recursive internal procedures that the only satisfactory reading of two internal definitions is that the names enter the environment simultaneously and that the scope of a local name is the entire body, then observes that the sequential evaluator gets such calls right for an accidental reason, and identifies precisely the restriction under which sequential and simultaneous evaluation agree: that the internal definitions come first and that evaluating their value expressions does not use any of the defined variables; the transformation that scans out internal definitions, creating all the local variables bound to a distinguished unassigned marker and then assigning their values, with variable lookup made to signal an error on that marker; the footnote recording that the language standard leaves implementors a choice by placing the restriction on the programmer rather than requiring enforcement; and Exercise 4.19 with its footnote, where three defensible readings are argued and the implementors side with erroring on the difficult simultaneous cases on the grounds that the fully simultaneous reading is in principle correct but hard to implement generally and efficiently, and that an error beats an incorrect answer.
