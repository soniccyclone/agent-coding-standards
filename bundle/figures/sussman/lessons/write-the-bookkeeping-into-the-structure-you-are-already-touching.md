# Write the bookkeeping into the structure you are already touching, and the auxiliary structures disappear

**Lesson:** A traversal that rebuilds a graph normally needs two side structures: a record of what has already been handled, so shared nodes are not duplicated and cycles do not spin, and a queue of what remains to be handled. Both are typically built as separate containers, sized in proportion to the data, and both can be made to vanish. The record of what has been handled goes into the very slot the object vacated: overwrite the old location with a marker meaning "moved" plus the address it moved to. Now the question "have I dealt with this already" is answered by looking at the thing itself, in one step, with no lookup, and the answer arrives together with the information you needed next anyway — where the replacement is. Any other reference still pointing at the old place discovers the migration on its own and repairs itself.

The queue disappears by a different observation: the output region already is the queue. Objects are appended to it as they are relocated, and each one, when appended, still refers to the old world and therefore still needs processing. So one position marks how far processing has got and another marks where appending happens, the span between them is exactly the pending work, and the traversal ends when the first catches the second. There is no container, no push, no pop, and the termination condition is a comparison of two positions. The reason this works is that the output has the same shape and the same order as the worklist would have had, which is worth stating as the general precondition: whenever what you are producing is traversed in the order you produce it, the production is the worklist.

The common move in both cases is to notice that some fact you were about to store separately is already implied by a place in the data you are guaranteed to visit, and to store it there instead. What that buys is not only the space of the omitted structure but the elimination of an entire consistency problem, since a separate visited-set or worklist can disagree with reality and an in-place marker cannot — the marker and the thing it describes are the same memory.

There is a real cost and it should be named. Writing bookkeeping into the data destroys the data, so this is only available when the old version is genuinely finished with, and it makes the structure temporarily uninterpretable by anything else — during the operation, the world contains objects that are neither the old thing nor a valid new thing. Any concurrent reader, any interrupt handler, any debugger that walks memory must know about the intermediate encoding. That is the trade: enormous simplification of the operation, at the price of a window during which the invariants everyone else relies on do not hold.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 5 section 5.3.2, the stop-and-copy collector: the marking of a relocated pair's old location with a special tag in the first field signalling an already-moved object, traditionally called a broken heart, together with a forwarding address in the second field pointing at the new location, so that the relocation subroutine tests the old location for that tag and, when present, simply returns the stored forwarding address instead of copying again; and the two-pointer main loop, in which both pointers start at the beginning of the new memory, relocated pairs are appended at the free pointer while the scan pointer advances through pairs that have been moved but whose own references still point into the old memory, each such pair's two references being relocated and updated in turn, with the process terminating when the scan pointer overtakes the free pointer because all accessible objects have then been moved and scanned.
