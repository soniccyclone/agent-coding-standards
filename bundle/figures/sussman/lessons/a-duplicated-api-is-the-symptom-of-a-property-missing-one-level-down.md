# A duplicated API is the symptom of a property missing one level down

**Lesson:** A recognizable shape in a maturing system: there is a type, and then there is a second type that is almost the same type, and a parallel set of operations named after the originals with a qualifier attached. Mapping, appending, filtering, indexing all exist twice, in versions that differ only in one small habit. Everyone accepts the duplication because the second type genuinely does behave differently in that one respect, and because each individual parallel operation is short and obvious. What the duplication is actually reporting is that the difference could not be expressed where it belonged, so it was pushed up into every operation instead of stated once underneath.

Trace it to the cause and the cause is usually a property the substrate does not let you vary. When a special construct is the only way to get a piece of structure built without demanding its contents, then anything using that construct is a different kind of thing from a value built the ordinary way, and every operation must be rewritten to know which kind it has. Give the ordinary constructor the ability to not demand its parts and the second type ceases to exist — not merges with the first, ceases to exist. The parallel operations then are the original operations, unmodified, and they behave correctly on unbounded structures for reasons that have nothing to do with having been adapted, because they never inspected the parts they did not use. Two families of code collapse into one and the collapse costs nothing at the call sites.

There is a second symptom that points at the same cause and is worth learning to notice. The special construct is not a value. It cannot be passed to something that takes procedures, cannot be stored, cannot be returned, so any generic machinery in the system silently excludes it — and the exclusion shows up as yet more duplication, since the generic machinery has to be re-provided in a form that handles the special case. When a feature has to be a construct rather than a value, ask what property of the evaluation rules forced it, because that property is also generating your parallel APIs.

The remedy generalizes past this example. Faced with a duplicated family of operations, do not look for a way to share code between the two families — abstract over the difference, parameterize the operations, unify them behind a common interface. All of those are work proportional to the number of operations, and they leave the two types in existence. Look one level down instead, at the mechanism that made the two types different, and ask what single capability there would have made the distinction unnecessary. The change is usually much smaller than the duplication it removes, and the reason it is so often missed is that the level where the fix belongs is not the level where the pain is felt.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) - the opening of chapter 4 section 4.2.3 on streams as lazy lists, which reviews the chapter 3 approach of introducing special forms to gain control over evaluation and calls it awkward on two grounds: that a special form is not a first-class object like a procedure and so cannot be used with higher-order procedures, and that streams had to be created as a new kind of data object similar but not identical to lists, forcing many ordinary list operations such as mapping and appending to be reimplemented; then shows that with lazy evaluation streams and lists are identical so that neither special forms nor separate stream operations are needed, requiring only that the pairing constructor be non-strict, achieved either by allowing non-strict primitives or by representing pairs procedurally, after which the standard list operations work on infinite lists as written; together with the footnote referring the first-class objection back to Exercise 4.26's argument that a conditional-like special form cannot be combined with higher-order procedures the way a procedure can, and section 4.2.2's footnote observing that building delaying and forcing into the evaluator is what makes the mechanism uniform and automatic throughout the language.
