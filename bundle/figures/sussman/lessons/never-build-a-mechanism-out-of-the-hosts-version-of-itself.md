# Never implement a mechanism out of the host's version of that same mechanism, or you inherit every limit the host imposed on it

**Lesson:** The tempting way to build a system that offers some capability on top of a platform that already offers it is to pass the request through: implement the guest's procedure calls with the host's procedure calls, the guest's interrupts with the host's interrupts, the guest's threads with the host's threads. The trap is that a pass-through does not merely borrow the host's implementation, it inherits the host's *restrictions*, and those restrictions become a hard ceiling on the guest that no amount of later cleverness lifts. If the host's control frames must nest and unnest in stack discipline, then any control structure in the guest that needs to resume a suspended computation twice, or resume one that has already been left, is not merely slow to build — it is unbuildable, because the object the guest needs to hold onto is exactly the thing the host reclaims on the way out. Systems get shipped with this defect quietly baked in, and the symptom is always the same: a feature list where the interesting entries are the ones that turned out to be impossible.

The discipline that avoids it is to descend one level and build the mechanism explicitly, in terms weaker than the one you are implementing. Instead of a recursive evaluator, an evaluator written as a flat dispatch loop over named state cells: the expression under consideration, the naming context, the pending-work chain, and a cell naming which step runs next. Nothing in that arrangement nests, so nothing is forced to unnest; a suspended computation is an ordinary value the guest can hold, copy, or resume, because it was always ordinary data rather than a privileged position in the host's own bookkeeping. The same discipline applied to preemption means a guest interrupt is never a host interrupt: the host is allowed to set one flag, and the guest's dispatch loop is the only thing that ever reads it. That single indirection is what makes it possible to reason about what the guest's own critical regions are, since the flag can only be observed at points you chose.

The general shape of the reasoning is worth separating from interpreters entirely. Whenever you build a layer that offers capability X, ask what the layer *below* assumes about X and whether the guest is permitted to violate that assumption. If it is, the implementation cannot route through the host's X. The cost is real — you write the bookkeeping the host would have done for you, and you give up the host's optimized version of it — and the payoff is that the guest's expressive power is now determined by your design rather than inherited from someone else's. It is worth noticing that the discipline is not "avoid the host": arithmetic, storage, and data constructors can all be borrowed freely, because the guest does not need to break their rules. The prohibition applies exactly and only to the mechanism you are claiming to reimplement.

**Source:** [Scheme: An Interpreter for Extended Lambda Calculus](../works/scheme-an-interpreter-for-extended-lambda-calculus.md) — the opening of the implementation section, which states the think-machine-language rule and names the earlier language whose implementation was ruined by using host recursion for guest recursion, and the scheduler discussion, which extends the same rule to interrupts by insisting that a host-level clock event may touch nothing but a single flag that the dispatch loop polls.
