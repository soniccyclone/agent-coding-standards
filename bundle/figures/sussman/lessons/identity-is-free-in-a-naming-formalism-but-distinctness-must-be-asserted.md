# In a formalism built on names, sameness is free and difference must be asserted

**Lesson:** Any notation that lets you write a placeholder and then write the same placeholder again has already given you a way to say two positions must agree, and it costs nothing: there is only one placeholder, so there is only one value, and no relation or comparison is involved at all. This is worth noticing because it is a strictly stronger form of expressing equality than testing for it. A test can only run once both sides exist; sharing a name means the constraint is structural and is enforced no matter which position gets determined first, in either direction, before either value is known. When you need two things to be the same, the move is not to compare them but to arrange for there to be one of them.

The asymmetry is the part that catches people. Reusing a name forces agreement, but using two different names does not force disagreement — nothing in the notation says distinct placeholders take distinct values, and they very often will not. So a description written to be about two participants will happily be satisfied by one participant playing both roles, and the result is not an error but a perfectly valid answer that is nonsense in the domain: everyone lives near themselves, everyone can replace themselves, every node is reachable from itself in one hop. The defect is not in the rule you wrote; it is that you read a distinctness assumption into your own notation which the notation never made.

So difference costs something and has to be paid for explicitly, with a real relation, real machinery, and real behaviour under partial information — and this is where such systems get subtle, because "these two are not yet known to be equal" and "these two are known to be unequal" are different claims and the naive implementation conflates them. The design guidance that follows is to arrange your descriptions so that as much of your intended structure as possible is carried by name sharing, which is free and total, and to treat every distinctness requirement as a deliberate, individually justified addition rather than something that falls out of writing different letters.

Generalized, this is a claim about which properties a representation makes true by construction and which it merely permits you to state. Constructed properties cannot be violated and cannot be forgotten; stated properties can be both, and their absence looks exactly like their being irrelevant. Auditing a representation, then, means going through the invariants you believe it has and sorting them into those two piles. The ones that turn out to be merely stated are where your surprises will come from, and the ones you never wrote down at all — because the notation made them look automatic — are where the worst ones come from.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 4 section 4.4.1, the rules section: the neighbour rule, whose body must include an explicit clause preventing it from concluding that everyone lives near themselves, and the accompanying definition of the identity relation as a bodiless rule whose conclusion repeats a single variable; together with its footnote, which observes that no relation is needed in order to make two things be the same because using one pattern variable in both positions means there was one thing rather than two in the first place, that the identity relation is useful precisely when the goal is to force two things to be different, and that while using the same variable in two places forces the same value to appear in both, using different variables does not force different values — the values assigned to different variables may be the same or different. Also the closely related exercises defining replacement and division-leadership relations, both of which require an explicit non-identity clause for the same reason.
