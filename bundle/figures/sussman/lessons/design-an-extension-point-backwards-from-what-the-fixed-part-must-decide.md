# Design an extension point backwards from the decisions the fixed part still has to make, not forwards from what the varying part computes

**Lesson:** The standard recipe for making a mechanism extensible is to find the part that varies with the data and hoist it into a replaceable operation, leaving the invariant part behind. The recipe is right and the interface it suggests is usually wrong, because the obvious signature is the one that describes what the varying part naturally produces, while the signature you need is the one that answers every question the invariant part is still responsible for. Take a shared location that combines contributions: the combining rule clearly varies with the kind of information involved, and the duty to notify interested parties clearly does not. But notification is conditional — announcing an update that carried no new information would defeat the whole point, since the system's termination depends on nothing being announced once nothing is learned. So the invariant part must be able to distinguish a contribution that taught it nothing, one that strictly improved on what it had, and one that conflicts. A combining rule whose contract is merely "return the combination" makes all three cases indistinguishable, and the notification logic then has to be rewritten inside every extension, which means it was never really factored out.

The fix is to state the contract in terms of those distinctions: return the very same object you were given as the current information when the contribution is redundant, the very same contributed object when it wholly supersedes what was held, and a distinguished marker for conflict. Now a cheap identity comparison in the invariant part recovers the full outcome, and every extension automatically inherits correct notification behaviour. Note what the contract costs: it demands object identity rather than mere equivalence, which is a real obligation on implementors and easy to violate accidentally by constructing a fresh equal result. That obligation is the price of the factoring, and it should be written down as part of the interface rather than discovered by whoever's extension mysteriously fails to settle.

There is a second cost to account for honestly. Extension organized by kind of data means that each newly added kind must relate to every kind already present, so a hierarchy of increasingly rich information forms accumulates promotion rules pairwise rather than linearly — plain values into ranges, ranges into justified values, justified values into collections of alternatives, each direction spelled out. The authors of such a system describe this work as boring and repetitive, which is exactly right and is also the point: it is not incidental, it is what a genuinely interoperable set of representations costs, and a design that skips it produces kinds that each work alone and cannot appear in the same computation.
