# Whether a description counts as a program is a fact about the evaluator, not about the description

**Lesson:** It is standard to distinguish a description that merely characterizes an answer from a description that produces one, and to dismiss the first as not really a program — you can write down that the thing you want is a value satisfying some property, but that just restates the question in the syntax of code. The distinction is real and worth being able to draw. What is not real is the belief that it is a property of the text. Take the same restatement of the question, feed it to a machine that knows how to enumerate candidates and abandon the ones that fail a requirement, and the text becomes an executable program that returns the answer. Nothing about the description changed. What changed is what the surrounding machinery was willing to supply.

That reframing is worth more than it first appears, because it converts a philosophical boundary into an engineering choice. If the line between characterizing and computing sits in the evaluator, then it moves whenever you are willing to build search, propagation, or inference into the substrate; and each thing you move across the line stops appearing in every program that needed it. The cost is symmetrical and should be stated honestly: what you have installed is a fixed strategy, applied to every program written above it, in cases where you have no idea whether it is the right strategy. A description that omits the method is only usable to the extent that some method supplied from underneath happens to be adequate.

The practical version of the question, then, is never "is this specification or is this implementation." It is: what would have to be true of my substrate for this specification to run, and is that thing narrow enough to build. Frequently it is much narrower than it looks. A requirement that a value have some property is executable the moment the surrounding machinery can generate candidates and can be told that a branch is dead. A relation between quantities is executable the moment something knows how to push information in whichever direction has enough inputs. In each case the leverage comes from noticing that the description was already complete and only the method was missing, so the method can be written once instead of once per problem.

The failure mode this guards against is the reflex of enriching the description until it stops being a description. Faced with a specification that will not run, the usual move is to add the steps — to convert the statement of what is wanted into an account of how to get it, at which point the statement of what is wanted is gone from the program and survives only in a comment, if anywhere. The alternative move is to leave the specification exactly as written and to ask what capability, added one level down, would let it stand as code. The first move is proportional to the number of specifications you have. The second is paid once.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 4 section 4.3 introducing nondeterministic computing, where the prime-sum-pair procedure is presented as seeming to merely restate the problem rather than specify a way to solve it, and is then declared a legitimate program because the evaluator supplies automatic search; and the accompanying footnote, which explicitly connects that procedure back to the unhelpful pseudo-Lisp square-root definition from section 1.1.7, observes that a square-root procedure along those lines can in fact be formulated as a nondeterministic program, and states that incorporating a search mechanism into the evaluator erodes the distinction between purely declarative descriptions and imperative specifications of how to compute answers, with a forward reference to the logic-programming section for a further step in the same direction.
