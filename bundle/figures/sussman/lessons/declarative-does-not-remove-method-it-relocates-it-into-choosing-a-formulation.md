# A declarative system does not remove method; it relocates the method into your choice among equivalent formulations

**Lesson:** The promise of stating what is true and letting the machinery figure out how to get there is real, but the accounting is usually done wrong. What such a system removes is the obligation to write the steps. What it does not remove is the obligation to supply information the steps used to carry. That information does not evaporate; it reappears as a choice among logically equivalent ways of stating the same truth, only some of which the machinery can actually execute usefully. Two rule sets that describe exactly the same relation, or two networks that impose exactly the same constraints, are interchangeable as statements and are not interchangeable as programs: one terminates and one loops, one propagates in the direction you need and one has nothing to push on. Choosing between them is procedural knowledge wearing declarative clothes, and no one else is going to supply it.

This matters because of how it changes the debugging experience. In a procedural system, when performance or termination goes wrong, you look at the steps, because the steps are where the decisions are. In a declarative system the steps are not yours, so the instinct is to conclude that the engine is deficient — and sometimes it is, but far more often the fault is a formulation that happens to be true and happens not to be effective. The productive question is therefore not "why is the engine doing this" but "what other formulation of this same fact would give the engine something better to work with." That reframing is the entire skill, and it is invisible to anyone who took the marketing claim at face value and believes there is nothing left to decide.

There is a boundary worth stating honestly, because it is where the whole approach stops. Some truths supply no purchase at all — a characterization that lets you verify an answer can be perfectly precise and still contain nothing an enumeration strategy can exploit, and in that case no reformulation helps and you must supply a method. Knowing which side of that boundary a problem sits on before committing to a declarative encoding is worth more than any amount of cleverness afterwards. The honest description of these systems is a large but bounded body of methodological knowledge built into the substrate, which covers a class of problems very well and covers everything else not at all.

The underlying pattern generalizes past logic engines to anything that claims to take the how away: query planners, build systems, constraint solvers, reactive frameworks, declarative deployment. In each case the user retains a real and often unacknowledged design responsibility, exercised through the shape of what they declare rather than through instructions. Treating that responsibility as real — deliberately choosing among equivalent statements for their execution behaviour, and knowing which properties of the statement the engine keys off — is the difference between these tools working and these tools being blamed.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — the opening of chapter 4 section 4.4 on logic programming, which contrasts imperative "how to" knowledge with declarative "what is" knowledge, observes that high-level languages already build a substantial body of methodological knowledge into the implementation, and notes that most languages are biased toward unidirectional computation because they capitalize on the pun that an expression describing a value can also be read as a means of computing it; the same passage's observation about the earlier constraint system that many different networks implement the same set of constraints and the user must choose a suitable one, so the user is not released from providing imperative knowledge; and the footnote to the append example, which states that many mathematically equivalent sets of rules formulate the same relation while only some can be turned into effective computing devices in any direction, and that sometimes "what is" information gives no clue how to compute an answer, instancing the definition of a square root; together with the section's admission that contemporary systems of this kind have substantial deficiencies because their general methods can lead to spurious infinite loops.
