# A boundary between two worlds can pass data across, but not behaviour

**Lesson:** When one system runs inside another — an interpreter on a host language, a sandbox, a plugin runtime, a process talking to a service — the cheap and correct move is to borrow the outer system's existing facilities rather than reimplement them. Borrowing works beautifully for anything that is inert. A procedure from the host that takes numbers and lists and returns numbers and lists can be adopted wholesale by the inner world: wrap it, give it whatever name you like on the inside, and it behaves. The inner and outer representations of ordinary data coincide, so the value crosses the boundary unchanged and the borrowed code never learns it was borrowed.

Now borrow something that takes a *procedure* as an argument, and the same move fails outright. The inner world's procedures are not the outer world's procedures; they are structures the inner world knows how to interpret and the outer world has never heard of. Hand one to a borrowed higher-order routine and it will attempt to invoke it by the outer world's calling mechanism against an object that only means something under the inner world's rules. The failure is not a subtlety of the two languages happening to differ. It is structural: a boundary between two systems of meaning can carry values whose meaning is representational, and cannot carry values whose meaning is *behavioural*, because behaviour is defined only relative to the machinery that runs it. Rewrite the same higher-order routine inside the inner world, in the inner world's own terms, and it works immediately — the code is trivial, and its triviality is the point. What had to be reimplemented was not the algorithm, it was the calling.

This is the general shape of every interoperability boundary, and it explains a class of decisions that otherwise look arbitrary. Serialization formats carry records and not callbacks. Remote interfaces exchange requests and responses rather than continuations. Sandboxes hand out data and hand back data. When a design does appear to pass behaviour across — a callback registered with a foreign library, a function shipped to a worker — look for the machinery that makes it possible, and you will find that both sides were made to agree on one representation of procedures, which is to say the boundary was removed at that point rather than crossed. Deciding early which side of your system owns the calling convention tells you, without further analysis, which imports will be free and which will have to be rebuilt.

The mundane corollary is that identifiers are part of the boundary too. Two worlds coexisting in one address space will each want the same obvious names for the same concepts, and defining the inner world's version of a name destroys access to the outer world's, which the inner world still needs underneath. Capture the reference before you shadow the name. That is a small mechanical point, but it is the same principle: the two things share a name and are not the same thing, and every place they touch has to be treated as a crossing.
