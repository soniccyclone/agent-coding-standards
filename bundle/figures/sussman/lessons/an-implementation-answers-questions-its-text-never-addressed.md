# An implementation answers questions its own text never addressed, by silently borrowing the host's answers

**Lesson:** Write an interpreter and you have written down, in one place, the meaning of everything the interpreted language can do. It looks complete: read it and you can say what any program will do. The uncomfortable fact is that the artifact answers strictly more questions than the text does. Ask in what order the arguments of a call are evaluated, and the interpreter's behaviour is perfectly definite while its source is silent — the recursion that builds the argument list evaluates one argument and recurs for the rest, and which of those two happens first is decided by the language the interpreter is written in, not by anything the author wrote or intended. The decision is real, observable, and unattributable to any line of the program.

That is a general hazard of building on a substrate that already provides the facility you are providing, and it is nastier than the familiar problem of inheriting the host's limitations, because there is no missing capability to notice. Everything works. The specification simply has a hole in it that the host has quietly filled, and the fill is invisible until someone ports the implementation to a different host and the behaviour changes. Anything the interpreted language leaves to the implementation of the interpreter is a place where the observable semantics is being set by an unstated dependency: evaluation order, arithmetic precision and overflow, the ordering of collection traversal, character comparison, recursion depth, how much numeric precision survives a round trip.

The remedy is not to eliminate the dependency but to make each such question a decision the text answers. Where you intend to commit, write the code that forces the commitment — sequence the argument evaluations explicitly so that no host convention can be consulted — and the interpreter now says what it means, at the cost of some code that looks redundant on the host you happen to be using. Where you intend not to commit, say so, because a deliberately unspecified point is a fact users of the language need and a specification that merely fails to mention it is a defect. The difference between "the answer is left open" and "we never noticed there was a question" is invisible in the artifact and enormous in the specification.

The same trap has a second form, which is representational rather than temporal. The interpreter tests the truth of interpreted values using the host's conditional, so somewhere it must convert one language's notion of truth into the other's. If the two languages happen to agree, that conversion is the identity and the whole issue disappears from view — and then the interpreted language has, without anyone deciding, exactly the host's notion of what counts as false. The authors put a small explicit translation there anyway, which is the right instinct: place a named crossing at every boundary between the implemented language and the implementing one, even where the crossing currently does nothing, because a crossing that does nothing is documentation of a choice while a missing crossing is an assumption nobody can find later.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) - chapter 4 section 4.1.1, whose subsection on conditionals notes that the use of an explicit truth predicate in the evaluator's conditional handler highlights the connection between an implemented language and its implementation language, since the interpreted predicate yields a value in the implemented language which must be translated into something testable by the implementation language's own conditional, and that the metacircular representation of truth might not be the same as the underlying one; together with Exercise 4.1, which observes that one cannot tell from the evaluator's text whether operands are evaluated left to right or right to left because the order is inherited from whichever order the underlying Lisp uses to evaluate the arguments of the pairing operation inside the argument-list procedure, and asks for versions that force each order regardless of the host; and the accompanying footnotes recording that the values returned by definitions and assignments are implementation-dependent choices.
