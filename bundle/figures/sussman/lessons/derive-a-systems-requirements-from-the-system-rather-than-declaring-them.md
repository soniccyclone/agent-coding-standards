# Derive a system's resource requirements from the system, and instrument it rather than reasoning about its cost

**Lesson:** Two kinds of fact about an artifact are routinely maintained by hand next to it and should not be. The first is its inventory of requirements — which resources it uses, which of them it saves and restores, which are used as destinations, what feeds each one. All of that is fully determined by the text, so a declaration of it is a second copy that can drift, and it will drift, in the direction of listing things that are no longer used and omitting things recently added. The right move is to compute the inventory from the text at the same moment the text is being processed for execution, and to expose it through the same interface as everything else. A requirement that is derived cannot be stale.

The stronger version is to let the derivation replace the declaration entirely rather than check it: instead of taking a list of resources and validating it, allocate each one the first time it is mentioned. The list stops existing, so there is nothing to keep in sync, and an entire category of error — declared but unused, used but undeclared — is not detected but made unrepresentable. That is the better outcome whenever it is achievable, and the reason it is often not attempted is that the declaration feels like documentation. It is not; it is a second implementation of a fact, and the derived version documents better because it is guaranteed accurate.

The second kind of fact is cost. Analytical reasoning about how many operations something performs is error-prone and gets abandoned as designs change. Building a counter into the shared mechanism — the allocator, the stack, the dispatch loop — costs a few lines and turns cost into an observable. What that unlocks is empirical complexity analysis: run the thing over a range of inputs, look at the numbers, and fit them. When you already suspect the shape of the relationship, a handful of measurements pins it down completely and you have an exact formula obtained without any derivation at all. When the numbers do not fit the shape you expected, you have learned something more valuable than the formula.

The habit generalizes past simulators. Anything that processes a description before running it — a build system, a loader, a request router, a query planner — is holding, at that moment, exactly the information needed to answer "what does this need" and "how much did that cost," and it is the only place in the system where the answer is certainly correct. Extracting it there and publishing it is nearly free. The alternative is that somebody maintains the answer in a document, and the document is wrong within a quarter.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 5 section 5.2, Exercise 5.12, which observes that the simulator can be used to determine the data paths required for a given controller and asks for the assembler to be extended to store in the machine model a duplicate-free list of instructions sorted by type, a duplicate-free list of the registers used to hold entry points, a duplicate-free list of the registers that are saved or restored, and for each register a duplicate-free list of the sources it is assigned from, all exposed through the machine's existing message interface; Exercise 5.13, which goes further and asks that the simulator determine what registers the machine has from the controller sequence itself, allocating each one when first seen during assembly rather than requiring a declared list; and section 5.2.4 on monitoring machine performance, which instruments the simulated stack to record the number of pushes and the maximum depth reached and adds a message to report them, together with Exercise 5.14, which asks the reader to measure those quantities for the factorial machine across small inputs and determine formulas in terms of the input, noting that each is a linear function and therefore fixed by two constants.
