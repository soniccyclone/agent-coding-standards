# A separate phase is a scheduling convention, not a property of the transformation, and keeping the transformer callable is what lets you collapse a level

**Lesson:** Systems that transform a description before running it almost always end up with the transformation as a separate phase, performed by a separate program, at a separate time, by a separate person. None of that separateness is inherent. The transformation is a function from descriptions to descriptions; when it happens is a decision about when to call it. If the transformer is an ordinary procedure in the running system rather than an external tool, then the same system that executes descriptions can also transform them, and the phase boundary becomes something you place wherever it is useful rather than something you inherit. A loop that reads, transforms, and then runs the result is then no harder to build than one that reads and interprets, and it is the same machinery either way.

What that flexibility buys is the ability to remove levels, which is the only intervention that matters when levels are stacked. Every layer that reads a description and acts on it multiplies the cost of everything beneath it, so a system running two levels down pays a product, not a sum, and no amount of tuning within a level competes with removing one. When the transformer is available as a callable thing, an inner interpreter that would have been run as a description can instead be transformed into the substrate's own terms once, and the layer it represented disappears rather than being made faster. This is why the ability to call the transformer at will is worth more than its quality: quality improves a factor, and calling it in the right place removes one.

The same movability applies at the other end. There is no rule that a transformation must target the substrate you are currently standing on; retargeting it produces descriptions for a different substrate, and now the same source can be either interpreted here, transformed and run here, or transformed and shipped elsewhere. Those look like three different projects and they are three schedules over one function.

The habit to take away: whenever some step in your pipeline exists only as a separate program invoked at a separate time, ask what it would mean for it to be a procedure the system can call on itself. Often the answer reveals a level that could be collapsed, a phase that could move earlier or later than convention put it, or a capability — transform-and-run at the point of use, transform for a foreign target, transform something you just received — that the tooling shape was hiding rather than the design forbidding.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 5, Exercises 5.48 through 5.52. Exercise 5.48 asks for a transform-and-run operation callable from inside the evaluator itself, replacing an interface where the compiler could only be invoked once, at machine start. Exercise 5.49 asks for a register machine running a read-compile-execute-print loop in place of the read-eval-print loop, observing that this is easy in the simulated setting because compile and assemble can be arranged as ordinary register-machine operations. Exercise 5.50 asks for the chapter 4 metacircular evaluator to be compiled and run on the register-machine simulator, and states that the resulting interpreter will run very slowly because of the multiple levels of interpretation. Exercises 5.51 and 5.52 pose the two directions as a matched pair: hand-translate the explicit-control evaluator into a low-level language to obtain an implementation there, or retarget the compiler to emit that low-level language and compile the metacircular evaluator with it to obtain an interpreter written in that language.
