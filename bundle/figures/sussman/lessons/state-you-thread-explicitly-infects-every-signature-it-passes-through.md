# State you thread by hand infects every signature it passes through, and kills the general combinator

**Lesson:** A pseudo-random generator is a pure function from one seed to the next; you never need mutation to use it. The authors write the Monte Carlo estimator both ways to show what the pure version actually costs, and the cost is not verbosity. With the generator's state hidden, the trial runner is a genuinely general procedure: it takes a count and an experiment — any experiment, expressed as a nullary procedure returning true or false — and reports the fraction that passed. With the state threaded explicitly, that procedure cannot exist. The loop must now carry the seed, produce the two values this particular test wants, and pass the last one forward, which fuses the idea of tallying trials with the fact that this experiment happens to consume two random numbers. Another experiment needing one, or three, is a different loop.

The mechanism is worth stating in general terms, because it applies far beyond randomness. Threading a value explicitly means the value appears in the type of every procedure it passes through, including procedures that have no interest in it. Those procedures are now parameterized by a concern that is not theirs, and any abstraction over them must be parameterized by it too. The abstraction you wanted — the one that quantifies over experiments, handlers, strategies, steps — cannot be written, because the things it would quantify over no longer have a common shape. Even the top-level caller ends up supplying an initial seed. The authors' phrase for it is that the generator's insides leak out into the rest of the program, and the visible symptom is always the same: a parameter that keeps propagating outward past everyone who cares about it.

That is a real argument for encapsulated mutable state, made by people who spend the following two sections cataloguing what it costs. Both halves are the lesson. Hiding state buys you the ability to write the general combinator, and it does so by removing a concern from signatures where it did not belong. It also destroys the substitution model, referential transparency, and the ability to reason about two calls as equal — which the same chapter says explicitly, in the very next section, having just made the case for it.

The practical resolution is not to pick a side but to notice which trade you are making at each seam. When a value must flow through code that has no business knowing about it, threading it costs you abstraction over that code. When a value is genuinely part of what the caller is reasoning about, hiding it costs you the ability to reason. The question to ask of a would-be piece of hidden state is whether anyone outside needs to reason about *when* it changed. Generator seeds, caches, and interned tables usually fail that test, which is why hiding them is uncontroversial; anything a caller must sequence its own actions around usually passes it, and hiding that is where the trouble starts.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) - chapter 3 section 3.1.2, which defines rand as a procedure with a local state variable updated by set! on each call, presents monte-carlo as a general procedure taking a trial count and an arbitrary nullary experiment procedure, then rewrites the same estimate using rand-update directly with the seed threaded through the loop, and argues that this second version betrays painful breaches of modularity because random-gcd-test must manipulate the two random numbers explicitly and recycle the second one through the iteration, intertwining the accumulation of test results with the fact that this particular experiment uses two random numbers, forcing even the top-level procedure to supply an initial value, and letting the generator's insides leak into the rest of the program so the Monte Carlo idea cannot be isolated for other tasks — closing with the warning that the story is not so simple, which section 3.1.3 immediately develops.
