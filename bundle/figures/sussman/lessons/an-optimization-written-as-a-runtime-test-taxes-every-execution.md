# An optimization written as a runtime test taxes every execution, so accumulating special cases eventually loses

**Lesson:** A general mechanism must be prepared for anything its input might be, so it does conservative work: it checks, it protects, it takes the path that is safe for the worst case. Noticing that a common case needs none of that, and adding a test that routes it to a cheaper path, is a real improvement and it is also the beginning of a trap. Each such test is itself work, and unlike the work it saves, it is performed on every execution including all the ones it does not help. Add enough of them and the accumulated cost of asking which special case applies exceeds what any of them save, and the mechanism is slower overall while being much larger and harder to reason about.

The relevant asymmetry is between how often a question is asked and how often it is answered. In a system that examines the input each time it acts, the number of times a classification is performed equals the number of executions. In a system that examines the input once and emits something specialized to what it found, the classification happens once no matter how many times the result runs. The two are not competing implementations of the same optimization; they have different cost structures, and the second one's advantage grows without bound with repetition. That is why the answer to "could we just keep adding cases to the general mechanism until it is as fast as the specialized one" is no in principle rather than in practice: the tests are the cost, and the specialized approach does not have them.

There is a second and subtler advantage in the same direction. A specialized artifact can exploit a fact about the specific input it was made for — this operand is a name, so nothing it does can disturb anything; this call is in final position, so nothing needs preserving — and having exploited it, the fact leaves no trace and costs nothing at runtime. A general mechanism cannot exploit such a fact, because it can only ask a question, and asking is not free. So the set of optimizations available to the two is not the same set with different overheads; the specializing approach can reach things the general one cannot express at any price.

The practical reading is that when a hot mechanism starts growing special cases, the growth itself is the signal — not that the cases are wrong, but that the classification wants to move earlier. Anywhere a system repeatedly examines something stable to decide how to act, the examination can be lifted out and its result reused, and the ordinary version of this in everyday code is caching the decision rather than the answer. The unpopular version of the lesson is the one worth keeping: a fast path added to a general routine makes some inputs faster and all inputs pay, so its benefit needs to be argued from the distribution of inputs, not from the fact that it is an improvement for the case that motivated it.
