# Deferred work is retained state, so a demand-driven discipline cannot express a loop no matter how the loop is written

**Lesson:** Postponing a computation is usually sold as pure gain: you avoid work that turns out to be unnecessary, and you can describe objects too large or too infinite to build. The cost is easy to miss because it is not paid in time. A postponed computation is a promise you must keep, so it must be represented, and it must be kept somewhere until demanded. Under a discipline where every argument is passed unevaluated, a loop that repeatedly steps a value by some function does not overwrite that value — it hands forward a promise that mentions the previous promise, and the chain of unforced promises grows in exact proportion to the number of steps taken. The loop terminates and returns the right answer, but it consumed memory linear in its trip count. The conclusion is stronger than "laziness has overhead": a demand-driven evaluator cannot realize iteration at all, in the sense that no program text you write in it will run in bounded space, and this is not an implementation weakness to be optimized away but a direct consequence of what the discipline promises.

The proof of that is available before any implementation exists, which is the methodological point. Model the language as expression rewriting and watch the size of the expression as reduction proceeds. Under eager argument evaluation the loop's successive states are the same shape with different numbers in them, so a constant bound exists. Under deferred argument evaluation the successive states are strictly larger each time, so no bound exists. The asymptotic space behaviour of every implementation of the language is visible in the rewriting sequence, before you have chosen a data representation, before there is any question of stacks or heaps. That is the right place to discover it, because it is the only place where the answer is a property of the language rather than a property of your code.

The resolution is instructive too, because it does not consist of picking a side. The unbounded growth is caused not by the order itself but by nesting: an expression can only be pending because it sits inside another one waiting on its value. Rewrite programs so that no call ever appears inside another call — every call names explicitly what should be done with its result — and the two evaluation orders coincide, because there is no longer any deferred outer context for either order to disagree about. A design tension that looks like a forced choice between two global policies turns out to be an artifact of a program shape, and eliminating the shape eliminates the choice. When two design axes seem to be in irreconcilable conflict, it is worth asking which third property both of them were quietly assuming.

**Source:** [Scheme: An Interpreter for Extended Lambda Calculus](../works/scheme-an-interpreter-for-extended-lambda-calculus.md) — the implementation-issues discussion of reduction order, which argues that a call-by-name evaluator accumulates deferred-argument structure proportional to the number of iteration steps and therefore cannot model iteration, grounds the claim in the growth of expression size under normal-order rewriting, and observes that the conflict disappears under a pure continuation-passing program shape where no combination is ever a subcombination of another.
