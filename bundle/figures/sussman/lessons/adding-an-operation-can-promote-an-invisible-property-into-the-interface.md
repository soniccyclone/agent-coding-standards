# Adding one operation can promote an invisible property into the interface and void every equivalence you relied on

**Lesson:** Build a two-element structure whose two halves point at one shared piece, and build another whose halves point at separate but identical pieces. Read them with the constructor and the two selectors and there is no experiment that tells them apart — the authors say flatly that sharing is completely undetectable if you operate on lists using only those three operations. Add a mutator and the two structures behave differently on the first write: in one, changing the first half changes the second; in the other, it does not. Nothing about the structures changed. The set of available operations changed, and a property that had been an implementation detail became part of the observable behaviour.

That is the general hazard, and it is worth stating separately from mutation, because mutation is only the most common instance. Every claim of the form "these two values are the same" is relative to the operations you have. Widen the operation set and previously equal things can come apart. A hash that ignored field order, a comparison that normalized whitespace, two encodings that decoded identically, two implementations indistinguishable until someone added a timing-sensitive path or an identity-based cache — in each case an equivalence that was true and useful became false because the language of observations grew. The equivalences you are relying on are not properties of the data; they are properties of the data *and* the interface.

The knock-on effect is that code written under the old equivalence is now wrong without being edited. The authors work this through with an exercise: a recursive procedure counting parts of a structure, obviously correct if the structure is a tree, returns various wrong answers when parts are shared and fails to terminate when the structure has a cycle. Nobody made a mistake writing it. It encoded an assumption about the shape of what it walks, that assumption held under the old operation set, and the new one made shapes reachable that violate it. Fixing it requires the algorithm to track identity — to know which parts it has already seen — which is exactly the concept that did not exist before.

So when you extend an interface, the review question is not only what the new operation does. It is which distinctions the new operation can now make, and which existing code assumed those distinctions were impossible. This is checkable in advance: list the properties your representation has that no current caller can observe, and treat each one as a hazard to be re-examined whenever an operation is added. The authors are candid that their own resolution — treating identity as equality of pointers, effectively declaring an object to be whatever sits at some set of memory locations — is enough for simple programs and is hardly a general answer to what sameness means.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) - chapter 3 section 3.3.1's subsection on sharing and identity, which contrasts a pair whose car and cdr point at one shared list with a pair built from two separately constructed identical lists, notes both print the same and that sharing is completely undetectable using only cons, car and cdr, shows a procedure mutating the car producing different results on the two, introduces eq? as a test of whether two things are the same object by pointer equality, warns that mutation can have unanticipated results without a good understanding of how data is shared, and adds the footnote conceding that identifying an object with the contents of particular memory locations suffices for simple Lisp programs but is hardly a general way to resolve sameness in computational models; together with Exercises 3.16 through 3.19, in which a naive pair-counting procedure returns three, four or seven for three-pair structures depending on sharing and fails to terminate on a cycle.
