# Whether a system has state is a fact about where the observer stands, not about the system

**Lesson:** Take a component with local state — an account balance decremented by each request — and rewrite it as a function from a balance and the whole succession of requests to the succession of resulting balances. There is now no variable that changes, no assignment, and none of the reasoning hazards that come with either. But arrange for the requests to be typed by a person and the results to be shown to that person as they arrive, and the person's experience is unchanged: they act, the thing responds differently than last time, it evidently has a state. Both descriptions are correct simultaneously. The function is genuinely a function; the perceived state is genuinely perceived. So statefulness cannot be a property the artifact either has or lacks.

What actually produces it is the observer's position. Someone embedded in the interaction, who exists in time and can only ever hold one moment at a time, must describe the counterpart as something that changes. Someone able to stand outside and consider the entire history at once sees an object with no time in it at all — the same relation as between watching a particle move and looking at its whole path in spacetime, where nothing changes because everything is already there. This generalizes past the toy example: from the vantage of one part of a large process, every other part appears to have hidden, time-varying local state, precisely because that part cannot see the others whole.

That reframes the choice between an object-oriented decomposition and a history-oriented one. It is not a choice about which is true, and not principally a choice about which is more elegant. It is a choice about where you are going to draw the boundary between what your program stands outside of and what it is embedded in. Whatever falls outside the boundary is describable as a function of its complete input and can be reasoned about without any notion of time; whatever the program is embedded in has to be modelled as something that changes, because from inside there is no other honest description available. Making the computation's own execution order carry the modelled world's time is what manufactures objects, and it is worth knowing you did it deliberately.

The authors give the one crisp criterion they have, and it is about sharing rather than about state: the object decomposition is worth its trouble when the state the pieces keep to themselves greatly exceeds the state they hold in common, because the decomposition is drawn along object boundaries and only pays when those boundaries actually separate things. Where the shared portion dominates, dividing the world into objects buys little and costs the whole apparatus of ordering and synchronization. And they refuse to declare an overall winner: each view has real advantages, neither is sufficient alone, and unifying them may be less a programming question than a question about how description works at all.

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) - chapter 3 section 3.5.5's subsection giving a functional-programming view of time, which contrasts a withdrawal processor holding a local balance and mutating it against one implemented as a function from a balance and a stream of amounts to a stream of balances, observes that the second implements a well-defined mathematical function whose behaviour does not change and yet presents the user with a system that appears to have changing state, resolves the apparent paradox by saying that it is the user's temporal existence that imposes state on the system and that a user who could step back and think in terms of the whole stream would find the system stateless, notes the physics parallel that a particle's position changes while its world line in spacetime does not, generalizes to the claim that from the point of view of one part of a complex process the other parts appear to have hidden time-varying local state, states that modelling this decomposition is what makes computational objects non-functional and makes execution time model world time, and closes with the footnote that the object model is useful when the unshared state of the objects is much larger than the state they share, together with the section's final admission that neither the object view nor the timeless functional view is completely satisfactory and that no grand unification has emerged.
