# An operator implemented by removal only means what you think once its subject is determined

**Lesson:** In a system that builds answers up incrementally, most operators extend a partial answer, and they behave sensibly whether the partial answer is nearly complete or nearly empty — an extension of nothing is just a broader set of possibilities. Operators implemented as removal are not like that, and the difference is not visible in the notation. Removing the candidates that satisfy some condition presumes there are candidates whose satisfaction of the condition is determined. Apply it to a partial answer in which the relevant quantity has not been decided yet, and the operator does something that is technically consistent with its definition and semantically nothing like what was meant: it asks whether the condition could be satisfied by anything at all, discovers it could, and discards everything.

The practical symptom is that two arrangements that ought to be equivalent are not. Constrain first and then exclude, and the exclusion runs against determined values and does the expected job. Exclude first and then constrain, and the exclusion runs against an empty state and annihilates it, so the whole computation yields nothing. There is no error, no warning, and no partial result to inspect — the honest-looking answer is that no solution exists. Once you know the shape you can spot it, but before you know it, the natural conclusion is that the problem has no solution, which is a very expensive mistake to make.

The general statement is that a component may carry a precondition on *how determined its input is*, and that this kind of precondition is invisible to the mechanisms that normally catch preconditions. Types describe what an object is, not how much of it has been decided; a partially determined value has the same type as a fully determined one. So the obligation falls back on discipline: for each operator, know whether it is monotone in the amount of information it receives — whether giving it a more complete input can only shrink its output — and know that non-monotone operators must be placed after the things that determine their subjects. The same reasoning explains why an escape hatch that hands values to an outside evaluator carries the same restriction, and for the same reason: outside code cannot be given something undecided.

The design-level conclusion is that the ordering freedom advertised by such a system is not uniform across its operators, and the operators that lack it should be identified explicitly rather than discovered. A system with a clean commutative core plus a small set of order-sensitive operators is workable if the set is known and documented; the same system with the distinction undocumented is a trap, because users will reason from the commutativity of the core and reorder something that cannot be reordered, and the failure will not point back at what they did.
