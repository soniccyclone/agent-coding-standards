# A second implementation of an abstraction is paid for in the private conventions underneath it, which nobody wrote down because nothing had crossed them

**Lesson:** An abstraction with one implementation has an interface that is stated and a set of conventions that are not. The conventions are the choices made below the interface about where things are kept, who owns what during a transfer, what has been done already by the time control arrives, what the caller is expected to clean up. None of them were written down, not through negligence but because there was nothing they could disagree with: the single implementation was consistent with itself, and consistency with yourself needs no specification. When a second implementation of the same interface appears, built by different reasoning for different reasons, it makes those same choices independently and gets some of them differently. The interface still matches. The system does not work.

So the cost of the second implementation is not in implementing it. It is in discovering the conventions — one at a time, each as a concrete failure — and then building the translation at every point where control passes between the two. That translation is genuinely necessary work, not glue to be avoided: something has to move the value from where one side left it to where the other side expects to find it. What can be avoided is discovering the conventions by debugging. The move is to write them down as an explicit protocol at the moment the second implementation is contemplated, by asking of every transfer point what the state is required to be on each side, and to treat that document as the actual interface from then on. The stated interface was never the interface.

There is a second, quieter cost, in the vocabulary. Category names accumulate around a system's existing distinctions, and some of them are defined by exclusion — a kind that means "the other one", "the general case", "not the special one". A third member of the category falsifies every such name without changing a character of it. The word keeps being used, keeps looking correct, and now denotes something narrower than it says, so old code and old prose read as though they cover a case they do not. Names defined as the complement of another name are therefore a latent hazard proportional to how likely a third case is, which is a reason to name each kind for what it is rather than for what it is not, even when there are only two.

The general habit: whenever you are about to add an alternative implementation of anything — a second storage backend, a second transport, a second execution engine — expect the schedule to be dominated by the unwritten agreements rather than the feature, go looking for them deliberately at the transfer points, and audit the category vocabulary for words that quietly mean "the other one".

**Source:** [Structure and Interpretation of Computer Programs](../works/structure-and-interpretation-of-computer-programs.md) — chapter 5 section 5.5.7 on interfacing compiled code to the evaluator: the modification of the evaluator's application dispatch to recognize compiled procedures as a third kind alongside primitive and compound ones and transfer control directly to the compiled entry point; the explicit note that the compiled entry point must be preceded by restoring the continuation from the stack into the continuation register, because the evaluator had been arranged so the continuation sits on top of the stack at the dispatch while compiled code expects it in the register; and the section's footnote conceding that compiled procedures are of course compound in the ordinary sense of being non-primitive, and stipulating that for compatibility with the explicit-control evaluator's existing terminology the word "compound" will henceforth be used to mean interpreted as opposed to compiled.
