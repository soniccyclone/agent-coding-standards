# Separate the structure from the position in it, and give the position its own invariant

**Lesson:** When a structure is traversed, there is a temptation to keep the current place inside the structure itself, and it is worth resisting on grounds that have nothing to do with elegance. The place is not a property of the data; it is a property of an act of inspection being carried out on the data. Once you separate them — the structure declared as a structure, and the access mechanism declared as its own object holding the position — three things follow immediately. Several inspections can be in progress on the same structure at once, at different places, without any of them knowing about the others, which is impossible when the structure owns a single position. The operations can be given as operations on the access object rather than on the structure, so the signature of each one says plainly that it advances something. And the structure's identity stops changing when someone merely reads it.

The second payoff is about correctness, and it is the reason to hide the position rather than merely relocate it. There is a relation that must always hold between the position and the structure it points into: the position lies within bounds, established when the access object is created and preserved by every advance. Make that field unreadable from outside and the relation cannot be broken by any client, no matter what it does — not because clients are trusted to be careful, but because the only operations that can touch it are the ones that maintain it. This is the general pattern for any invariant spanning two pieces of state: put both pieces behind the same wall, expose only operations that preserve the relation, and the invariant becomes a property of the type instead of a property of every program that uses it. What the client is given instead is a derived observation — whether a previous advance ran off the end — which is a fact about the traversal, not a piece of its machinery.

There is also a design lesson in what happens when a traversal needs more than the position. Determining where an ordered stretch ends requires seeing one element beyond the one being processed, and a structure that only ever reveals its current element cannot supply that. The move is not to weaken the structure's discipline but to extend the access object: give it a field holding the element already read and a flag for the derived boundary condition, and define the extended object as an extension of the plain one so that everything already written for the plain one still applies. The general principle is that a lookahead, a buffer, or any other apparatus a particular traversal needs belongs to the traversal, and adding it should be an extension of the access mechanism rather than a change to what the data is.

**Source:** [Algorithms and Data Structures](../works/algorithms-and-data-structures.md) — section 1.7's conclusion that it is appropriate to distinguish the sequence as a data structure from the mechanism for accessing its elements, with several access points able to exist concurrently on the same sequence; section 1.7.1, where the rider's position is invisible so the invariant relating it to the sequence's length cannot be falsified by direct access, and the end-of-file flag is the only property exposed; and section 2.4.2, where determining the end of a run requires lookahead and is met by defining an extended rider type carrying the next key and an end-of-run flag rather than by altering the sequence.
