# Metadata lives as long as the longest-lived thing it describes

**Lesson:** Descriptive data that never changes invites an obvious placement: put it with the code that declared it, among that code's other constants, where it costs nothing and is manifestly correct. The placement is wrong whenever the things being described can outlive the code that declared them, and in any system that supports both dynamic allocation and removal of code, they can. An instance allocated by one component may be reachable from a structure rooted in another, so removing the first component does not remove the instance — and the instance still needs its description, for reclamation, for dispatch, for checking, for anything the run time does with it. Placing the description with the code makes its lifetime the code's lifetime, when what the design requires is that its lifetime be the union of the lifetimes of its instances.

The general rule is that immutability tells you nothing about where something belongs; reachability does. A constant is placed correctly when it is stored in the region whose reclamation rule matches the set of things that can refer to it — so a description referred to only from within one component may live with that component, and a description referred to from arbitrary long-lived structures must live in the region governed by the same reclamation rule as those structures. The awkward consequence, worth accepting deliberately rather than resisting, is that constant data ends up in the dynamically managed region, alongside mutable data, where its residence is decided by whether anything still points at it. That looks like a category error and is in fact the whole point: residence is about lifetime, and lifetime is about who can still refer.

The situation that forces this is worth being able to recognize before it produces a fault, because the fault it produces is a dangling reference discovered long after the removal that caused it. It arises whenever a type declared in one place can be extended in another, and instances of the extension can be stored where something declared with the base type is expected. Then a structure whose root belongs to the surviving component contains members whose descriptions belong to a departed one. Any design with substitutable extensions and unloadable components has this shape, so the question to ask early is: for each piece of per-type information the run time consults, which components can hold a reference to an instance of that type, and does the information outlive all of them?

**Source:** [Project Oberon](../works/project-oberon.md) — section 8.3's statement that type descriptors must be allocated in the heap and cannot be placed among a module's constants in the block space even though they are constants, with the reason given that heap elements may still refer to a descriptor after the module defining the type has been unloaded, illustrated by a structure rooted in a variable of a base type declared in one module containing elements of an extension type defined in a second module that has since been unloaded while the first remains; together with the description of what those descriptors hold — the size of the type, the number of reference fields, a table of pointers to the descriptors of the base types, and the offsets of the reference fields — and the note that descriptors themselves carry the same prefix, with a size in place of a type tag and a bit distinguishing the two, because a descriptor has no descriptor of its own.
