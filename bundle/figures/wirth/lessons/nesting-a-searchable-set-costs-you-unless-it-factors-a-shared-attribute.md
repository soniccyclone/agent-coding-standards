# Nesting a searchable set costs you unless the nesting factors out a shared attribute

**Lesson:** Organizing a large collection into a hierarchy feels like it must help, on the intuition that dividing a search space makes searching easier. For a collection that is already held in a structure whose search cost grows logarithmically, this intuition is exactly backwards, and the arithmetic is short enough to carry around: the logarithm of a sum is smaller than the sum of the logarithms, so one search through the whole set costs less than a search to find the group followed by a search within it. Every level of nesting you impose is a level of search you have to pay for on the way in, and it buys nothing on the retrieval side because the flat structure was already sublinear. Subdivision is not a performance technique. Where it appears to be one, the structure being subdivided was linear to begin with, and the real fix was the structure.

What subdivision genuinely buys is factoring. If the members of a group share an attribute, the group node can hold that attribute once instead of every member holding its own copy — storage is saved in proportion to group size, and, more importantly, any question posed in terms of that attribute is answered at the group node without descending at all. That is the test, and it is a specific one: name the attribute the grouping factors out, and name the queries that become cheap because it is stored once. If you cannot name either, the hierarchy is providing arrangement rather than capability, and arrangement is not worth a level of search. Notice that the usual attributes on which people group — ownership, permissions, and other apparatus for keeping parties out of each other's way — are real answers to this test but only in a setting where multiple parties exist. Import the structure into a setting with a single party and you have imported the cost without the attribute.

The transferable discipline is to make the scope condition part of the design record. A structure justified by a property of its environment should say which property, so that when the environment changes — one party becomes many, one machine becomes a fleet — the reasoning can be re-run rather than rediscovered. And the inverse is worth stating too: hiding the internal structure of the collection from its clients, so that they see an unordered set of names and nothing else, is what makes the choice revisable at all. A hierarchy exposed in the naming scheme has been promoted from an implementation decision into part of the interface, and can no longer be flattened when it stops earning its cost.

**Source:** [Project Oberon](../works/project-oberon.md) — section 7.4's comparison of a flat directory, in which the internal tree structure is invisible from outside and the whole thing is a single ordered set of name-and-file pairs, against systems whose directories expose a visible tree so that a name is a sequence of names traversed one component at a time; the argument that because search path length grows with the logarithm of the number of elements, any subdivision inherently decreases performance, since the logarithm of a sum is less than the sum of the logarithms for any positive operands; the statement that subdivision is justified only where sets of elements share property values, which can then be stored once at the referencing subdirectory rather than in every element, yielding both storage economy and possibly faster accesses that depend on those properties; and the identification of those properties as owner, password and access rights, which have significance primarily in a multi-user environment, with the conclusion that a system conceived explicitly for a single user has little need of them and gains the best performance and a simpler implementation from a flat directory.
