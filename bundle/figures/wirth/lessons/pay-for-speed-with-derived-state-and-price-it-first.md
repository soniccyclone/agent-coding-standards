# Pay for speed with derived state, but price the exchange before you buy

**Lesson:** A representation that minimally and faithfully records the state is often not the representation the hot operation wants. The standard remedy is to carry additional data derived from the state — redundant by construction, since it says nothing the primary state does not already imply — chosen so the frequent question becomes cheap to answer. The trade is exact and can be written down: you save on every occurrence of the frequent operation and you pay on every occurrence of the operations that mutate the state, so the transformation is profitable only when the frequency ratio between the two exceeds the cost ratio between maintaining the summary and recomputing without it. Do this arithmetic with the actual counts from the algorithm's structure — which operations run once per step of the outer construction, which run once per inspected alternative — rather than by intuition about what feels expensive. Intuition reliably mispredicts here because the maintenance cost hides in code that looks trivial.

Which derived facts to keep is the whole design decision, and the seductive wrong answer is to mirror the surface of the state. A structure shaped like the problem's physical layout, marking each position as available or not, gives an immediate test — and is disqualified anyway, because restoring it correctly when the state is undone requires recomputation that costs more than the test ever saved. The productive move is to find what the predicate actually depends on and key the summary on that. If safety is decided by whether a row or a diagonal is already claimed, then per-row and per-diagonal occupancy flags are the right shape: they make the test a small fixed conjunction and, crucially, they make both claiming and releasing a constant-cost update. Two properties to demand of any derived state, then: cheap to interrogate, and cheap to maintain incrementally in both directions. The second is where naive choices die.

Every piece of redundant data also creates obligations that the primary state did not have, and they are correctness obligations rather than performance ones. It must be initialized to agree with the initial state, which is easy to forget precisely because it encodes an absence. Undoing an update must restore it exactly, and that soundness usually rests on a discipline elsewhere in the algorithm rather than on the update code being locally obvious — releasing a claim is safe only because claims are released in the reverse order they were made, so nothing later still depends on it. When the argument for a piece of redundant state depends on an ordering invariant like that, the invariant is now part of the program's meaning and has to be stated, not left implicit in the fact that the code happens to work. Finally, notice that the transformation is recursive: once the fast version exists, whatever expression now dominates the innermost frequent path is a candidate for the same treatment, and the same inequality decides it.
