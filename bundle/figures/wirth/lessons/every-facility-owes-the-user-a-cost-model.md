# Every facility owes its user a cost model it can explain by itself

**Lesson:** Hiding a mechanism is only legitimate if using it costs something predictable. Treat this as a design requirement with a precise form: the method by which each facility is realized must be explainable on its own, without reference to any of the others, precisely enough that someone reading a program can estimate the work it will do. Independence is the demanding half. A construct whose implementation you can only describe by enumerating cases about what else appears nearby has no cost model, and the programmer using it is guessing. Storage access is where this matters most, because it is the operation that happens constantly, so any concealed cost there is multiplied across an entire program — and a great deal of poor performance traces exactly to a design that obscured what was happening under the banner of sparing the user from details. Making the mechanism visible is a service, not a leak of implementation.

Meeting the requirement means organizing facilities so that each corresponds to a distinct access technique rather than offering one uniform-looking mechanism with wildly varying realizations. A structure whose parts are chosen by a computed position implies offset arithmetic deferred to run time; one whose parts are chosen by a fixed name has every address resolvable during compilation, which incidentally lets its parts differ in size and type since the compiler can tabulate them individually; a structure whose parts are not individually selectable at all can be represented as a membership bitmap in a single word; a structure of varying length needs dynamic allocation but gets much simpler if access is restricted to one position at a time through a sliding window. Each has a different characteristic cost, each is named differently, and choosing between them is the programmer's business because it is the choice that fits a representation to an algorithm. A design that makes these look interchangeable has taken away the information needed to make that choice while leaving the consequences in place.

The failure mode to watch for is not a single expensive feature but a pair of individually harmless ones whose combination collapses a scheme. Dense packing with statically known layout is sound precisely because the compiler knows every size and offset; permit sizes to be withheld until run time and indirect addressing becomes necessary, which costs some speed and, much worse, destroys the entire storage-economy scheme that justified the first feature. Foreseeing that class of interaction is a large part of the skill. And the tempting escape — have the compiler produce the good code when it can and fall back otherwise — is a bad trade twice over: it is the road to enormous, unreliable optimizing compilers, and it leaves the user with a facility whose cost swings by large factors under circumstances that look nearly identical, which is the exact property that makes a cost model useless. Be suspicious, finally, of the argument that these distinctions will stop mattering as the substrate improves. Substrates that promise to erase such differences tend to do it by absorbing enormous complexity of their own, to the point of needing an interpretive layer beneath the instruction set, and the result is that the complicated behavior becomes the default, simpler means are no longer reachable, and the built-in inefficiency can no longer even be measured for comparison.
