# When an optimization forces two loops together, give each advance its own guard

**Lesson:** The clean formulation of a two-index traversal keeps the indices in separate loops: an outer one that advances a position and an inner one, hidden behind its own name, that does the work at that position. The two are independent, each has a short invariant, and neither has to know how the other terminates. This is the version worth writing first and it is also the version that blocks every serious improvement, because the improvements all consist of letting the outer index advance by more than one step using something the inner loop learned. The moment that information has to flow outward, the independence is gone — not by choice but by the nature of the optimization — and the usual next move is to flatten the two loops into one and reconnect them through a flag that stands for how the inner one ended. That version is faster and much worse: the flag is a stand-in for a condition, its meaning has to be reconstructed at each place it is read, and the reconstruction is what quietly breaks the next time somebody edits the loop.

The better shape is a loop with several alternatives, each carrying the guard under which its own advance is legitimate. Now the coupling is explicit and typed: there is one condition under which the inner index may move, another under which the outer index moves and the inner resets, and the loop ends when none applies. The invariant is stated once for the whole loop and each branch is checked against it separately — a local obligation per branch rather than a global argument about a flattened body. Deriving the guards is mechanical once the invariant is written down: for each way of advancing, ask what must hold for that advance to preserve the invariant, and that is the guard. The termination condition then falls out as the conjunction of the negated guards, which means the postcondition is read off the loop rather than argued for.

The transferable content is about what to do when a performance requirement destroys a decomposition. The decomposition was carrying the correctness argument, so losing it costs something real, and the choice is not between "keep the clean version" and "merge and cope". Look instead for a control construct that can express the coupling directly, so the merged code still has a place to put each condition. Where the language offers no such construct, write the guards down beside the code as comments and accept that the invariant is now yours to maintain by hand — which is a real cost, and worth knowing you are paying, because it is exactly the cost that shows up later as an error introduced during an unrelated change.

**Source:** [Algorithms and Data Structures](../works/algorithms-and-data-structures.md) — section 1.9.1's assessment of straight string search, which credits the two-decoupled-loop formulation with transparency but notes that the more sophisticated algorithms use information from the inner loop to advance the outer index by more than one so the loops can no longer be independent, and that eliminating the inner procedure by means of a logical variable loses the original transparency and may cause errors during the program's evolution; and the same section's reformulation using a multibranch guarded loop, with the invariant fixed first, a guard derived for each of the two ways of advancing, and the postcondition obtained as the conjunction of the negated guards.
