# Ship a minimal core with an extension mechanism, and earn features by reusing it rather than by adding them

**Lesson:** A monolith is not merely large, it is a pricing model: every user carries every conceivable capability in order to use the few they need. The alternative structure is a core containing only what is essential, plus a mechanism by which anything else can be added later without disturbing what is already there — so each user assembles the system their task actually requires. This is the difference between a design that anticipates all uses and a design that anticipates being extended. The second is a much weaker and much more achievable requirement, and it is what lets a system stay small at every point in its life rather than only at the beginning. Extensibility is the precondition of leanness, not a feature bolted on for the benefit of third parties.

The design work that makes this possible is the choice of primitives, and that choice is the hardest judgment in the whole exercise: find the small set of operations that offer the greatest leverage for extension while resisting the urge to mint a new primitive for every situation. Both failure directions are real. Too few or badly chosen primitives and extensions cannot be written without breaking into the core; too many and you have rebuilt the monolith with extra steps, since a proliferating primitive set is itself the complexity you were avoiding. The test is generative reach per concept: how much unforeseen functionality can be expressed by composing what already exists. And the corresponding structural work is decomposition into parts with precisely stated interfaces — which imports what, which exports what, each part owning its implementation technique and keeping all its operations consistent about the types it exposes. That decomposition is the most demanding part of system design and is rarely right the first time, so it has to be iterated while iteration is still possible, before release freezes it.

The payoff shows up as capabilities that cost nothing because they are not implemented at all. Make command invocation a matter of pointing at a name wherever text appears, and menus are just texts holding frequently used commands; add a graphics editor over the same text notion, and buttons and icons appear as decorated versions of the same act; let a message body be text, and executable commands arriving by mail follow with no mail-specific machinery. Each of these would be a subsystem in a design that added features directly. Similarly, define a new type as compatible with an existing one and everything the old type supported applies to the new — a mail message is editable because it is a text, not because someone wrote an editor for messages. When you notice that a whole class of requested functionality is falling out of a mechanism already present, that is the signal that the core's abstractions were chosen correctly. When every request needs new code, they were not.

One further discipline: keep the naming honest and minimal too. Reaching for fresh vocabulary when an existing concept already covers the thing adds nothing but a translation burden for every reader, and dressing a mechanism in anthropomorphic language invites reasoning about it by metaphor instead of by its actual semantics. Economy of concepts includes economy of names for them.
