# Enumerate the machine-dependent parameters and publish the list; its length is the portability claim

**Lesson:** Portability is not obtained by pretending the differences between machines do not exist, and it is not obtained by refusing to let programs exploit the machine they run on. It is obtained by making the dependence explicit, finite, and enumerable. Two moves do the work. First, at every point in the general definition where a property genuinely depends on the host, say so there — the available character set, how many characters are packed into a unit, the range of the integers, the precision of the reals. Marking the dependence in place is what lets a reader know exactly which of their assumptions is local, instead of discovering it when the program moves. Second, collect the actual values for a given host into a separate document that amends the general definition rather than replacing it, organized by reference to the sections it modifies so the delta is inspectable as a delta.

The reason to structure it that way is that the amendment document becomes a measurement. Its brevity is the substantive claim: if characterizing a whole implementation of a system takes a short chapter, then the system's machine dependence is genuinely bounded, and the claim can be checked by anyone who counts the pages. That converts a quality usually asserted into something demonstrated, and it is a discipline on the designer too, since every dependence that has to be written into that chapter is one you can see accumulating. A design where this document would run long has a portability problem that its authors can no longer avoid noticing. Be prepared for the list to include categories beyond arithmetic ranges and character sets — which parts of the general definition are restricted rather than extended here, how many characters of a name are actually distinguished, what the limits are on particular constructs, which combinations this host does not support at all. Restrictions belong in the list as much as extensions do, because an unstated restriction is the same problem as an unstated extension.

The same document is where you admit the host's specific facilities, and that placement is the point. If a program needs to reach the surrounding operating system's notion of a persistent named object, the annotation that connects a declaration to that notion belongs in the amendment, not in the general definition — the general definition stays free of any commitment to a particular system's commands and vocabulary, and the coupling is confined to a place a reader knows to consult. This is the general pattern worth taking away: do not choose between an abstraction that cannot touch its environment and one that is entangled with it. Keep the abstraction clean, and give the environment-specific facilities a designated, separately documented place to live, so that the size of the entanglement is always known and every use of it is visible as such.

**Source:** [The Programming Language Pascal](../works/the-programming-language-pascal.md) — the introduction's statement that the implementation dialect is described by a few amendments included as a separate chapter to demonstrate the brevity of a manual needed to characterize a particular implementation and to show how facilities permitting the programmer to exploit a particular machine are introduced into a machine-independent language; the in-place marking of implementation dependence throughout the definition for the character set, the packed character count, and the integer and real ranges; and the Pascal 6000 chapter itself, listing per-section amendments for the vocabulary, the number of significant identifier characters, the concrete integer, real and character definitions, the restrictions on powerset base types and on structured components, the input and output mode specifiers tied to the host system's permanent-file commands, and the restriction on recursive activation of procedures with local file declarations.
