# State the instruction budget for the frequent case before choosing a representation

**Lesson:** The usual order is to choose a representation, implement the operations, measure, and then repair whatever turned out slow. A better order is available when one operation is known in advance to dominate: write down, before choosing anything, what that operation is *allowed to cost*, expressed concretely enough to be checked — this many memory accesses, one comparison, one increment — and treat every candidate representation as passing or failing that test. A budget written in those terms is not a target to approach but a constraint that eliminates candidates outright, and it does the eliminating while changing course is still free. It also has the useful property of being falsifiable by reading code rather than by running it.

Two things make the budget realistic rather than fantasy. First, it applies only to the frequent case, and you should say so and say why: the rare case — crossing a boundary, growing a structure, taking an exceptional branch — is explicitly permitted to be as involved as it needs to be, because its contribution is its own cost times its own frequency. Second, the frequency should be a number, not an adjective. Knowing that the involved path is taken once per some definite count of the cheap path turns the design into an arithmetic claim someone can check and, when the parameters shift, recheck. A design justified by "usually" cannot be re-evaluated when the usual changes; one justified by a stated ratio can.

The technique that most often brings a candidate inside a budget is worth naming, because it is the same one every time: carry, in the accessing object, the resolved result of the address computation, and recompute it only on the transition that invalidates it. The general computation stays in the code — it is still the definition of where an element lives — but it is executed at transitions rather than at accesses, and what the common path does is dereference something already computed and step it forward. The condition detecting the transition is then the only extra thing the common path pays for, so pick a structure parameter that makes that condition a single cheap test rather than an arithmetic one. This is the general shape of turning an O(1)-but-expensive access into an O(1)-and-cheap one, and it is available far more often than it is used, because it only becomes visible once you have written the budget down and seen the candidate miss it.

**Source:** [Project Oberon](../works/project-oberon.md) — section 7.2's statement that the primary concern in designing the file access scheme must be the efficiency of access to an individual element while scanning, and its specification of that requirement as no more than a comparison of two variables, an indexed access, and the incrementing of a pointer to the successor, with the explicit allowance that the procedure may be more involved when the successor lies in another sector because such transitions occur much less frequently; the initial access program derived from the two-level sector table, judged short but involving considerable address computation at every access; the introduction of a cached current-position address in the rider record as the remedy, with the position redefined to absorb the header offset so the addition disappears; and the closing observation that in all but one case out of a thousand and twenty-four the access consists of three instructions and a single test, described as crucial to the efficiency of file access and of the whole system.
