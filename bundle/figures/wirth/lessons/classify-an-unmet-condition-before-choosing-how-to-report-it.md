# Classify an unmet condition as a caller's error, an implementation's limit, or a wait — before you choose how to report it

**Lesson:** Two operations on the same structure can each fail their guard, and the two failures can belong to completely different categories. Asking for an element past the end of a collection is a mistake by whoever asked: there is nothing there, and no implementation could have made there be something. Failing to append because the storage chosen happens to be exhausted is not a mistake by whoever asked; the request was meaningful and this particular realization could not honour it. The distinction has nothing to do with severity and everything to do with who has to change something for the failure to go away — the caller in the first case, the implementer in the second. Deciding this before writing the handling is what keeps a diagnostic honest, because the categories want opposite treatments: a caller's error should be loud and should point at the call site, while a limit reached should point at the configuration or the design of the component and should never be phrased in a way that makes the caller believe they did something illegal.

The categories are not intrinsic to the condition, which is the part that catches people. Change the surroundings and a condition changes class. Reading from an empty queue is a programming error when a single agent is alternately filling and draining it, because the agent could always have known. Put an independent producer on the other end and the very same condition becomes entirely legitimate — the element is not absent, it has not arrived yet — and the correct response is neither a diagnostic nor a refusal but a delay until the condition holds. Nothing about the queue changed. What changed is whether the caller was in a position to know, and that is the actual test underlying all three categories: could the caller have avoided this with information available to it, could a better-built component have avoided it, or is it simply a fact about time that will resolve itself.

So make the classification explicit at the point where the guard is written, and write down which of the three it is next to the condition. Two payoffs. First, a component whose failure modes are sorted this way can state its precondition precisely — the caller's-error conditions are exactly the preconditions, and everything else is the component's own business — which is the difference between a contract and a list of things that might go wrong. Second, the reclassification that happens when you introduce concurrency becomes a deliberate review rather than a discovery: every guard in the component has to be re-sorted, and the ones that move from error to wait are precisely the places that now need a synchronization mechanism rather than a check. Skipping that review is how a component that was correct alone becomes a component that aborts under load for reasons that read like bugs in the caller.

**Source:** [Algorithms and Data Structures](../works/algorithms-and-data-structures.md) — the closing note of section 1.7.1 distinguishing a sequence growing beyond the implementation's fixed maximum, which is called an inadequacy of that implementation rather than a mistake of the program, from a read proceeding beyond the current end, which is called the program's mistake; section 1.7.2's parallel classification of the buffer guards, where fetching from an empty buffer is a programming error and depositing into a full one is a failure of the suggested implementation; and the same section's observation that once producer and consumer are independent concurrent processes both attempts become quite legitimate and merely have to be delayed until the guarding condition is established.
