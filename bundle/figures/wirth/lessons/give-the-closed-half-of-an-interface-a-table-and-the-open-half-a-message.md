# Give the closed half of an interface a table and the open half a message

**Lesson:** Designs for dispatching an operation to a heterogeneous collection form a ladder, and the useful discipline is to climb it by naming what each rung removes and what it adds rather than by picking the one that is fashionable. A test-and-branch on the element's type in the traversal is direct and cheap and puts every type's name in the base module, so admitting a new type edits the base and recompiles its clients. Attaching the operations to each element as fields removes that — the base no longer names any extension — at the price of storage proportional to instances times operations, and a permanently fixed operation set. Collapsing those fields into one entry point that takes an extensible request removes the fixed operation set, and reintroduces a branch, this time over request kinds. Each rung buys a specific freedom with a specific cost, and none of them is free of both.

The rung that is easy to miss is the one that stops treating the operation set as a single thing. Most interfaces have a part you are genuinely confident is closed — the operations every element must supply for the system to function at all, which you would have to invent anyway if a new one appeared — and a tail you expect to grow in ways you cannot enumerate. Put the closed part in one record per *type*, referenced by a single pointer per instance, so the per-object cost is one word no matter how many operations there are and each call is a direct, statically typed invocation. Put the open tail behind one member of that record which takes an extensible request. Both properties then hold at once: adding an operation for existing types does not touch any object declaration, and adding a type does not touch the base module. The design act is deciding where the line between the two halves falls, and it is a claim about the future you should be able to defend, not a default.

Two smaller consequences generalize. First, when a field of every instance holds the same value for all instances of its kind and is never assigned after creation, it is a constant of the kind and not a variable of the instance, and pushing it into a per-kind record is a mechanical improvement rather than a judgement call — the per-instance copy was paying for a variability nobody uses. Second, prefer building this machinery out of the ordinary constructs already in the language — a record of procedure values, an extensible record parameter — over acquiring it from a built-in facility that hides it. The visible version has an obvious cost model and an obvious data structure, and when the shape you actually need differs from the built-in shape, the visible version can be changed and the built-in one cannot.

**Source:** [Project Oberon](../works/project-oberon.md) — section 13.3's development of the graphics object representation, which passes through the type-test cascade in `drawObj`, the per-object procedure fields, and the single handler with extensible `Msg` records, before settling on a `do` field pointing to a per-type `MethodDesc` that holds the fixed methods (new, copy, draw, selectable, read, write, print) alongside a `handle` method taking an extensible message; including the observations that the procedure fields are never changed and so act as constants rather than variables of each object, and that this construction exhibits the language's type extension and procedure variables without hiding the data structures in a built-in run-time mechanism.
