# Make the container and the contained the same kind of thing, and global policy becomes a local default

**Lesson:** A system that subdivides a resource has to commit to a discipline — how regions are laid out, how they may be split, what shapes are allowed — and that commitment normally propagates all the way down, because the discipline is baked into the manager and the manager is the only thing that knows how to subdivide. The alternative is to define one recursive entity: a region has a position, a size, a behaviour, and a list of sub-regions of the same type. The manager's arrangement is then just the top two levels of a structure that continues downward without limit, and every region is both something managed and, potentially, a manager of its own contents.

The payoff is that the global discipline stops being a law and becomes a default. Whoever owns a region owns how its interior is organised, so a subdivision policy chosen for the system as a whole can be overridden inside any one region by a component that wants something different — and it can do so without a special exemption, an escape hatch, or any change to the manager, because from the manager's point of view nothing unusual is happening. The policy debate that would otherwise have to be settled once for everybody is instead settled per region, by whoever has the context to settle it. This is also what makes such a system genuinely extensible in its display or layout dimension rather than only in its procedural one: a new kind of region defined years later composes with everything already there, because it is the same type.

Two structural conditions make this work, and both are worth checking before claiming the property. First, the specialised types must be extensions of the common one rather than parallel to it, so that a specialised region can be handed to code that knows only the general form and still be treated correctly — including code that has no idea the specialisation exists. Second, the manager must reach its contents by sending them requests rather than by calling operations it knows they have, because the whole point is that the contents were written later and the manager cannot name their operations. Where either condition fails, you have a hierarchy in the diagram but not in the type system, and the flexibility is illusory.

The general form: whenever a design has a manager of things and the things could plausibly manage things of their own, ask whether the two can be one type. If they can, you get nesting to arbitrary depth, local override of global policy, and late-arriving extensions, all from a single declaration — and none of them has to be designed separately.

**Source:** [Project Oberon](../works/project-oberon.md) — section 4.3's introduction of frames as arbitrary rectangles that may recursively contain other frames, with a descriptor carrying a next and a descendant pointer, and the accompanying revelation that the viewer type is a type extension of the frame type so that viewers inherit the hierarchical structure of frames; the same section's example of a desktop class of viewer whose area takes the role of a background covered by an arbitrary collection of possibly mutually overlapping frames, with the explicit statement that the decision to use a tiling scheme globally can easily be overwritten locally; section 4.4.1's note that the viewer manager's data structure is heterogeneous with the frame type as base, the first two levels of the nesting corresponding to the first two levels of the type hierarchy; and the same section's framing of the manager as a manager of black boxes whose contents are unknown to it and whose controlling software might have been developed years later, which it says immediately makes it impossible for the implementation to call fixed procedures and requires a message-oriented interface instead.
