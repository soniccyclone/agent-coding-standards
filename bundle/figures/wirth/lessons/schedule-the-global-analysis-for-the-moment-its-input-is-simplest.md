# Schedule the global analysis for the moment its input is simplest

**Lesson:** Some questions — what is still reachable, what is still consistent, what can be released — are answerable only by looking at everything at once, and are therefore expensive and disruptive. The reflex is to make them cheaper by making them cleverer: incremental algorithms, concurrent variants, finer-grained bookkeeping. There is an earlier and much cheaper move available, which is to choose *when* the question is asked. The cost of a global analysis is dominated by the size and messiness of its starting set, and that set is not constant over the lifetime of a system. Find the instant at which it collapses to something trivial, and run the analysis there.

The instant usually exists and is usually a transition the system already performs. Immediately after start-up, before anything has been opened or bound, nothing holds a live reference to the resource in question except the durable registry, so the reachability question that would otherwise require scanning every module's variables and every intermediate structure reduces to enumerating the registry — a small, well-defined, already-ordered traversal with no concurrency to contend with. The same shape appears at the end of a batch, at a quiescent point between phases, or after a checkpoint. Two things are being bought at once here: the analysis is cheaper because its root set is small, and it is *simpler* because at that moment there are no mutators to race with, so the algorithm can be the naive one instead of the concurrent one. The second saving is usually the larger, since it is paid in code that never has to be written or trusted.

Two obligations come with the choice. Since reclamation now happens only at that instant, the interval between instants is a design parameter, and you have to say what happens to a deployment where the instant rarely arrives — a long-running service that is never restarted accumulates whatever the analysis would have released. The honest response is a manual operation that releases a specific item immediately, offered with its precondition stated in full: the caller, not the system, must guarantee that nothing refers to it, and the consequence of being wrong is unbounded rather than a clean error. Attaching that warning to the operation is not a formality — it marks the boundary of what the design guarantees, and an escape hatch whose precondition is written down is a supported tool, while one whose precondition is merely understood is a trap.

**Source:** [Project Oberon](../works/project-oberon.md) — section 7.2's treatment of reclaiming a file's sectors, which observes that the moment at which a file becomes unreachable from any loaded module's variables and from the directory is difficult to determine, and therefore adopts collection rather than prompt deallocation; the decision to confine that collection to system initialization on the grounds that file space is large and sector collection relatively time-consuming, with the accompanying observation that at initialization the only referenced files are those registered in the directory, so the routine can simply scan the directory and mark each file's sectors in the sector reservation table; and the provision of a purge operation for applications such as servers where initialization occurs very infrequently, together with the statement that the programmer then bears responsibility for guaranteeing no references remain, that this may be feasible in a closed system, and that violating the precondition leads to unpredictable disaster.
