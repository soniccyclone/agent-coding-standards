# Obtaining a handle to something external is a lookup, not an allocation

**Lesson:** A sound general convention says the caller should allocate the object and hand it to the component to be filled in, because then the caller may supply an extended variant and the component still works — allocation by the callee fixes the type and forecloses that. The convention is right often enough to be worth stating as a rule, and there is a class of cases where following it produces a defect, so it is worth being able to say precisely when to override it. The class is: the object being obtained is not a thing in itself but a stand-in for an entity that exists outside the program and has its own identity. Two callers asking for a stand-in to the same external entity must receive the same one. If each caller allocates, each gets a distinct stand-in, each accumulates its own state about the entity, and those states drift out of agreement — which is not a bug in any one caller but a consequence of the interface having promised the wrong thing.

Notice what actually clarifies the question: distinguishing what is being created from what is being obtained. Nobody is creating a new entity; a descriptor is being created, at most, and only if one does not already exist. Once phrased that way the design writes itself — the operation is a lookup in a collection of live descriptors, keyed by whatever identifies the external entity, that creates one only on a miss. And the invariant to state and defend is that each open entity has exactly one descriptor, because that single sentence is what every consistency argument downstream will lean on. Any interface that lets a caller conjure a second one has repealed it, which is why the allocation convention has to yield here rather than the invariant.

The unpleasant consequence is worth carrying too, because it always arrives with this design. The collection of live descriptors is reachable from a fixed root, so nothing in it is ever unreachable, and automatic reclamation will retain every descriptor and everything it holds for the life of the system. There is no clean fix — reachability is exactly what the collection exists to provide — and the remedies are all compromises: teach the reclaimer to disregard this collection and rely on some other rule for emptying it, or make the membership weak so that entries fall out once no ordinary reference remains. Choose deliberately and record the choice as a known weakness rather than presenting it as a design. A registry that grants identity and a reclaimer that infers death from unreachability want incompatible things, and the honest form of that situation is a documented exception, not a pretence that it does not exist.

**Source:** [Project Oberon](../works/project-oberon.md) — the commentary following the file module in section 7.3, which notes that the open operation deviates from the general Oberon rule that an object be allocated by the calling rather than the called module, states the rule's justification as allowing an extension of the type to be allocated for greater flexibility, and gives the reason for the deviation: that not a new file but only a new descriptor is at stake, and that several opens of the same name in different modules must deliver pointers to the same descriptor to avoid file inconsistency, so that each opened file must have exactly one descriptor and opening therefore begins by checking whether one already exists, all descriptors being linked into a list anchored by a global variable; together with the pitfall the same passage identifies, that every opened file thereby remains permanently reachable so that neither descriptors nor their buffers could ever be collected, and the acknowledgement that no better solution was found than designing the collector to exclude that list from its mark phase.
