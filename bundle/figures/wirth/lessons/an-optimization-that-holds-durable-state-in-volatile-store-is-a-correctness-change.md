# An optimization that holds durable state in volatile store is a correctness change

**Lesson:** The most tempting speedups in any system that keeps data across restarts take the form "this piece is touched by every operation, so keep it in fast memory and write it back later." Presented as a performance decision, it is not one. It moves a piece of state that the system's consistency depends on out of the medium that survives failure and into the medium that does not, and it does so for exactly the piece that every operation depends on — so the window in which a crash leaves the durable structure inconsistent is not a corner case but the whole time the system is running. The correct way to score such a proposal is against a different question than "how much faster": what does the persistent structure look like if power is lost at an arbitrary instant, and is that state recoverable?

Two further costs belong in the same accounting, and they are the ones that get left out. The optimized element must now be handled differently from all its peers, so every routine that touches that class of thing acquires a case, and the uniform argument that made the code reviewable is gone — complexity is being spent, not just cycles saved. And the operation being accelerated has to be shown to be on the path that dominates; an improvement to something that is not dominant is unnoticeable at the level anyone experiences, so the complexity is bought with nothing. Put those together with the durability question and you have a three-part test that most such proposals fail, which is worth knowing because they will keep being proposed by people reasoning only about the access count.

The complementary half is what makes this a matter of allocation rather than asceticism. Find what actually dominates, measure it, and spend the effort there instead — and be specific enough to be embarrassed later: name the operation, name the workload size, name the time. When the dominant cost turns out to be a bulk pass over a durable store, the effective remedy is usually not caching but reordering, since transforming a scattered set of accesses into an ordered one converts random seeks into a sweep and costs only a sort of identifiers you already have in hand. Then record the declined optimization alongside the accepted one, with its reasons. That record is the most valuable artifact of the exercise, because the obvious idea will occur to the next person too, and without the record they will implement it.

**Source:** [Project Oberon](../works/project-oberon.md) — section 7.4's statement that every directory operation begins with an access to the root page and that the obvious improvement of holding that page permanently in main store was deliberately not adopted, together with the enumerated reasons: that a hardware failure or a power-off before the root page is written back would leave the file directory inconsistent with severe consequences, that the root page would have to be treated differently from other pages and so complicate the program, and that directory accesses do not dominate the computation so that the improvement would hardly be noticeable and the payoff for the added complexity small; and, in the same section, the contrasting treatment of the initialization routine that traverses the whole directory to build the sector reservation table, where the file sector numbers are collected into a buffer and sorted before the header sectors are read, described as speeding up that reading considerably, with the acknowledgement that this initialization nonetheless dominates the machine's start-up time, on the order of fifteen seconds for a file system of ten thousand files.
