# Ship what the compiler knew, and let the transport carry it uninterpreted

**Lesson:** A translator knows a great deal that its output does not obviously contain: where every variable of a given kind sits, which names were attached to which entry points, what shape each record has. Ordinarily all of it is consumed and discarded, on the reasonable-sounding grounds that the machine only needs the instructions. But every run-time facility that reasons about a program rather than merely executing it — reclaiming storage, resolving a name a user typed, checking a dynamic type, reporting a location in a fault — needs some piece of that discarded knowledge back. There are only two ways to get it: reconstruct it at run time, which is expensive, fragile and sometimes impossible; or decide before translation which parts must survive, and require the translator to emit them as data. The second is the design question, and it wants answering deliberately rather than by whichever facility happened to be built first.

The criterion for what must survive is not "what might be interesting" but "what cannot be recovered from what remains". A collector must know which locations hold references, and no amount of examining the instructions reliably tells it; therefore the set of such locations is emitted as a table. A dispatcher asked for a name typed by a person must map that name to an entry point, and the translator's own numbering scheme deliberately erased names; therefore the names that are meant to be reachable this way are emitted with their offsets. Notice the two-sided design in each case: the same offsets appear both in a table indexed by ordinal for internal linking and in a table keyed by name for external invocation, because the two consumers ask different questions of the same fact, and answering both directly is cheaper than making one of them search.

The structural move that keeps this from accreting is to make the transport ignorant. The loader's job is to place sections and record where they landed; it should copy the collector's table and the dispatcher's table without knowing what either is for, exposing only their addresses in the descriptor it publishes. Then a new run-time facility that needs a new kind of compile-time knowledge is a change to the translator and to that facility, and no change at all to the machinery in between — whereas a loader that understands its payload becomes a dependency of every facility and has to be revised each time one is added. A pipeline stage that interprets what it carries is a stage that must be modified whenever the meaning of the cargo changes; one that merely carries is not.

**Source:** [Project Oberon](../works/project-oberon.md) — section 6.2's account of the two additional parts of a module block beyond those needed for execution and linking: a table of pointer offsets giving, for each global reference variable, its offset in the data section, present because those variables are the roots from which the collector's marking phase begins; and a command table whose entries pair an identifier with an offset, consulted when a user selects a command in a text so that the identifier can be turned into an entry address, the same offsets also appearing in the ordinal-indexed entry table; together with the statement that both tables have counterparts in the object file which the loader merely copies into the block, and that pointers to both are added to the module descriptor.
