# A reference count counts only the references your mechanism can see

**Lesson:** Removal is the operation that exposes whether a dependency-tracking scheme is sound. Tracking usually works by counting declarations: when one component names another, increment; the count is zero, therefore nothing depends on it, therefore it can go. The reasoning is valid and the premise is usually false, because declaration is not the only way a reference comes into existence. Any construct that lets a run-time value denote part of a component — a procedure held in a variable, a callback registered elsewhere, a handler installed in a table — creates a dependency that no declaration records and that the counter therefore does not see. The count is not wrong about what it counts; it is answering a narrower question than the one being asked of it, and the gap is invisible precisely because the counted references are the ones anybody thinks about.

Once you see this, the design question stops being how to make the count exact and becomes what to do about a known-approximate one. Three responses are available and they compose. Do not perform the dangerous operation automatically: if removal cannot be proved safe, requiring a deliberate human request means the residual risk is taken by someone who can weigh it, and does not fire spontaneously at an arbitrary moment. Arrange the substrate so that using a stale reference is *detected* rather than silently wrong — allocate the resource in question strictly monotonically so that a released region's identifier is never handed out again, and a stale use lands on nothing and faults. That converts an unbounded corruption into a localized, attributable failure, which is a large improvement even though it fixes nothing. And state plainly, in the documentation, that the guarantee does not hold, along with the exact construct that breaks it and the conditions under which the detection trick stops working — here, when the resource must be recycled and identifiers are therefore reused, at which point the fault-on-stale-use property is gone and there is no substitute for it.

The transferable rule is to ask, of any accounting scheme, which population it can observe, and then to go looking for the population it cannot. The features that defeat such schemes are almost always the ones that made the system expressive: first-class functions, dynamic registration, values that outlive the scope that created them. That is not an argument against those features. It is an argument for not claiming a safety property that rests on their absence, and for spending the effort instead on making the unsafe case loud.

**Source:** [Project Oberon](../works/project-oberon.md) — section 6.3's treatment of unloading a module, in which each module descriptor carries a reference count initialized at load time and incremented whenever a newly loaded client imports it, the freeing procedure refusing to proceed unless the count is zero and offering a transitive variant that recurses over the module's own imports; the statement that unloading is never automatic and must be explicitly requested by the user; and the accompanying admission that ensuring no references to an unloaded module remain is not at all easy and is not guaranteed, with procedure variables named as the offending construct, since a procedure of one module assigned to a variable of another leaves a dangling reference to the unloaded code block, together with the note that strictly sequential allocation in virtual address space turns such a reference into an unallocated-page trap and that the situation is unsatisfactory on a machine where code space is reused.
