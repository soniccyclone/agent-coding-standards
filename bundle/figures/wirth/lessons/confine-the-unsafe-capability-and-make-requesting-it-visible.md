# Confine the unsafe capability to a named region, and make requesting it visible in the text

**Lesson:** Two requirements that look irreconcilable: the abstraction should be independent of the machine underneath it, and yet it must be able to express every operation the machine can perform, or the people who need that last operation will abandon it entirely. The usual responses are both bad. Weaken the general rules until the dangerous operation is legal everywhere, and the guarantee is gone for all code including the code that never needed it. Refuse the operation, and the abstraction is unusable for the work it was built for, which is how you end up with a system where the interesting parts are written in something else. The third answer is to keep the general rules intact and create a bounded region in which specific rules are suspended — machine-dependent items are introduced inside particular components, and it is inside exactly those components that the compatibility rules are permitted to relax. The dangerous capability still exists; what has changed is that its blast radius is a nameable, countable set of components rather than the whole program.

What makes this more than a naming convention is that entering the region has to be visible in the text of whoever enters it. Put the privileged operations — taking the address of a variable, learning its size, transferring control between coroutines, reinterpreting a word — in a component that must be imported by name before any of them can be written. Now the question "which parts of this system can violate the abstraction" is answered by a search for that import, mechanically, without reading any bodies. Compare the alternative in which the same operations are built-in words of the notation: identical power, but the audit is impossible, because there is no declaration anywhere that says a given piece of code reaches beneath the model. The privileged component should also be subject to the same import discipline as every ordinary component — not a second mechanism for dangerous things, the same mechanism, which is what keeps the discipline from having an exception in the one place exceptions are most harmful.

Generalize the shape and it applies to any escape hatch. First, do not resolve a conflict between safety and reach by lowering the general standard; localize the exemption. Second, require the exemption to be requested rather than merely permitted, so that its use leaves a trace at the point of use, not just in the definition of the thing being used. Third, expect to pay for this with a small standard collection of components that wrap the privileged ones for the common cases, so that most code never requests the exemption at all. The cost is a little ceremony at a few boundaries; the return is that a property of the whole system — where can the model be broken — becomes a finite list you can print.

**Source:** [MODULA-2](../works/modula-2.md) — the introduction's statement of the dilemma between machine independence and a systems language's need to express all operations inherent in the underlying computer, resolved by confining machine-dependent items to specific modules where rules about data type compatibility may be relaxed; together with section 10.2 and section 13, where ADR, SIZE, PROCESS, NEWPROCESS, TRANSFER and IOTRANSFER must be imported from the module SYSTEM before use, and section 13.2's treatment of device registers as variables at declared absolute addresses whose type is chosen by the programmer.
