# Enumerate cases until they cover the precondition, and only then decide their order

**Lesson:** A case analysis has two independent questions inside it, and most of the difficulty in writing correct branching code comes from answering them at the same time. The first question is whether the cases are complete: does every state the code can legitimately be in fall under at least one of them? The second is what happens where cases overlap, which is settled by the order in which they are examined and by whatever redundant tests you strip out once you know an earlier case has already excluded something. These are different obligations with different failure modes — an incomplete analysis has a state with no handler, an ill-ordered one has a state handled by the wrong branch — and the discipline is to close out the first entirely before opening the second.

Completeness has a stopping rule you can actually apply, and it is worth stating precisely because "I think I got them all" is not a criterion. Write down what is assumed true on entry. Then for each way the computation can make progress, write the condition under which taking that step is legitimate — meaning it moves toward the goal and leaves the invariant intact. Keep adding cases until the disjunction of their conditions is implied by the entry assumption. At that point you are done enumerating, and you know it, because there is no state satisfying the precondition that fails every guard. This also hands you the exit condition for free: the analysis terminates exactly when all conditions are false, so whatever you can derive from the conjunction of their negations is what holds afterward. You do not have to argue separately for the postcondition; you read it off.

Deferring the second question is what makes the first tractable. Each case, while you are enumerating, is checked against the invariant on its own — a local obligation involving only that branch — and this stays local only as long as you are not simultaneously reasoning about which earlier branch might already have ruled out part of its condition. Once every case is present and justified in isolation, you can go back and exploit the ordering: drop a conjunct from a later guard because an earlier one has already established it, reorder so the common case is tested first, merge branches that turned out to do the same thing. Each of these is a small, checkable edit against a structure already known to be complete. Done in the other order, they are edits against a structure whose completeness is still an open question, and the two uncertainties multiply.

The wider point is that low-level optimization of a decision structure is almost never where the value is, and is always where the risk is. Ordering guards, eliminating redundant tests, short-circuiting evaluation — these buy little, and they buy it by making the correctness argument non-local. Take them last, take them one at a time, and take them only after the structure they are optimizing has been shown to cover its own precondition.

**Source:** [Algorithms and Data Structures](../works/algorithms-and-data-structures.md) — Appendix C's account of the multibranch guarded loop, in particular its statement that the postcondition is the conjunction of the negations of all guards, that the invariant must hold at the start and end of each branch, that an efficient construction method consists of enumerating the possible situations, describing each by a guard and independently of the others giving it operations that advance toward the goal and restore the invariant, that enumeration stops when the disjunction of all guards covers the assumed precondition, and that construction is simplified by postponing concern with the order of guard evaluation and with optimizations of that evaluation until the loop has been correctly constructed, such lower-level optimizations rarely being significant.
