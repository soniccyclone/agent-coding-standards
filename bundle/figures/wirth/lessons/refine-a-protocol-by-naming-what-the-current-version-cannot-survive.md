# Refine a protocol by naming what the current version cannot survive

**Lesson:** An agreement between two parties is a thing you should be able to write down in a few lines, and the way to arrive at those lines is not to imagine every hazard at once. Start with the version that assumes a perfect world — a request goes out, a reply comes back, the answer is either the thing or a refusal — and write it in full even though it is obviously inadequate. Then state exactly one fact about reality that it cannot cope with, and derive the next version from that fact alone. Each round adds one mechanism, and each mechanism is attached in the record to the specific hazard that forced it. What you get at the end is not just a protocol but a justification for every element of it, which is the part that survives contact with the next person who wonders whether some field is really necessary.

The order in which the hazards are admitted matters, because they are not independent. A limit on how much can be carried at once forces the exchange to become repetitive, which introduces the notion of a continuing conversation, which is what makes loss meaningful at all — there is now a specific missing thing rather than a failed attempt. Loss then forces a deadline on waiting, since silence is indistinguishable from a message that will never come. A deadline forces retransmission, and retransmission forces a way to tell a repeat from a successor, because the party that timed out and the party that was merely slow will otherwise produce a duplicate that nobody can detect. Every one of those is implied by the previous, and running the derivation in that order produces the minimum design; guessing the final feature set instead tends to produce mechanisms whose motivating hazard nobody can any longer state.

Two habits make this concrete. Write the protocol in a grammar: an alternating exchange is a language over the messages, so its legal sequences can be given as productions, and this immediately exposes which party may speak at each point and which sequences are simply not in the language — questions that prose descriptions leave open and implementations then answer differently at each end. And terminate the derivation deliberately. There is always a next hazard, and the right stopping point is not exhaustion but the moment when the remaining hazards are ones you are consciously choosing not to survive, recorded as such, so that a later failure is a known gap rather than an oversight.

**Source:** [Project Oberon](../works/project-oberon.md) — section 10.2's development of the file transfer protocol, which begins by defining the request as a name followed by either the data or a refusal, then observes that this fails because the driver limits the size of each transmitted portion so files must be broken into a sequence of confirmed packets with each acknowledgement also serving as the request for the next and the final portion identified by being shorter than the maximum, then observes that the revised version fails to cope with transmission errors since erroneous packets are silently discarded by the redundancy check, requiring the receiver to impose a timeout and repeat the request, which in turn requires sequence numbers on acknowledgements and data packets so that a repeat can be distinguished from a successor; with the whole development written in a grammar formalism on the stated grounds that the two parties' actions strictly alternate.
