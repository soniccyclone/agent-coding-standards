# An indirection relocates cost into demands on the layer below — enumerate them or the technique fails quietly

**Lesson:** A representation that gets its speed by referring to storage instead of owning a copy of it looks, in isolation, like a pure win: the expensive operation becomes cheap because nothing is moved. The analysis that produces that conclusion is honest but incomplete, because it accounts only for the work the technique does. The work it avoids does not disappear — it becomes a set of standing obligations on whatever layer actually holds the bytes, and those obligations are invisible in the local analysis precisely because they belong to a module you were not thinking about. So the design is not finished when the representation is chosen. It is finished when you have written down what the substrate must guarantee for the representation to be correct, and gone and checked that it does.

Three shapes of obligation recur, and they are worth recognizing by shape rather than by the particular system that produced them. First, a reference outlives the thing that produced it. Once descriptors from one document can name storage originally created for another, no one can any longer reason locally about when a region is dead, and the storage layer must either become able to answer a global reachability question or must give up reclamation entirely within a session. Reclamation and unrestricted sharing are alternatives; picking sharing means paying for the reachability answer somewhere. Second, the *granularity* of the references becomes a performance parameter of a layer that never agreed to it. A representation that in the worst case fragments a small span of data across many descriptors turns one sequential read into a scatter of small reads at unrelated positions, and whether that is fine or ruinous is decided entirely by the buffering strategy underneath — a strategy tuned for one access pattern and now handed another. Third, the concurrency model changes: a store that is being appended to while it is being referenced requires the substrate to permit a reader and a writer on the same object at once, which is exactly the case a simple storage layer forbids.

The habit to take from this is procedural. When you propose an indirection, produce alongside it an explicit, short, numbered list of the properties the underlying layer must have — not prose, a list, because a list can be checked off against a real implementation and prose cannot. Each item on that list is a coupling you have just created, and the list is the honest statement of what the technique costs. The trade may still be excellent; the point is that a technique advertised as elegant and self-contained is usually neither, and the difference between a design that works and one that works only on the machine it was written on is generally whether that list was written down or discovered later.

**Source:** [Project Oberon](../works/project-oberon.md) — the closing discussion of section 5.2, which observes that the piece-chain technique interoperates with the rest of the system in unobvious ways: that after editing, descriptors in one document commonly point into files that originated with other documents, so the file system must either perform reachability-based reclamation or not recycle pages at all even when a same-named file has been rewritten; that a line composed of several small pieces makes sequential reading jump between positions in several files, with mouse tracking becoming visibly unsteady if the buffering mechanism is not up to it; that inserted keystrokes accumulate on a continuously growing file requiring several readers and one writer at once; and the resulting three-item list of qualities the file system must supply for the technique to work, together with the section's summary that the technique depends on a suitable file system rather than standing on its own.
