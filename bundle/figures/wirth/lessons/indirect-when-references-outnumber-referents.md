# Indirect when references outnumber referents, and count before deciding

**Lesson:** A recurring choice in any system that must resolve names late is whether to write the resolved value into every place that uses it, or to write it once into a table and let every use carry only a table index. The choice is usually argued on feel — directness is fast, indirection is clean — but it has an arithmetic answer. The direct scheme performs one resolution per *reference*. The indirect scheme performs one per *referent*. Where a handful of things are named from very many places, that ratio is the entire decision, and it is a ratio you can measure in an existing system rather than guess at.

Three consequences follow from indirection that are easy to miss when only speed is being discussed, and together they usually outweigh the per-access cost. Every use site shrinks, because an index into a small table needs far fewer bits than a full address — and code size is not a vanity metric, it is instruction fetches and cache residency. The body of the artifact is never modified, so no separate record of which locations need patching has to be produced, carried alongside, or kept correct; a whole auxiliary data structure and the code that maintains it simply do not exist. And an unmodified body is a body that can be shared, memory-mapped, or verified, which the patched version cannot. The cost is one small table and one extra memory reference per access, and whether that extra reference is affordable is a question about the substrate — an architecture that provides an addressing mode for exactly this pattern makes the trade lopsided, and one that does not may not.

The last part of the discipline is the one most often skipped: build the alternative and measure it, then publish what you found *including* the parts that did not come out the way you expected. It is a much stronger position to say that the rejected scheme produced code measurably longer by a specific fraction, with a larger penalty in the cases that stress it, and that the expected speed advantage did not show up clearly in the data. That last admission is what makes the rest credible. A design defended by a mechanism nobody tested is a preference; a design defended by numbers that include an inconclusive one is a result — and it also tells a later reader exactly which measurement to redo when the substrate changes.

**Source:** [Project Oberon](../works/project-oberon.md) — section 6.1's statement of the two strategies for converting relative external references into absolute ones, the first patching addresses directly into the code with a list of locations to be patched, the second providing a separate link table that the code refers to by index; its enumeration of the trade — execution speed for the first, and for the second a faster linking process because a conversion is needed once per referenced object rather than once per reference, no list of patch locations, an untouched compiled body, and significantly greater code density from an index typically eight bits wide replacing a typically thirty-two-bit address, against the slight cost of the table; and section 6.2's justification of the second choice by the addressing support and high code density of the target architecture, together with its report of building the alternative and measuring code fifteen per cent longer on average and up to twenty per cent longer where external calls were frequent, with the speed data described as inconclusive.
