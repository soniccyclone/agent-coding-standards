# Match the structure's granularity to the transfer unit, then re-derive the cost

**Lesson:** Moving a structure to a slower medium is mechanically trivial and analytically total. The references stop naming locations in one store and start naming locations in another, and nothing in the code has to change in shape — but the cost model underneath the design is now wrong, because the operation that used to be nearly free is now the dominant expense, and it dominates by orders of magnitude rather than by a constant. Every design decision that was settled by counting comparisons has to be reopened and settled again by counting transfers. This is the general hazard of a substrate change: the algorithm survives the port and the analysis does not, and nobody notices because the code still works.

Redoing the analysis usually reveals a second fact about the new medium, which is that its transfers have a minimum size. Fetching one element brings a whole neighbourhood of elements along at no extra cost, so any structure that consumes exactly one element per fetch is throwing away most of what it paid for. The corrective is to make the structure's unit of decomposition equal to the medium's unit of transfer: gather what would have been many small nodes into one block, fetch the block, and do all the work it permits before fetching again. The effect on the cost is not a constant factor but a change in the base of the logarithm — an operation that took twenty transfers takes three — and that is the whole reason such structures exist. The design parameter to tune is therefore the branching factor, and it is set by dividing the transfer size by the element size, not by anything internal to the algorithm.

Two consequences follow that are easy to get wrong. Once a block is in fast storage, the choice of how to search within it barely matters, because the search happens in the medium whose cost you have just declared negligible; spending effort there is optimizing the term you proved irrelevant. And the improvement is entirely contingent on the blocks staying reasonably full, so the moment blocks can be created by arbitrary growth you must add a rule that bounds their occupancy from below — otherwise the worst case reverts to something far worse than the structure you replaced, since each nearly-empty block still costs a full transfer. Occupancy floor and transfer-sized granularity are one design, not two: the first is what makes the second's arithmetic true.

**Source:** [Algorithms and Data Structures](../works/algorithms-and-data-structures.md) — section 4.7's discussion of placing tree nodes on secondary storage, where the principal innovation is stated to be merely that pointers become disk addresses, followed by the observation that a million-item binary tree needs about twenty search steps each now involving a disk access with its latency, that accessing an item on secondary store brings an entire group of items at little additional cost, and the resulting subdivision of the tree into pages accessed as units, with the arithmetic showing about three page accesses in place of twenty; the note that if the tree is left to grow at random the worst case may still be enormous so that controlled growth is almost mandatory; section 4.7.1's page-occupancy rule bounding items per page between n and 2n and its stated guarantee of at least 50% store utilization; and the remark that the time for the within-page search is probably negligible against the time to move the page into primary store.
