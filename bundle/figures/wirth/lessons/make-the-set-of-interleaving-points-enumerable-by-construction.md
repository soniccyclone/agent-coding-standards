# Make the set of interleaving points enumerable by construction, and hang the exclusion on the boundary

**Lesson:** Reasoning about concurrent code is hard in proportion to how many places control could plausibly leave one activity and enter another. That number is usually treated as a fact about the runtime, and it does not have to be: with a switching primitive that is explicit rather than pre-emptive, the set of switch points is exactly the set of places you wrote one, so it is under your control how large and how scattered that set is. The discipline that follows is to collect the shared state, the operations that touch it, and every transfer of control into a single named region, and to write no transfer anywhere outside it. Now the answer to "where can another activity observe this data mid-update" is not a whole-program analysis; it is the text of one component, readable in one sitting. The shared variables and the switch points have been made co-located on purpose, because the reasoning requires them together and the alternative is a proof obligation spread across every file.

The second move is to attach the protection to the boundary rather than to each operation inside it. If an activity can also be started by something outside the program — a device announcing completion — then the region must be able to suppress those announcements while it is inconsistent, and the natural place to declare that is the region's own heading: one number saying which classes of external event are held off while any operation of this component runs. Compare the alternative of bracketing individual critical sections by hand. Same effect when done correctly, but the correctness is now a property of every operation individually, and the next operation somebody adds is one omission away from breaking it. Declaring it once on the enclosing boundary makes the protection a property of membership, which is the difference between an invariant that holds by construction and one that holds by vigilance. Accept the residual honestly: the value chosen has to match what the hardware actually assigns to the device, and nothing in the notation can check that — it stays the programmer's responsibility, and stays worth writing down as such.

The transferable content is a general strategy for taming a cross-cutting hazard. Find the smallest textual region that the hazard can be confined to, make confinement structural rather than conventional, and then express the countermeasure as an attribute of that region instead of as a step in each procedure. When you can do that, the number of things you must check does not grow as the component grows. When you cannot, ask whether the hazard is escaping because the primitive is too permissive: a facility that lets control leave at any point is a facility that has made the set of interleaving points unbounded on your behalf, and no amount of local care recovers what that took away.

**Source:** [MODULA-2](../works/modula-2.md) — section 13.3 on interface modules, which recommends grouping shared variables such as buffers together with the procedures that operate on them in one module and programming transfers of control only within it, and the accompanying rule that such a module's heading may specify a processor priority so that all its procedures execute with interrupts from devices at or below that level disabled, with the note that matching the priority to the device remains the programmer's responsibility.
