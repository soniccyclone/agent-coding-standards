# Separate the unit of action from the unit of packaging

**Lesson:** Most systems inherit a conflation they never chose: the thing you build and deploy is also the thing you invoke. One artifact per translation, one entry point per artifact, so the smallest action a user can request is the whole of whatever somebody decided to compile together. Compare that unit against the actions people actually want — insert a fragment here, rename this, show me what is in there — and the mismatch is enormous. The consequence is not only clumsiness at the interface; it distorts the software, because anything that ought to be separately invocable has to become its own deployable artifact, and the packaging then fragments to match the invocation granularity rather than to match what belongs together.

The fix is to notice that these are two different questions and let each have its own answer. What belongs together for purposes of compilation, naming, and dependency is one question, settled by cohesion: what shares a representation, what maintains a common invariant. What constitutes one request is a different question, settled by the user's model of the work: the smallest change to the world that makes sense on its own. Once the two are decoupled, a package can offer many actions, and an action can be small enough to be worth invoking by pointing at it. The cost is a naming convention that identifies an action by the package it lives in — and that cost is trivial next to what it buys.

The consequences reach further than convenience. If actions are small and numerous, the interface between them cannot be a heavyweight artifact created and destroyed per invocation; it becomes whatever state the system already holds, and the design question shifts to which parts of that state are legitimate to communicate through. If actions are small, the granularity at which the system may switch between concurrent lines of work can be an action rather than an instruction, which removes at a stroke the need for locking and for defending shared state against interleaving. And if an action is defined as a unit that does not stop to ask questions, then anything that would have been a mid-action prompt becomes instead the boundary between two actions, with whatever the user does in between — including running something else entirely — perfectly legitimate. Each of these follows from the initial split, which is why the split is worth making deliberately rather than discovering by accident.

The general form: whenever a system has one notion serving as both the deployment unit and the invocation unit, ask what would change if it did not. Usually the invocation unit wants to be much smaller than anyone has been letting it be, and the reason it is not is a tooling accident rather than a design decision.

**Source:** [Project Oberon](../works/project-oberon.md) — section 2.2.2's statement that a program in the common sense of a text compiled as a unit is far too large a unit of action to serve as a command, compared explicitly against the insertion of a piece of text by a mouse click, and its consequent separation of the unit of action, an exported procedure, from the unit of compilation, a module, so that a module typically defines many commands identified by the pair of module and procedure name; section 2.2.2's further observation that because modules persist after command termination the links between consecutive commands are not restricted to files but can be any global variable; and section 3.3.1's definition of a command as an atomic action without user interaction, with the argument that when a traditional interactive program requires input in order to proceed there is no justification for forbidding the user to preempt it and start another task to produce that input, so a traditional interactive program is properly viewed as a sequence of atomic actions separated by interactions.
