# Find the notion the hardware event already is, instead of adding machinery to describe it

**Lesson:** When a physical event has to be brought into an abstract model, the instinct is to add a construct for it, and that instinct is usually wrong, because the construct arrives with its own semantics that then have to be related to everything already present. The better first question is whether the event is an instance of something the model already has, viewed from an unfamiliar angle. An interrupt looks like a new kind of thing — asynchronous, externally caused, outside the program's control flow. Look again with a symmetric switching primitive in hand, one that suspends the current activity, records where it was, and resumes a named other activity, and the interrupt is simply one half of that operation with the two halves separated in time: the program performs the outbound switch and simultaneously arranges that the return switch will be triggered by the device rather than by an instruction. Nothing new has been introduced. One existing operation has been given a variant in which the second party is the hardware.

The same test applied to device access gives the same answer. A control register is a location with an address, and a variable is a location with an address, so what is needed is not statements for input and output but the ability to fix a variable's address at its declaration and to let the programmer choose the type through which its bits will be read. The abstract notion was already general enough; only the binding of address was missing. Two payoffs follow whenever this works. The count of irreducible concepts does not grow, so everything already proved or understood about the general notion applies to the hardware case at no extra cost. And the asymmetry that remains is small and locatable, which is what lets it be confined rather than spread: the variant operation and the address-fixing declaration are the only places where the physical world is visible.

The discipline is to spend effort searching for the unifying notion before spending it on new constructs, and to be suspicious of a design in which the hardware-facing part has its own vocabulary. That vocabulary is a signal that the abstraction was built for the comfortable cases and the uncomfortable ones were bolted on, which is precisely the arrangement in which the two halves drift apart. Note also the negative result this implies: if no existing notion covers the event without distortion, that is real information about the model, not a licence to add whatever is convenient. The right response is to look for the more primitive operation from which both the familiar and the physical case can be built — the reason the symmetric switch works here is that it is lower-level than the process abstraction people usually reach for, and being lower-level is what let it reach the device.

**Source:** [MODULA-2](../works/modula-2.md) — section 13.1's TRANSFER operation, which suspends the calling activity, assigns it to one variable and resumes the one designated by another; section 13.2's IOTRANSFER, described in explicit analogy to TRANSFER as the same suspension and resumption with the return transfer additionally prepared and later initiated by the interrupt signal from the device at a given vector address; and the same section's treatment of device registers as variables whose absolute address is given in the declaration and whose data type is left to the programmer's choice.
