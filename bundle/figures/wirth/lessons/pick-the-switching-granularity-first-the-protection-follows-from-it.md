# Pick the switching granularity first; the protection machinery follows from it

**Lesson:** Concurrency is usually adopted as a capability and its costs are then absorbed as inevitable: shared state must be guarded, guards can deadlock, every piece of state that two lines of work touch acquires an ownership discipline, and the whole apparatus has to be reasoned about at every future change. But almost none of that follows from concurrency as such. It follows from one parameter — how finely control may be taken away from a running line of work — and that parameter is a design choice, not a fact about the problem. Set it at the instruction, and every shared variable is a hazard because a switch may fall between any two operations on it. Set it at some coarse, meaningful unit of work, and the hazard disappears: there is no interleaving to defend against, because the points at which control can move are the points at which the work is between consistent states by construction.

The consequence is that whole mechanisms simply do not need to exist. No locks, because nothing can be observed half-updated. No deadlock analysis, because there is nothing to acquire. No preserved per-line-of-work state across a switch, because a switch only happens where the line of work has finished and has nothing to preserve. This is not an optimization to the usual design; it is a different design in which the usual problems are absent rather than solved. What you give up is responsiveness at fine grain: a unit of work, once begun, runs to its end. Whether that is acceptable is a real question, and it is the only question — which is exactly the point, because it is a question about your workload rather than about correctness.

Two further moves make the coarse choice practical rather than merely appealing. The first is to separate the arrival of an event from the servicing of it: something asynchronous still has to be captured the moment it happens, so the lowest layer records it in a buffer and returns immediately, without disturbing whatever is running. Interruption exists, but it is confined to that layer and is invisible above it, so the coarse-grained model holds for everything written against the system. The second is to make sure that the unit of work is genuinely small in the common case, which is why the granularity question and the question of how big an invocable action should be are the same question asked twice. A system whose actions are typically milliseconds can afford to run them to completion; a system whose actions are typically minutes cannot, and will be driven back toward fine-grained switching and everything that comes with it.

The general form: before accepting the standard toolkit for a hard problem, look for the parameter whose setting is why the problem is hard. Often it was set by convention rather than by necessity, and moving it makes the toolkit unnecessary instead of merely better.

**Source:** [Project Oberon](../works/project-oberon.md) — section 2.2.3's account of the single-process scheme, in particular the statements that task switches occur at user-defined points where no local process state has to be preserved until resumption, that because the switches are chosen rather than imposed the tasks cannot interfere by accessing common variables, and that the system designer can therefore omit all kinds of protection mechanisms; its identification of the essential difference from multiprocess systems as one of granularity of action, switches occurring between commands rather than after any single instruction; the same section's treatment of buffering in device drivers so that an interrupt evokes no task selection or switch and returns control to the point of interruption, remaining unnoticeable to programs; and section 3.1.2's conclusion that transfers of control between tasks are ordinary procedure calls and returns, preemption is not possible, active periods are sequentially ordered, and consequently locks of common resources are dispensable and deadlocks are not a topic at all.
