# Prefer the state that is already visible as the interface between steps

**Lesson:** When successive operations communicate through persistent state rather than through arguments passed at the call, the flexibility gained is enormous and the danger is exact: the outcome of an operation now depends on things the person invoking it cannot see. That is the whole of the problem, and stating it that way makes the remedy specific. Persistent state is not the hazard; *invisible* persistent state is. So the discipline is not "avoid globals" — a rule that would forbid the good cases along with the bad — but "prefer, as the medium of communication between steps, the parts of the state that are already being displayed." When the shared structure is the one the user is looking at, referring to it is not a hidden dependency; it is the most honest possible parameter, because the argument and its presentation are the same object.

This gives a design test that is sharper than the usual one about scope. For each piece of state that outlives an operation, ask whether someone deciding what to do next can determine its value by looking. If yes, it is a legitimate interface and should be used as one. If no, it is a mode — a state of the system that silently changes the meaning of what you do — and every mode is a thing the user must remember instead of see. The accumulation of modes is what turns a system into something whose behaviour you predict by reconstructing history rather than by observation, and reconstructing history is precisely what people are bad at.

The same criterion resolves how to treat failure. If the interface between steps is a fresh artifact created per operation, an operation that dies mid-way leaves nothing and the work is gone. If the interface is durable state, an operation that dies leaves that state in whatever condition it reached — possibly inconsistent, but present and inspectable — and the next operation can start from there. This turns a failure from an event that destroys context into an event that merely ends one step early, which is a much better thing for a failure to be. It also argues for spending effort on making the failure legible, since the state at the moment of failure is now the most valuable diagnostic available and the whole point is that it survived.

The transferable rule: when choosing what two stages of a system will communicate through, weight observability as heavily as convenience. A slightly clumsier channel that the operator can see beats a frictionless one they cannot, because every invisible channel is a fact about the system that has to be carried in someone's head, and heads are the least reliable storage in the design.

**Source:** [Project Oberon](../works/project-oberon.md) — section 2.2.2's discussion of using global variables as interfaces between commands, which names the danger as hidden states, hidden in the sense that the user is generally unaware of them and has no easy way to determine their value, and its positive counterpart that the display structure is rooted in a global variable so that parts of it constitute visible states which are highly appropriate to refer to as command parameters, together with the stated rule of the Oberon programming style to avoid hidden states and reduce the introduction of global variables while explicitly declining to raise it to a dogma; section 2.2.3's claim that the state of the system is practically determined by what is visible to the user so that no long history of previously activated commands and entered modes need be remembered, with the remark that modes are the hallmark of user-unfriendly systems; and section 2.2.2's closing observation that a detected failure results in a trap treated as abnormal command termination, after which global data may be left inconsistent but are not lost, a next command can be initiated from their current state, and the trap opens a viewer listing the invoked procedures with their local variables and values.
