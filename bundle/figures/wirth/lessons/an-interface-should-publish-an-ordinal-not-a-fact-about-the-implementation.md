# An interface should publish an ordinal, not a fact about the implementation

**Lesson:** Separate compilation is worth having only if it delivers one specific property: a change confined to a component's implementation must not oblige its clients to be rebuilt. That property is not achieved by declaring an interface; it is achieved by auditing what the interface actually carries. Every value in a published interface that is *derived from* the implementation rather than *chosen for* the interface is a recompilation trigger, because a change that moves it invalidates the copies clients baked into themselves. The test is mechanical and worth running item by item: for each thing the interface publishes, ask what would have to change inside for that value to change. If the answer is "an ordinary edit", the item does not belong there.

The replacement is an identifier the interface owns: assign each exported entity a position that is stable by fiat, publish that, and require the *loader* to convert positions into implementation facts at the moment of use, by reading a translation table that the implementation ships alongside itself. Now the implementation may be rearranged freely, since it regenerates the table whenever it is rebuilt, and clients hold nothing but positions. The general shape is worth recognizing beyond compilation: whenever two independently versioned parties must agree on a name, have them agree on a token that neither party's internals determine, and put a translation step at the boundary. The translation costs something, and what it buys is that one side can change without the other's consent.

The honest part of this reasoning is the exception, and it should be argued the same way rather than hidden. There will be a case where the translation is judged not worth its cost and the implementation fact is published directly — accepting that changing it forces clients to rebuild. That is a legitimate decision, but only when the argument is made explicitly and rests on something checkable: that entities of this kind are few, that they are declared where a change is conspicuous, and above all that ordinary changes to the component do not disturb them. Note what makes the last clause true and be sure it is: additions and removals of the *non*-published entities of that kind must not shift the published ones, or the exemption silently becomes a trigger on every edit. An exception with a stated bound can be re-examined when the bound stops holding; an exception adopted by default cannot be found at all.

**Source:** [Project Oberon](../works/project-oberon.md) — section 6.1's account of separate compilation, in which a module's interface as recorded in its symbol file specifies a unique number per exported procedure rather than an entry address, stated as being so that the implementation can be modified and entry addresses changed without affecting the interface, and identified as the crucial property that implementation changes must not force recompilation of clients; the consequent requirement that the object file carry a table of entry addresses indexed by procedure number so the loader can perform the binding, and that an external reference in code be a module-number and procedure-number pair indexing an import table and that module's entry table; and the immediately following treatment of exported variables, where the same scheme is said to be available but not used, the offset being placed directly in the code instead, with the acknowledged drawback that a change to a variable's address forces client recompilation and the justification that exported variables are rare, are declared at the start of the text, and that additions or deletions of non-exported variables do not affect the exported information.
