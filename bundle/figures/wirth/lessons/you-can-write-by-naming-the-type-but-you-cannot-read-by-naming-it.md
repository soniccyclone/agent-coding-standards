# You can write by naming the type, but you cannot read by naming it

**Lesson:** When a component supports both directions of a transfer, the reflex is to build the inbound interface as the mirror image of the outbound one: an operation per kind of thing, named to match. Outbound this is exactly right, because the caller already holds a value and its kind is known before the call — choosing the operation is choosing what you have. Inbound the same design is a trap, because the kind of the next item is not something the caller knows; it is the thing the caller is trying to find out. An interface that requires you to name the type in order to read it has silently made the caller responsible for a prediction, and a prediction that is wrong does not fail cleanly, it consumes the wrong number of units and corrupts everything after. The apparent symmetry of the two directions hides a real asymmetry in when the information is available.

The correct inbound shape follows directly: one operation that consumes the next item and afterwards reports what it turned out to be, with the value available under a discriminator the caller inspects. Determination happens after the read rather than before it, which is the only ordering the information permits. Notice what this costs and what it buys. It costs generality — a component that classifies items must have an opinion about what an item is, so an implicit grammar is now baked into the reader that was not present in the writer, and that grammar has to be stated. It buys the elimination of a whole failure class, since the caller can no longer misdeclare what is coming. The trade is almost always worth taking, and the stated grammar is the deliverable that makes it honest: an inbound interface that classifies without publishing the rules by which it classifies has only moved the guessing.

The general principle is that inverse operations are inverses on values, not on interfaces. Before pairing a reader with a writer, a decoder with an encoder, or a query with a command, write down what each side knows at the moment it is invoked. Where the two knowledge sets differ, the interfaces have to differ, and forcing them into symmetry for the sake of a tidy API imposes the harder side's ignorance on both. The asymmetry usually points the same way — the producing side knows its own intent, the consuming side is discovering someone else's — which is why consuming interfaces so often need a classification step that producing interfaces do not, and why building the consumer as a transliteration of the producer is such a durable source of protocol bugs.

**Source:** [Algorithms and Data Structures](../works/algorithms-and-data-structures.md) — section 1.7.4's statement of an essential asymmetry between input and output of texts, that a text is generated by a sequence of calls of type-specific writing procedures while reading a text by the corresponding sequence of type-specific reading procedures is questionable practice because one wishes to read the next element without knowing its type and to determine the type after reading it; and the resulting introduction of a scanner that reports the class and value of the item just read, together with the observation that a scanner necessarily imposes a syntax on the text, which the section then specifies explicitly.
