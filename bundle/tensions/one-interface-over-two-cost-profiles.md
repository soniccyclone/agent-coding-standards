# One name over two realizations: proof of a good abstraction or a false claim of equivalence

## The decision
You have one described operation that could be backed by two realizations with radically different prices and radically different ways of going wrong: the pipeline held entirely in memory or staged through files, the value fetched from this machine or from another one. The question is whether both realizations are entitled to answer to the same name. Hoare treats the existence of the second realization as the proof that the abstraction was worth writing. Wirth treats presenting the two as one operation as the definition of a dishonest interface.

## Hoare: if only one realization is sensible, the description was a paraphrase of the code
[The mark of a successful abstraction is that it admits several implementations](../figures/hoare/lessons/a-successful-abstraction-admits-several-implementations.md) offers a criterion in place of the usual unfalsifiable defences of abstraction. Cleanliness and detail-hiding cannot be checked; this can. An abstraction has earned its place when the same description can be realized in genuinely different ways, each correct, each the right choice under some real constraint. His case is a multi-pass compiler: with enough store, every pass is live and items flow between them as produced; without, one pass runs to completion into a file that the next pass reads back. Different resource profiles, different failure characteristics, different code, same answer.

The criterion's value is that it tells you when to stop designing. A description admitting only one sensible realization will change every time the implementation does, because it is the implementation with different punctuation. A description admitting several turns the choice into a decision made once per deployment and revisitable when constraints change, so one product spans a range of machines. He also asks you to keep implementation vocabulary out of the description, since anything in it that only one realization needs quietly rules out the one you will need on the machine you did not anticipate. His companion rule, [an operation is primitive when its cost depends on the representation](../figures/hoare/lessons/an-operation-is-primitive-when-its-cost-depends-on-the-representation.md), holds the line even for operations that are ruinous on large values: keep them, because meaning is uniform across types and the price is negotiated later, in the open.

## Wirth: an interface that spans two failure profiles is asserting an equivalence that does not hold
[Do not hide a difference in kind behind a uniform interface](../figures/wirth/lessons/do-not-hide-a-difference-in-cost-behind-a-uniform-interface.md) attacks the same situation from the caller's side. Making the remote thing look like the local thing is a fine engineering challenge, and the framing is the mistake, because speed is not the only difference. The remote case can fail where the local case cannot, can fail halfway, can fail after appearing to succeed, and can be slow enough that an algorithm which was reasonable becomes absurd. Code written against the merged interface is correct only for whichever case its author happened to have in mind.

His alternative is to give the second thing its own name, its own invocation, and its own layer that a program may decline to depend on. The gain is what becomes sayable about the system: the places that can fail for reasons outside the machine are visible in the text and can be counted, the cost of a design shows up at the point of design because someone writing the transfer explicitly notices when they have put it in a loop, and the base system does not depend on the facility, so it can be absent or broken without implicating everything else. The general rule is that an abstraction may hide a layout, a device model, an algorithm choice, and may not hide a difference in failure modes or a cost difference large enough to change which algorithms are viable, because those are the things the caller is obliged to reason about.

## Resolution
**LLM DECISION — Nathan may overturn.**

The line is how many realizations are live inside one running program, and both lessons state their own side of it clearly enough that this is not a reconciliation imposed from outside.

Hoare's realizations are alternatives to each other. His own text calls the choice a deployment decision, made once, for a machine, and the client program above is textually unchanged and correct under whichever one it got. Exactly one is present in any given system, and the party who chose it, the person deploying, knew which. Wirth's are not alternatives. Local and remote access coexist in a single program and are selected per call site, so the caller cannot be written once and be right; every use has to be reasoned about individually, and the merged interface is precisely what removes the information needed to do that. When realizations are alternatives, one name is right, and Hoare's test is a genuine falsifiability check on whether a description constrains enough to be worth having. When realizations coexist and are chosen per use, Wirth's rule governs and the second one gets its own name.

The important consequence is that following Wirth costs Hoare nothing. Two named operations can still answer to one description; Hoare never requires the alternatives to be reachable through the same call site, only that the same description govern both. His criterion is applied to a description before you build, as a test of whether the abstraction is doing work. Wirth's is applied to a shipped interface, as a rule about what a caller may be made to depend on unwittingly. A design can pass the first and fail the second, and the repair for failing the second is renaming, not abandoning the shared description.

One residue is real and Hoare should concede it. He claims differing failure characteristics as evidence of a good abstraction while also claiming the results are indistinguishable, and those cannot both hold in the failure cases. The file-staged compiler can run out of disk; the in-memory one cannot. If the description is silent about that, a client correct on one deployment is incomplete on the other, and the deployment decision has quietly become a change to the program's obligations. The fix is within his own rules: whatever the caller must handle belongs in the description, stated in terms neutral between realizations, and only the differences the caller never handles are free to vary underneath. Under that repair his criterion still bites and his compiler example still passes, because what actually varies there is store versus disk pressure inside a batch job, not the set of outcomes the client program deals with.

The same question about price rather than about failure is worked out in [cost model against uniform generality](cost-model-vs-uniform-generality.md), and the two resolutions land on the same test: a difference may live under one name when the party obliged to act on it has been told, and may not when it has been made invisible to them.

**Strongest counter-argument:** the count of live realizations is not stable, and Hoare's side of the line may be the temporary one. The pipeline that was chosen per deployment becomes chosen per stage, then per input size at run time, because that is what every mature system does with a knob it was given. If the honest end state of any successful abstraction over two cost profiles is that both realizations end up live and selected dynamically, then the resolution proposed here just delays Wirth's objection rather than answering it, and the safer rule is his from the first day: name them separately at the outset, and let a higher layer choose between two visible things rather than discovering later that one name has silently become two.
