# A question with no principled answer: delete the vocabulary or publish a menu of answers

## The decision
You are designing a notation, a model or a language standard, and it contains a question whose answers keep coming out arbitrary or machine-dependent: whether two occurrences coincided, how long something took, what happens when a sum exceeds the register. You have to decide what the notation does about it. One option is to remove the words, so that nothing written in the notation can refer to the thing at all. The other is to keep the words, state the properties every implementation must honour, and publish a short list of mutually exclusive answers from which each implementation picks one. Hoare gives both instructions, generalized in both cases, and applied to the same question they produce opposite artifacts.

## Hoare on the deletion side: take away the ability to ask
[Make the awkward question unaskable rather than answering it carefully](../figures/hoare/lessons/make-the-question-unaskable-rather-than-answering-it-carefully.md) argues that a model which records when each thing happened has committed itself to being interrogated about simultaneity, and every answer it can give is either arbitrary or a bet on one machine's speed. Keep only the order of occurrences and the question loses its expression. Nothing can depend on it because nothing can say it, which is a much harder guarantee than a rule asking designers not to depend on it. He is careful that this is not a loss, because the cases that mattered are re-encoded rather than dropped: where two parties must genuinely act together, that becomes one indivisible occurrence with one name, so the togetherness is carried by structure and cannot be broken by scheduling; where it does not matter, both orders are permitted and neither preferred, which is the positive statement that the difference is unobservable. Duration gets the same treatment, an extended activity becoming a start and a finish, so overlap is defined by order alone. Then he generalizes: when a modelling question keeps producing arbitrary answers, remove the ability to ask it.

## Hoare on the menu side: keep the question, bound the answers
[Underspecify on purpose](../figures/hoare/lessons/underspecify-on-purpose-and-make-the-choice-explicit.md) starts from a dilemma about specification. Pin down every behaviour and implementers are forbidden from doing the sensible thing on hardware nobody anticipated. Leave it unstated and portability degenerates into folklore, with programs acquiring silent dependencies on whatever the local implementation did, surfacing years later on a different machine. His way out is that the dilemma has only assumed two options. The third is to specify the decision as a choice: a common core of properties that hold everywhere, plus a small menu of mutually exclusive supplementary properties covering exactly what an implementer legitimately decides. The payoff is that reasoning is conducted against a stated property set, so a program that actually leans on a local decision cannot pretend otherwise. The proof refuses to go through on the core alone, the dependence surfaces while you are still reasoning rather than while you are migrating, and every site that would break on a differently-configured host is already marked, because those are the sites where the argument used the menu item. Machine dependence stops being contamination and becomes a declared parameter.

## Resolution
**LLM DECISION — Nathan may overturn.**

The two rules are selected by whether the arbitrariness goes all the way down, and the test is whether any implementation has a definite answer that a client could sensibly rely on.

Simultaneity in the CSP model is arbitrary at every level. No machine has a considered position on whether two occurrences coincided; the answer is an artifact of how the recording was taken, it is not stable across runs on the same host, and there is no client whose correctness could rest on it. Nobody owns the distinction, so deleting it takes nothing from anyone. Overflow is the opposite. Each host has a definite, stable, engineered answer, and the answer is not arbitrary where it lives, only variable across sites. There are clients whose correctness rests on it, a checksum wanting wraparound being the obvious one. Deleting overflow from the vocabulary would not be removing residue, it would be confiscating something both parties legitimately hold. That is the line: delete an unowned distinction, menu an owned one.

The re-encoding move is the practical check for ownership, and it is the part of the unaskable lesson that does the real work. Hoare does not merely drop simultaneity, he claims the legitimate uses survive translation into vocabulary that remains, and he names both of them. Run the same exercise on overflow and it fails immediately, because there is no restructuring of arithmetic under which "this computation wraps" and "this computation aborts" become the same statement. So the procedure is: try to say each legitimate need in the reduced vocabulary. If they all go through, the question was never carrying anything and you should remove it. If one refuses to translate, someone owns the distinction, and your remaining choice is silence or a menu, where the menu wins for the reasons the underspecification lesson gives.

That leaves the case the spotting note raised as a counterexample, and it turns out to be a third disposition rather than a contradiction. Real-time clients do need duration, CSP cannot say it, and Hoare drops it anyway. He does not put it on a menu either. The reason is a second condition the menu technique requires and elapsed time cannot meet: a menu has to be small and its entries mutually exclusive. Overflow has three disciplines and you can write them down. Elapsed time is a continuum, so any menu over it is either a fiction or the whole real line, and either way the bookkeeping benefit collapses. When a distinction is owned but not enumerable, Hoare's actual move is to expel it into a separate concern with its own vocabulary, which is exactly what "settle logical correctness first and treat timing independently" means. So the full disposition is three-way: delete what nobody owns, menu what is owned and enumerable, and split off what is owned and continuous.

One consequence is worth stating because it cuts against a comfortable reading. Under this account the menu is not the safer general-purpose option and the deletion is not the aggressive one. Deletion is the cheaper move and should be attempted first, because it costs nothing when it succeeds and its failure is loud, showing up as a legitimate need you cannot restate. Reaching for a menu before running that check leaves declared parameters in the standard for distinctions no implementation actually owns, and each one is a permanent bookkeeping obligation on every proof conducted against it.

**Strongest counter-argument:** ownership is judged, not measured, and it is judged before the clients exist. The unbounded-versus-bounded integer split looks obvious in hindsight because we have decades of code that depends on wraparound, but the same reasoning at the time the standard is being written is a designer guessing which distinctions someone will later want to depend on. Guess generously and you menu everything, which is the failure the resolution warns about. Guess meanly and you have confiscated something, and the confiscation is invisible in the way Hoare himself says these failures are invisible, since you never see the program that could not be written. There is a sharper version: the re-encoding check is not a test of ownership at all, it is a test of the designer's ingenuity. Hoare found the joint-occurrence encoding for simultaneity because he was Hoare. A less able designer runs the same check on the same question, fails to find the encoding, concludes the distinction is owned, and ships a menu that a better model would have made unnecessary. If that is right, the honest rule is weaker than mine and closer to the plain unaskable version, which is that you should keep attacking the question until it disappears and treat the menu as an admission of defeat rather than as a coordinate disposition with its own domain.
